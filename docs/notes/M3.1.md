# M3.1 — Memory bandwidth: read, write and copy

*Milestone notes, written for someone learning benchmark methodology. Measured on
2026-09-21 on a Core Ultra 9 185H laptop under WSL2, release build, **plugged in**, Windows
power plan "Balanced", power mode **"Best performance"** ("Max Performance Overlay"),
battery 100 % and charging, Docker containers stopped. Power state was recorded before and
after every run; the logs are in `docs/results/m3.1/`. Earlier notes: `M1.2.md`, `M2.1.md`,
`M2.2.md`, `M2.3.md`, `M2.4.md`, `M2.5.md`.*

## The problem this milestone solves

Phase 2 measured how fast the CPU can compute. This one measures how fast it can be *fed*,
which on modern hardware is usually the number that decides whether a program is fast.

"Memory bandwidth" sounds like one number. It is at least six, because it depends on two
things the phrase leaves out:

- **How far away the data is.** A buffer that fits in L1 and a buffer that lives in DRAM
  are both "memory", and on this machine they are **11× apart** for reads.
- **What you are doing to it.** Reading, writing and copying are three different
  transactions with three different costs, and a write costs more than it looks like it
  should for a reason that is invisible in the source code.

So the milestone builds one workload with three metrics and a working-set sweep, and the
output is a curve rather than a number. The curve is the interesting artifact: it is a
picture of the cache hierarchy taken from inside a VM that never told us the hierarchy
exists.

## What was built

1. **`mem_bw`** — one workload class, three metrics (`mem_read_bw`, `mem_write_bw`,
   `mem_copy_bw`), selected per configuration. Per-thread buffers of `working_set_bytes`,
   huge pages when ≥ 2 MiB, first-touched by the owning thread.
2. **`--nt`** — non-temporal (streaming) stores for the write and copy kernels, recorded
   in `params.nt` / `params.nt_effective`.
3. **`--no-hugepages`** — turn off `MADV_HUGEPAGE`, so the huge-page path can be tested
   rather than assumed (its payoff is measured in M3.2, where TLB pressure matters more).
4. **`--metric`** — select individual metrics rather than whole workloads. `mem_bw` alone
   is three configurations per working set, and a sweep of fifteen working sets is 45.
5. **Runner generalization** — the piece that took the most care, described below: the
   trial loop no longer assumes that a workload has one metric, that its unit of work is an
   "op", or that a value is a rate.
6. **Schema**: eight new `params` keys (`unit_of_work`, `mem_mode`, `buffer_bytes`,
   `passes_per_batch`, `nt`, `nt_effective`, `huge_pages_requested`,
   `pre_trial_prep_max_us`). All additive; no `schema_version` bump.
7. **27 new tests** (`mem_bw_test.cpp`, and `mem_bw_scaling_test.cpp` labelled `perf`).
   137/137 pass in release, debug, ci, asan and tsan.

## The runner had to stop assuming three things

The trial loop from M2.1–M2.5 was written for the CPU workloads and had their shape baked
in. Three assumptions had to come out before a bandwidth metric could exist at all, and
each one is a small lesson in what a "benchmark result" is.

### 1. A workload has one metric

`cpu_int` produces `cpu_int_ops` and nothing else, so the runner held a single `Metric` per
configuration. `mem_bw` produces three.

The tempting design is one trial that reads, writes and copies and reports all three. It is
wrong: a trial that does all three measures none of them, because each kernel leaves the
cache and the memory controller in a state the next one inherits. So a configuration is per
**metric**, not per workload, and `--workload mem_bw` expands to three configurations that
each get their own worker pool, their own warmup and their own trials.

There is exactly one exception, built now because M4.1 needs it: a metric that is a
*different reading of the same trial*. `disk_rand_read_p99_us` is the 99th percentile of
precisely the reads that `disk_rand_read_iops` counted. Running it separately would measure
a different second's worth of I/O, cost twice the time, and give a worse answer. Those
"rider" metrics ride along in the same session and are emitted next to their host. The
`--metric` flag refuses a rider on its own, because asking for it alone would silently run
something else.

### 2. A work unit is an "operation"

`params.ops` used to be unambiguous because everything counted operations. Now `ops` is
bytes for a bandwidth metric, dependent loads for a latency chase, completed I/Os for IOPS.
The same key holding three different kinds of thing is exactly how a dashboard ends up
plotting bytes against operations and nobody notices.

The fix is not to rename the key per metric — that makes every consumer special-case it —
but to say what the count means, in the row: `params.unit_of_work` is `"ops"`, `"bytes"`,
`"loads"` or `"ios"`. The row stays self-describing, which is the same reason `unit` is
stored redundantly next to `value`.

### 3. A value is a rate

`value = ops / seconds` covers throughput. It does not cover `GB/s` (bytes ÷ seconds ÷
1e9), `MB/s` (÷ 1e6), `ns` per load (the *reciprocal* of a rate), or a p99 latency, which
is not a function of the unit count at all.

That last one is why this is an enum (`ValueRule`) and not a scale factor. Four of the five
rules are arithmetic on `(units, elapsed_ns)`; the fifth says "this value does not come
from here", and the type system now makes that visible instead of leaving a `1.0` scale
factor that silently produces nonsense.

### A batch is a whole number of passes, never a short one

The trial loop runs whole batches until the trial's time is up, and reads the clock once
per batch. For the CPU workloads a batch is a million operations and the clock cost is
nothing. For a 4 KiB buffer, one pass takes about **40 ns** — roughly three
`steady_clock::now()` calls. Timing one pass at a time would have been measuring the clock.

So a batch repeats the pass until it has moved at least 4 MiB: 1024 passes at 4 KiB, and
exactly one pass at 256 MiB. The per-batch clock cost is under 0.05 % everywhere in the
sweep. `batch_units()` reports the real number, and a test asserts `run_batch()` returns
it — the same rule as M2.4's `kBatchOps`, now a runtime value because a memory batch is
only sized once the buffer exists.

### The compiler would have deleted 1023 of those 1024 passes

Repeating a pass raises a problem the CPU kernels never had. Summing the same unmodified
buffer 1024 times is 1024 identical pure computations, and the compiler is entitled to run
one and multiply. Copying the same source to the same destination 1024 times is 1023
redundant stores, and `memcpy` is a function GCC understands well enough to know that.

Either would have produced a batch that reported 4 MiB moved and moved 4 KiB — a
bandwidth number 1024× too high, with nothing in the output looking wrong.

`DoNotOptimize` on the accumulator is not enough here: it stops the *result* from being
discarded, not the *work* from being shared between passes. The fix is a `ClobberMemory()`
at the end of each pass — an `asm volatile` with a memory clobber, which tells the compiler
that memory may have changed and it must re-read it. It emits no instructions. The write
kernel needs no barrier because it stores `fill_ + p`, a different value each pass, which
the compiler cannot merge.

## What the kernels are, exactly

**Read**: eight independent `uint64_t` accumulators over the buffer. Eight, not one,
because a single accumulator makes the loop a dependency chain of adds and measures add
latency instead of load bandwidth — the same lesson as `cpu_fp`'s eight FMA lanes in M2.4.
GCC's SLP vectorizer turns the eight into two 256-bit accumulators; the hot loop is two
instructions:

```
7a4:  vpaddq (%rax),%ymm0,%ymm0
7a8:  vpaddq 0x20(%rax),%ymm1,%ymm1
```

64 bytes folded per iteration, `vpaddq` taking its operand straight from memory. That is
PLAN.md's `objdump` verification, and it passes; the full disassembly is in
`docs/results/m3.1/disasm_mem_bw.log`.

**Write**: a store loop filling the buffer with a value that comes from a runtime RNG. The
runtime value is deliberate. `std::fill` with a compile-time constant becomes `memset`, and
`memset` is a legitimate way to measure write bandwidth — but it is a different primitive
with its own hand-written kernel, and *which one ran* should not depend on whether the
optimizer happened to notice a byte-uniform constant. PLAN.md flags this as an acceptable
ambiguity; this engine resolves it instead.

**Copy**: `std::memcpy` from a source to a destination, each `working_set_bytes`, counted
**once**. A 21 GB/s copy moves 21 GB of payload per second even though the memory
controller saw 42 GB of traffic. Some tools report the doubled number; CLAUDE.md pins this
one, and the copy kernel allocates `2 × working_set_bytes` so `cold_region()` covers both
halves.

## Verify 1 — the working-set sweep

`--working-set 8K…256M -t 1`, 10 trials of 50 ms each, pinned, `--cold clflush`.
Medians, GB/s (1 GB = 1e9 bytes). Full table and CoVs: `docs/results/m3.1/analysis.md` (and `ctest_presets.log` for the test runs).

| working set | read | write | copy | write/read |
|---|---:|---:|---:|---:|
| 8 KiB | 213.8 | 237.7 | 296.8 | 1.11 |
| 16 KiB | 237.8 | 273.0 | 302.6 | 1.15 |
| 32 KiB | **253.7** | **290.9** | 67.6 | 1.15 |
| 64 KiB | 190.6 | 80.6 | 68.9 | 0.42 |
| 128 KiB | 201.7 | 80.0 | 65.3 | 0.40 |
| 256 KiB | 201.8 | 79.8 | 69.0 | 0.40 |
| 512 KiB | 201.0 | 80.6 | 65.0 | 0.40 |
| 1 MiB | 173.4 | 75.4 | 36.3 | 0.43 |
| 2 MiB | 181.8 | 78.6 | 37.7 | 0.43 |
| 4 MiB | 72.7 | 50.4 | 35.9 | 0.69 |
| 8 MiB | 72.2 | 50.3 | 36.5 | 0.70 |
| 16 MiB | 45.0 | 39.6 | 31.7 | 0.88 |
| 32 MiB | 23.9 | 20.4 | 25.5 | 0.85 |
| 64 MiB | 26.0 | 15.1 | 23.0 | 0.58 |
| 256 MiB | 22.9 | 14.1 | 21.4 | 0.61 |

**The plateaus land where the cache sizes say they should.** `bench sysinfo` reports
48 KiB L1d, 2 MiB L2 per core, 24 MiB L3. Reads:

| region | working sets | read GB/s | step |
|---|---|---:|---|
| L1d (48 KiB) | 8–32 KiB | 214–254 | — |
| L2 (2 MiB) | 64 KiB – 2 MiB | 173–202 | 1.3× |
| L3 (24 MiB) | 4–8 MiB | 72 | **2.5×** |
| L3, contended | 16 MiB | 45 | 1.6× |
| DRAM | 32–256 MiB | 23–26 | **1.9×** |

Three things in that table are worth more than the numbers.

**The L1→L2 step is the smallest one.** 1.3×, against 2.5× for L2→L3 and 1.9× for
L3→DRAM. That is not what the folklore picture of a cache hierarchy suggests, and it is
real: Meteor Lake's L2 is wide and close, and a *streaming* read — sequential, fully
prefetchable, no dependencies — is close to the best case for it. A pointer chase over the
same working sets will show a completely different shape, because it takes away everything
the prefetcher is good at. That comparison is M3.2, and it is the reason both metrics
exist.

**16 MiB is not L3 speed even though 16 < 24.** Reads there run at 45 GB/s, halfway between
L3's 72 and DRAM's 23, with the sweep's worst CoV (16.3 %). L3 is shared with everything
else on the machine — including, under WSL2, whatever the host is doing — so a working set
at two thirds of it does not get it all. The honest label for that row is "partly L3", and
the elevated variance is the evidence rather than an embarrassment.

**The copy curve is the read/write curve shifted one step left.** Copy falls off its
plateau at 32 KiB, where read and write are still at their fastest. That is not an anomaly:
copy allocates *two* buffers, so at a 32 KiB working set it touches 64 KiB and has already
left the 48 KiB L1d. The same shift appears at every level. It is a nice self-consistency
check — the curve moved by exactly the factor the allocation changed by.

## Verify 2 — the thread sweep at 256 MiB, and the knee

| threads | GB/s | per thread | vs 1 thread | CoV % | late trials % |
|---:|---:|---:|---:|---:|---:|
| 1 | 23.1 | 23.10 | 1.00× | 1.9 | 0 |
| 2 | 38.0 | 18.99 | 1.64× | 2.8 | 0 |
| 3 | 42.4 | 14.13 | 1.84× | 3.2 | 0 |
| 4 | 48.5 | 12.14 | 2.10× | 9.3 | 0 |
| 6 | 68.4 | 11.40 | 2.96× | 3.2 | 0 |
| 8 | 70.8 | 8.86 | 3.07× | 2.7 | 0 |
| 11 | 79.8 | 7.25 | 3.45× | 2.6 | 0 |
| 16 | **84.2** | 5.26 | 3.65× | 2.3 | 0 |
| 22 | 64.0 | 2.91 | 2.77× | 14.9 | **100** |

**The knee is at 11–16 threads, around 80–84 GB/s.** Scaling is already badly sub-linear at
2 threads (1.64× rather than 2×) and the last useful step is 11→16 threads for +5 %.

The single-thread number deserves a note: **23 GB/s is not one twenty-second of the memory
system, it is one core's concurrency limit.** A core can only have so many cache misses
outstanding at once (the line-fill buffers), so single-thread read bandwidth is
(outstanding misses × 64 bytes) ÷ memory latency, and no amount of DRAM bandwidth helps.
This is why more threads buy more bandwidth even though the DIMMs have not changed, and why
"single-thread memory bandwidth" is a statement about the core, not the memory.

**22 threads is a measurement artifact and is labelled as one.** Throughput *falls* to
64 GB/s and every single trial had a worker arrive more than 1 ms late off the start
barrier. With 22 workers on 22 vCPUs there is no vCPU left for the coordinating thread, or
for the host. M2.5 measured the same collapse for `cpu_fp` at 22 threads (91.8 % late
trials). The `late_trials` column exists precisely so this row can be published rather than
quietly dropped: the number is real, it just is not a fact about memory bandwidth.

## Verify 3 — write vs read, and what `--nt` is worth

PLAN.md predicts: write ≈ ½ read in the DRAM regime without `--nt`, because of
write-allocate; with `--nt`, write approaches read. Measured at 256 MiB per thread:

| threads | stores | read | write | copy | write/read |
|---:|---|---:|---:|---:|---:|
| 1 | plain | 21.0 | 13.2 | 21.4 | **0.63** |
| 1 | non-temporal | 23.1 | **43.5** | 19.1 | **1.88** |
| 8 | plain | 67.9 | 41.4 | 39.7 | **0.61** |
| 8 | non-temporal | 66.1 | 59.5 | 41.9 | **0.90** |

**Write-allocate is real and its size is measured.** A store to a line that is not already
in cache cannot just write it: the cache line is 64 bytes, the store is 8, so the line has
to be *fetched first* and then modified. Every byte written to DRAM therefore costs a byte
read as well. That is the argument behind "write ≈ ½ read", and it predicts the sharpest
feature in the whole sweep: at 64 KiB, the moment the buffer stops fitting in the 48 KiB
L1d, write bandwidth falls from **290.9 to 80.6 GB/s, a 3.6× cliff**, while read falls only
1.3×. Nothing changed in the store loop. What changed is that each store now drags a line
in behind it.

**But the ratio is 0.61–0.63, not 0.50, and the reason is on the other side of the
fraction.** The "½" prediction assumes the read number is the memory system's ceiling. It
is not: at 1 thread, read is limited by the core's outstanding-miss concurrency (23 GB/s),
as the thread sweep above shows by getting to 84 GB/s with more cores. So the denominator
is too small and the ratio comes out too high. The prediction's *mechanism* is confirmed by
the L1 cliff; its *arithmetic* is off because the baseline it used was not a bandwidth
limit.

**`--nt` at 1 thread does not "approach" read — it beats it by 1.9×.** Non-temporal stores
go through write-combining buffers straight to memory: no line is fetched, and the store
does not wait for anything. That removes both the write-allocate traffic *and* the
concurrency limit, and a single core turns out to be able to push 43.5 GB/s of writes while
it can only pull 23.1 GB/s of reads. At 8 threads, where reads are no longer
concurrency-starved, the predicted behaviour appears exactly as written: 0.61 → 0.90.

So the PLAN prediction is right at 8 threads and wrong at 1, for a reason that is itself
one of the findings.

## The copy number was lying, and the tunable proved it

The table above has an oddity: at 1 thread, plain copy (21.4 GB/s) beats plain write
(13.2 GB/s). A copy moves the same bytes a write does *and* reads them first. It cannot be
faster than a write on the same store path — unless it is not on the same store path.

It is not. **glibc's `memcpy` switches to non-temporal stores above
`glibc.cpu.x86_non_temporal_threshold`**, which on this system defaults to the L3 size
(`getconf LEVEL3_CACHE_SIZE` = 25165824). At 256 MiB, "copy without `--nt`" was already
using NT stores.

That is a hypothesis about someone else's library, so it was tested rather than asserted.
Forcing the threshold above the working set with `GLIBC_TUNABLES` makes `memcpy` take the
plain-store path, and the prediction is directional and specific: the 256 MiB point should
get *slower*, and the 8 MiB point — below the threshold either way — should not move.

| working set | default threshold (24 MiB) | forced to 1 GiB | change |
|---|---:|---:|---:|
| 8 MiB | 35.49 | 36.48 | +2.8 % |
| 256 MiB | 21.31 | 18.71 | **−12.2 %** |

Both halves hold. The 256 MiB copy loses 12 % when denied NT stores; the 8 MiB copy is
unchanged within noise. And the forced-plain number (18.71) lands next to this engine's own
`--nt` copy (19.1), which is the second confirmation: once both are on the same store path
they agree, and glibc's remaining 12 % edge over our four-word NT loop is its prefetching
and unrolling, not a different kind of store.

The consequence for the results: **`mem_copy_bw` without `--nt` is not a plain-store
baseline at DRAM-sized working sets**, and it must not be compared with `mem_write_bw` on
the write-allocate argument. This is recorded in `docs/methodology.md` and is the sort of
thing that would otherwise sit in a results table for years being misread.

## Cold mode across the sweep

`--cold clflush` behaves as M2.3 designed it and as the working sets require. Below L3 the
buffer is flushed before every trial and `params.cold` reads `"clflush"`; above L3 the
region was never cache-resident, so flushing it would cost ~100 ms per 512 MiB and cool
nothing — `params.cold` reads `"n/a"` and the engine says so rather than claiming a cold
start it did not perform.

Worth being clear about what cold mode can and cannot do for a *bandwidth* metric. A 50 ms
trial over a 1 MiB buffer makes thousands of passes; only the first is cold. So cold mode
changes a bandwidth number by well under a percent, which is not a failure — it is the
difference between a latency metric, where the cache state is the whole measurement, and a
throughput metric, where it is a transient. M3.2's pointer chase is where cold mode earns
its keep.

## Deviations from PLAN.md, all deliberate

- **`--working-set 4K` was dropped from the sweep in favour of 8K.** A 4 KiB copy needs two
  4 KiB buffers and the whole thing was already comfortably inside L1; 8 KiB starts the
  curve at the same place with one fewer degenerate point.
- **The default working set is 64 MiB**, not specified in PLAN.md. It is past this
  machine's L3, so a bare `bench run -w mem_bw` reports DRAM bandwidth — the number most
  people mean by "memory bandwidth" — rather than a cache's.
- **`docs/methodology.md` now exists**, started early because M3.1's Verify block asks for
  the write-allocate explanation to live there. It gains a section per milestone rather
  than being written in one go at M8.1.

## What is not established here

- **No CoV claim.** These runs are 10 trials of 50 ms each, chosen to make a curve visible
  in about a minute of measurement. Target #2 for memory metrics is M3.3's job and is not
  attempted here.
- **`mem_read_bw` at 22 threads is not a bandwidth number**, for the reason given above.
- **These are virtual-machine numbers.** The 22 "CPUs" are Hyper-V vCPUs, the hybrid P/E
  layout is hidden, and pinning does not determine which physical core runs a thread
  (M2.1). The shape of the curve is trustworthy; the absolute peak is a lower bound on what
  the hardware can do.
