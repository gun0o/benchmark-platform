# M5.3 — Aggregation, comparison, and a cache that cannot take the API down

*Milestone notes, written for someone learning where a read API's traps are. Measured on
2026-09-21 over the 112,510 rows M5.2 seeded, against Postgres 16 and Redis 7 in compose
with the API native in WSL. Raw logs: `docs/results/m5.3/`. Earlier notes: `M5.1.md`,
`M5.2.md`.*

## The problem this milestone solves

`GET /v1/measurements` can return every row the dashboard needs, and that is the problem.
A thread-scaling chart over five thread counts and 100 trials each is 500 rows the browser
would have to group, sort and reduce itself — and a comparison of three machines is 1,500,
which the browser would then have to align on a shared axis. Statistics computed in five
places drift apart; statistics computed in the browser also mean shipping 400 KB to draw
five points.

The other half is repetition. The dashboard asks the same handful of questions on every
page load. Those answers change only when data for that machine changes.

## What was built

1. **`GET /v1/aggregates`** — `n, mean, median, stddev, cov, min, p5, p95, max` per group,
   in SQL (`percentile_cont`, `stddev_samp`), grouped by `thread_count` or
   `working_set_bytes`.
2. **`GET /v1/compare`** — one series per machine over the *union* of their group values,
   plus each machine's ratio to the first.
3. **`GET /v1/trials`** — `[trial, value, recorded_at]` triples for one configuration, up
   to 10,000, with optional `downsample=lttb:N`.
4. **`internal/lttb`** — Largest-Triangle-Three-Buckets, with tests.
5. **`internal/cache`** — Redis cache-aside with a canonical key, per-machine invalidation,
   a 60-second TTL, and a circuit breaker.
6. **`/readyz`** now reports `"redis": "ok" | "degraded" | "disabled"`, and stays 200 in
   all three cases.

## Each decision, and why

### The statistics are defined once, and checked against numpy

`stddev` is `stddev_samp` (n−1). `median`, `p5` and `p95` are `percentile_cont`, which is
linear interpolation between the two neighbouring order statistics — the same thing numpy
calls `method="linear"`, and the same definition `engine/include/bench/stats.hpp` uses.
`cov` is `stddev / mean`.

Saying that is cheap. The verification is not: `TestAggregatesMatchNumpy` seeds two
machines, reads the rows back **through the list query the dashboard itself would use**,
hands them to numpy, and compares every field of every group to the SQL answer with a
relative tolerance of 1e-6. Four metrics, 25 groups, all fields, all inside tolerance.

This is the test that would have caught the classic percentile bug. There are at least
nine defensible definitions of a percentile; `percentile_disc` would have passed a "median
looks about right" eyeball and disagreed with numpy on every even-sized group.

### Aggregates require `machine_id` and `metric`

`percentile_cont` sorts each group. Over a filtered configuration that is 100 values; over
an unfiltered 112,510-row table with a `GROUP BY thread_count` it is five sorts of ~22,500
values, on every request, uncached. The endpoint returns **400 `missing_filter`** rather
than accepting a question whose cost grows with the database:

```
{"error":{"code":"missing_filter","message":"machine_id and metric are required;
 an aggregate over every machine and metric is not a question this endpoint answers"}}
```

An API that will happily do something expensive for a client that did not mean to ask is a
load test waiting to happen. Compare is bounded differently: two to eight machines, and
the same required metric.

### Compare aligns the series server-side

Three machines swept at different thread counts produce three series on different axes.
`/v1/compare` returns the union of the group values and, for each machine, an array of the
same length with a value per group — so the chart is `groups` against `series[i].median`
with no reconciliation in the browser.

The first machine in `machines=` is the baseline, and every series carries `ratio`: its
median divided by the baseline's at the same group. That makes `machines=a,b` and
`machines=b,a` genuinely different answers, which is why the cache key keeps the order the
client gave instead of sorting it like every other parameter.

The measured output says what this is for (`docs/results/m5.3/endpoints.log`):

```
synthetic-01   median 3.9e+09 7.78e+09 1.54e+10 3.03e+10 5.88e+10
synthetic-03   ratio  0.795 0.729 0.459 0.354 0.249
```

The 4-vCPU instance is 80 % of the 64-core server's single-thread throughput and 25 % of it
at 16 threads. The ratio column is the sentence "this machine falls behind as threads are
added", and it took one query to say it.

### Trials are triples, not objects

10,000 rows as JSON objects with six keys each is ~1 MB of mostly repeated key names. As
`[trial, value, recorded_at]` triples it is a fifth of that. Measured on a 100-trial
series: 5,468 bytes full, 1,695 gzipped, 1,203 with `downsample=lttb:20`.

The interesting comparison there is the last two. **Gzip and downsampling are not
substitutes**: gzip sends every point compressed, downsampling sends fewer points. For a
chart 800 pixels wide, sending 10,000 points is 12 per pixel, and the client then has to
parse and hold them all. LTTB drops the points that cannot be seen and keeps the ones that
define the shape.

Which is the property the tests pin: a series of 10,000 identical values with **one spike**
at index 4,137, downsampled to 500 points, must still contain the spike. Decimation by
every-20th would drop it 19 times out of 20 — and in a variance study, the spike *is* the
measurement.

### The cache key is canonical, and includes everything

A key is the endpoint name plus every filter that affects the answer, names sorted, values
sorted within a name. `?metric=cpu_int_ops&machine_id=X` and `?machine_id=X&metric=cpu_int_ops`
produce one key; two queries that differ in any filter cannot collide. A key that forgot a
filter would serve one configuration's aggregate as another's — a wrong answer, delivered
quickly, with a 200.

### Invalidation is per machine, and is a set, not a scan

Every cached key is registered in `keys:machine:<id>`; an ingest for that machine reads the
set, deletes those keys and the set. No `KEYS` or `SCAN` pattern matching (`KEYS` is O(n)
over the whole keyspace and blocks Redis).

The measured behaviour, posting one run for synthetic-02:

```
before: agg|…-01|cpu_int_ops   agg|…-01|mem_read_bw   agg|…-02|cpu_int_ops
        trials|…-02|…          cmp|…|machines=-01,-02
after:  agg|…-01|cpu_int_ops   agg|…-01|mem_read_bw
next:   agg -01 → hit    agg -02 → miss    trials -02 → miss    compare → miss
```

The compare key was evicted too, because it is registered against **both** machines it
depends on. A comparison that kept showing the old synthetic-02 numbers after an ingest
would be the subtlest kind of wrong.

### The circuit breaker, which the verification forced

The requirement was "with Redis down, the endpoints still work, slower". They did. The
measurement said *how much* slower:

```
compare: HTTP 200 in 3.447481s
trials:  HTTP 200 in 3.359997s
```

**3.4 seconds** for a query that takes 3 ms from Postgres. go-redis retries three times by
default, and each request touches Redis twice (a GET, then a SET on the miss), so a dead
Redis cost eight dial attempts per request. The API was up, and unusable — a cache making
a service *slower* than having no cache at all is the failure this design was supposed to
avoid, and only measuring it revealed it.

Two changes: `MaxRetries = -1` (no retries — retrying a cache is pointless, the answer is
in Postgres either way), and a circuit breaker. After three consecutive errors the cache is
skipped entirely for 30 seconds; any success closes it. After that:

```
request 1: 0.810s   request 2: 0.806s   request 3: 0.0013s   … request 8: 0.0011s
compare: 0.0033s    trials: 0.0020s
```

Two slow requests while the breaker trips, then 1.3 ms — a **2,600× improvement on the
degraded path**, and a reminder that "it still works" is not a measurement.

Errors are logged at most once a minute with a count of what was suppressed, so a Redis
outage does not also become a disk-space incident. `/readyz` reports `"redis": "degraded"`
and stays **200**: Redis being down is not a reason to take the API out of the load
balancer, because every endpoint still answers correctly.

### A field the machines endpoint could never fill

Writing the invalidation test meant round-tripping a machine block: `GET /v1/machines/{id}`
into a `POST /v1/runs`. It failed with

```
machine.engine_version is required and must be non-empty
machine.engine_git_sha is required and must be non-empty
```

`MachineRow` embedded `Machine`, so the response advertised `engine_version` and
`engine_git_sha` — but the `machines` table does not store them, and should not: the engine
version describes *the run*, not the box, and one machine can post runs from several engine
builds. The response was emitting two permanently empty strings.

`MachineRow` now has its own field list without them, `openapi.yaml` says so, and a test
asserts the response does not carry fields the store cannot populate. A small thing, found
only because something tried to use the output as an input.

## Verification

| verify step | result |
|---|---|
| aggregates match numpy over the same rows, 1e-6 relative | **yes** — 25 groups, 4 metrics, every field |
| cache hit path p50 < 2 ms | **0.48 ms** (p95 0.66 ms); miss 6.68 ms |
| one `SET` per distinct query, `GET`s thereafter | yes — 5 queries, 5 value keys, 2 machine sets |
| ingest for machine X evicts X's keys only | yes, plus the comparison that depends on X |
| `docker compose stop redis` → endpoints work, `/readyz` 200 `"degraded"` | yes |
| trials endpoint, 10K points, compact | yes; `lttb:N` keeps a single spike out of 10,000 points |

```
$ go test ./...                    58 tests, ok
$ go test -tags integration ./...  17 store tests, ok
$ go vet ./... && gofmt -l .       clean
```

## What this milestone does not do

- **No Prometheus metrics or pprof.** The cache counters exist (`cache.Stats`) but nothing
  exposes them yet; that is M5.5.
- **No cache warming.** The first request after an ingest pays the miss, deliberately: a
  warmer would have to guess which of the 112,500 possible questions matters.
- **No k6 numbers.** M5.4.
