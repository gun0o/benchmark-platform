# M2.3 — Cold-cache infrastructure

*Milestone notes, written for someone learning benchmark methodology. Measured on
2026-09-19 on a Core Ultra 9 185H laptop under WSL2, release build, **plugged in**, Windows
power plan "Balanced" with the power mode set to **"Best power efficiency"**. Raw runs and
commands are in `docs/results/m2.3/`. Earlier notes: `M1.2.md`, `M2.1.md`, `M2.2.md`.*

## The problem this milestone solves

Run a benchmark twice in a row and the second run is faster. Not because the machine got
better, but because the first run left everything the second one needs sitting in cache.

A CPU has three or four levels of memory that get slower and bigger as you go out. On this
machine, measured in this milestone: data in L2 is about **3.6 nanoseconds** away, and data
in main memory is about **105 nanoseconds** away. That is a factor of **29**. So "how fast
is this code" has two very different answers depending on a thing the code itself does not
control — whether the data happened to already be in cache.

If a benchmark does not decide which of those two questions it is asking, it answers
whichever one the previous trial set up. Trial 1 measures cold memory, trials 2 through
1000 measure warm cache, and the reported average is a blend of the two in a proportion
nobody chose. Worse, that proportion changes if you reorder the trials, so the number is
not even reproducible.

This milestone adds the machinery to *choose*: before every trial, put the caches into a
known state, and record which state that was.

## What was built

1. **`cache.hpp` / `cache.cpp`** — the cold-cache library:
   - `flush_lines(region)` — tell the CPU to drop specific cache lines, using the
     `CLFLUSHOPT` instruction.
   - `evict_llc(scratch)` — the blunt alternative: read a big private buffer so the cache
     fills up with *that* instead of what you care about.
   - `alloc_buffer(bytes)` — an owned, page-aligned buffer that asks for transparent huge
     pages when it is big enough, first-touches its own pages, and **measures** whether the
     huge pages were actually granted.
   - `ColdPrep` — the per-worker object that decides what a requested cold mode actually
     means on this machine for this region, and performs it once per trial.
2. **`--cold {clflush|evict|none}`**, default `clflush`. Preparation happens on each worker
   thread, for that thread's own data, immediately before the trial's start barrier — so it
   is outside the timed region by construction.
3. **New result fields**: `params.cold` (what happened), `params.cold_requested` (what was
   asked for), `params.cold_bytes`, `params.cold_prep_mean_us`, `params.cold_prep_max_us`,
   `params.huge_pages`, `params.huge_page_bytes`. Documented in the JSON Schema and checked
   by `bench validate`.
4. **`cold_region()` on the `Workload` concept** — every workload now declares which bytes
   it wants cooled. That is the buffer for a memory workload and, for `cpu_int`, its own
   80 bytes of lane state.
5. **20 new tests**: 16 functional (`tests/cache_test.cpp`) and 4 timing-ratio tests
   (`tests/cold_cache_test.cpp`, labelled `perf`).

## Each correctness decision, and why

### Cold preparation happens before the barrier, not inside the trial

This is the single most important rule here, and it is worth being precise about why.

The engine times a trial from the moment the start barrier releases all workers to the
moment the last one finishes (M2.1). If flushing happened inside that window, the flush's
cost would be added to the measured time and reported as if the workload had been slow.

How much would that matter? Measured: `evict` mode costs **5.7 milliseconds** per thread
per trial at 8 threads. A trial is 50 ms. So cold preparation would inflate the trial by
11 % and the reported throughput would drop by the same amount — an enormous error for a
project whose variance target is 3 %.

So the order inside each worker is: prepare the cache, arrive at the barrier, then measure.
The preparation is still *timed*, separately, and reported in
`params.cold_prep_mean_us` — because a cost you cannot see is a cost you cannot reason
about, even when it is not in the number.

There is a second, subtler rule attached: **cold preparation must be the last thing a
worker touches before the barrier.** If a worker flushed its buffer and then did something
else — touched a counter, walked a list — those accesses could pull the flushed lines back
in. Hardware prefetchers make this worse: they watch access patterns and speculatively fetch
neighbouring lines, so touching *one* address near the flushed region can undo the flush for
several lines around it. The only thing between the flush and the barrier is the barrier
itself, which touches only its own two cache lines.

### `CLFLUSHOPT` needs a fence after it, and that fence is the entire cost

`CLFLUSHOPT` is the "optimised" version of `CLFLUSH`. The optimisation is that flushes to
different cache lines are allowed to proceed in parallel and out of order, where the old
`CLFLUSH` was strictly ordered. That makes it much faster for a big region — and it means
that when the instruction retires, the line may not actually be gone yet.

So the flush loop is followed by `SFENCE` (which is what Intel's manual specifies for
ordering `CLFLUSHOPT` against later stores) and then `MFENCE` (so that nothing the thread
does afterwards can be reordered ahead of the flush completing).

Measured, on an 80-byte region (`docs/results/m2.3/flush_cost.log`):

| | cost |
|---|---|
| two clock reads, nothing between them | 15 ns |
| two `CLFLUSHOPT`s, no fence | 15 ns |
| + `SFENCE` | 17 ns |
| + `MFENCE` | 128–422 ns |
| `MFENCE` on its own | 27 ns |

The flush instructions are free — you cannot even distinguish them from the cost of reading
the clock. **All** of the cost is the `MFENCE`, and it is far more than a bare `MFENCE`
because it is waiting for a dirty cache line to be written back to DRAM. That is the honest
shape of the operation: flushing is not "an instruction", it is "wait for memory".

### Flushing a region larger than the cache is recorded as `n/a`, not performed

If a workload's buffer is 512 MiB and the last-level cache is 24 MiB, the buffer was never
cache-resident. Flushing it line by line cools nothing that was warm, and it is not free.

Measured per-line cost for lines that are dirty (which is the case that matters, since a
workload writes to its buffer): **~5.5 ns per 64-byte line**. So 1 MiB costs 90 µs and
512 MiB would cost roughly 46 ms per trial — comparable to the trial itself.

`ColdPrep` therefore refuses: when the region is larger than L3, `params.cold` is recorded
as `"n/a"` while `params.cold_requested` still says `"clflush"`. Two different facts, two
different fields. The alternative — silently doing nothing and still writing
`"cold": "clflush"` — would put a false claim in every row of the output file, and the
whole point of this project is that its claims are measured.

The same applies to a region of zero bytes, and the decision table is pinned by a test
(`Cache.ColdPrepDecidesWhatIsActuallyPossible`).

### Runtime CPU detection, not a compile-time `#ifdef`

`CLFLUSHOPT` is not in every x86 CPU. The obvious approach is `#ifdef __CLFLUSHOPT__`,
which the compiler defines when `-march` enables the instruction.

The problem: this project has two builds. The `release` preset uses `-march=native`, which
makes a binary specific to the machine that compiled it. The `ci` preset uses
`-march=x86-64-v3`, which is portable — and does *not* include `CLFLUSHOPT`. Under an
`#ifdef`, the portable build would silently fall back to the slow `CLFLUSH` even on a CPU
that supports the fast one.

Instead, the flush loop is compiled with GCC's `[[gnu::target("clflushopt")]]` attribute,
which emits the instruction regardless of `-march`, and the decision to call it is made at
runtime by `__builtin_cpu_supports("clflushopt")` — which reads the CPU's own CPUID data.
Verified (`ci_portable_clflushopt.log`): the `ci` binary contains 14 `clflushopt` sites and
reaches them, achieving the same 29× ratio as the native build.

The general principle: **`-march` describes what the compiler may emit; CPUID describes what
the machine can run.** They are not the same question, and a fallback path should be chosen
by the second one.

### Huge pages are measured, never assumed

A "page" is the unit the operating system maps memory in — normally 4 KiB. The CPU caches
these mappings in a small table (the TLB). A 48 MiB buffer is 12,288 pages, far more
mappings than the TLB holds, so a benchmark walking it randomly pays a TLB miss on most
accesses — and that is measuring the TLB, not memory. Transparent huge pages let the kernel
map 2 MiB at a time, cutting 12,288 mappings to 24.

But the kernel may refuse. `/sys/kernel/mm/transparent_hugepage/enabled` can be `never`, or
it can be `madvise` (meaning you only get them if you explicitly ask), and even then there
may be no contiguous free memory. So `alloc_buffer` asks, and then **reads back** how much
it actually got, from the `AnonHugePages` field of the buffer's own mapping in
`/proc/self/smaps`. That number goes into `params.huge_pages` and `params.huge_page_bytes`.

Two details worth recording:

- *Per-mapping, not process-wide.* PLAN.md specified reading `/proc/self/smaps_rollup`,
  which totals the whole process, and taking a before/after difference. That works only if
  nothing else allocates in between — and in this engine several worker threads allocate at
  once, so a rollup difference could credit one thread's huge pages to another. Reading the
  specific mapping from `/proc/self/smaps` has no such race, so that is what is done.
- *The parser nearly got it wrong.* `/proc/self/smaps` alternates between mapping headers
  (`7f2a...-7f2a... rw-p 00000000 08:40 27127 /path`) and field lines (`AnonHugePages: 0 kB`).
  The obvious way to tell them apart is that field lines contain a colon — except the
  header's device field (`08:40`) contains one too. The first version of this code therefore
  classified *every* header as a field, never matched a mapping, and reported 0 huge pages
  for a buffer that had them all. It reported a plausible-looking false negative, which is
  the most dangerous kind of bug in measurement code. It is now told apart by parsing hex
  digits up to a `-`.

The counterfactual was measured too (`thp_alignment.log`), on a 48 MiB mapping:

| mapping | AnonHugePages granted |
|---|---|
| 2 MiB-aligned + `MADV_HUGEPAGE` | 48 MiB of 48 |
| 2 MiB-aligned, no madvise | 0 MiB |
| unaligned + `MADV_HUGEPAGE` | 46 MiB of 48 |
| unaligned, no madvise | 0 MiB |

This corrected a comment in the header that had claimed alignment was the essential part.
It is not: under the `madvise` policy the `madvise` call is what does the work, and the
alignment buys back the partial huge page at each end. Worth doing, much smaller effect
than it sounds.

### Buffers are first-touched by the thread that will use them

Asking the operating system for memory does not give you memory. It gives you a promise. The
pages are only really allocated when you first write to them, and that first write is a
**page fault** — roughly 1–2 µs of kernel work.

A 64 MiB buffer is 16,384 pages. If those faults happened during the first timed trial, that
trial would carry ~25 ms of kernel time that has nothing to do with the workload. So
`alloc_buffer` writes one byte to every page before returning, on the calling thread —
which, in the runner, is the worker that will own the buffer. (On multi-socket machines the
"first touch" also decides *which* socket's memory the pages come from, which matters even
more; this laptop has one socket, so here it is purely about the faults.)

### The eviction buffer streams one line at a time, ascending

`evict_llc` reads one 8-byte value per 64-byte cache line. Reading the whole line would be
pointless — the cache works in 64-byte units, so touching one byte brings in all of it.

The loop accumulates into a value that is passed through `DoNotOptimize`, because a loop
whose result is unused is a loop the compiler deletes, and a cold-cache function that got
optimised away would be invisible in exactly the same way the `smaps` bug was.

It ascends, unlike `flush_lines`, which descends. Both directions are deliberate and they
are opposite for the same reason: hardware prefetchers follow ascending sequential patterns.
When evicting, that help is wanted — the goal is to fill the cache as fast as possible. When
flushing, it is not — a prefetcher running alongside the flush would refill lines behind it.

### Every worker gets its own everything

Each worker has its own `ColdPrep`, holding its own 48 MiB eviction buffer, flushing its own
region. Nothing is shared. If workers shared an eviction buffer, thread 2's pass would find
the buffer already in cache from thread 1's pass and would evict much less — the cold state
would depend on thread ordering. Pinned by `Cache.ColdPrepIsPerThread`.

### Publishing the preparation cost without a data race

Cold preparation runs *before* the start barrier; the main thread reads each worker's slot
*after* the end barrier. So a worker timing its preparation for trial N+1 is running at the
same moment the main thread is reading the results of trial N — writing the cost straight
into the slot would be a genuine data race.

The fix is one line: the worker keeps the duration in a local variable and copies it into
its slot *after* the start barrier releases, inside the window where the main thread is
known not to be reading. This is the same invariant M2.1 established ("every write to a slot
happens between the two barriers"), and the new field had to be made to obey it rather than
being an exception to it. TSan confirms: clean, 71/71.

## What the Verify steps showed

### 1. A flush makes the next access miss to DRAM — required ≥ 5×, measured 28.7×

The test builds a **random cyclic pointer chase**: a 256 KiB buffer where each 64-byte line
holds the address of the next line to visit, arranged by Sattolo's algorithm into a single
cycle through all 4,096 lines. Each load's address is the previous load's *result*, so the
CPU cannot overlap them, and the order is random, so it cannot prefetch them. The time per
step is then a direct read-out of which level of memory the data is in.

```
clflush 256 KiB  n=41  warm 3.65  cold p5 100.03 / med 104.83 / p95 121.93 ns/load
                       ratio 28.74x  (per-rep 15.62x..34.96x)   require >= 5.0x
```

3.65 ns/load is L2; 105 ns/load is DRAM.

Sattolo's algorithm rather than an ordinary shuffle, because an ordinary shuffle produces a
permutation with *several* cycles, and the chase would fall into whichever short cycle
contains the starting point and stay in L1 — measuring nothing. Sattolo guarantees exactly
one cycle of full length.

### 2. Eviction works too — required ≥ 3×, measured 15.4×

```
evict 48 MiB     n=41  warm 3.73  cold p5 38.33 / med 57.51 / p95 117.97 ns/load
                       ratio 15.41x  (per-rep 6.44x..53.54x)   require >= 3.0x
```

Across ten consecutive runs, clflush ratios ranged 13.5×–31.1× (median 28.7×) and evict
ratios 9.4×–25.8× (median 16.4×). Both cleared their bars every time. The flush cools more
thoroughly — its post-cool latency was higher in 8 of the 10 runs — and it costs 0.9 µs
against eviction's 2.4 ms, which is why it is the default and eviction is the fallback for
machines where `CLFLUSH` is unavailable or trapped.

**This verification initially failed, and the failure was mine, not the code's.** The first
version used 9 repetitions. Across runs of the identical binary on the identical machine it
reported eviction ratios of 2.95×, 3.80×, 4.60× and 23.63× — and failed its own 3× bar once.
The eviction was working the whole time; 9 samples of a wide distribution simply do not have
a stable median. At 41 repetitions the worst of ten runs is 9.4×.

The lesson is uncomfortable and worth keeping: a flaky test looks exactly like an
intermittent bug, and the temptation is to "fix" it by lowering the bar until it stops
failing. That would have hidden the real finding, which is that the two mechanisms have very
different *reliability*, not just different means.

### 3. Cold costs the first pass and nothing afterwards

PLAN.md specifies this on `mem_latency`, which does not exist until M3.2, so it was run on
the pointer chase that workload will be built from. ns per dependent load; p1..p5 are the
five passes after the flush:

| working set | warm | p1 | p2 | p3 | p4 | p5 |
|---|---|---|---|---|---|---|
| 64 KiB | 3.63 | **130.56** | 3.24 | 3.63 | 3.63 | 3.63 |
| 256 KiB | 3.82 | **106.03** | 3.84 | 3.82 | 3.82 | 3.82 |
| 1024 KiB | 6.47 | **143.92** | 7.53 | 6.84 | 6.78 | 6.82 |

Both halves of the claim hold: the first pass costs 22–36×, and by pass 2–3 the value is
back to the warm one exactly. Cold mode sets the starting state and then stops mattering. A
cold mode that still cost something at pass 5 would be *changing* the measurement rather
than controlling its starting point.

This one also had to be measured before it could be written down. The first version asserted
that the *second* pass was already back to warm, and it failed — at 1 MiB the second pass is
still 15 % slow, because the first pass could not keep every line it fetched. Steady state
arrives at pass 3. The assertion was wrong; the code was right.

### 4. The control

`--cold none`: warm 5.35 ns/load, "cold" 5.35 ns/load, ratio **1.00×**.

Without this row, the two tests above would also pass for a pointer chase that was simply
slow every time, for any reason at all. A test that only ever checks "the number went up"
cannot tell a working flush from a broken measurement.

### 5. Cold mode does not change the `cpu_int` number

50 trials × 50 ms, pinned:

| cold | threads | median Gops/s | CoV |
|---|---|---|---|
| clflush | 1 | 3.801 | 20.13 % |
| evict | 1 | 3.731 | 16.67 % |
| none | 1 | 3.807 | 16.62 % |
| clflush | 8 | 30.461 | 6.33 % |
| evict | 8 | 30.704 | 5.55 % |
| none | 8 | 30.112 | 8.97 % |

Under 2 % apart, inside a CoV of 6–20 %. This is the *correct* result, not a
disappointment: `cpu_int`'s whole state is 80 bytes, so cooling it costs a few cache misses
at the start of a 50 ms trial and then nothing. Cold mode will matter for `mem_bw` and
`mem_latency`, which is what it was built for.

The run's real value is as a check that preparation stays outside the timed region. `evict`
adds 5.7 ms of work per 50 ms trial; if any of it leaked into the measurement, the `evict`
rows would be ~10 % slower than the others. They are not.

### 6. Preparation cost

| cold | threads | bytes/thread | median µs | overhead on a 50 ms trial |
|---|---|---|---|---|
| clflush | 1 | 80 | 0.85 | 0.00 % |
| clflush | 8 | 80 | 0.74 | 0.00 % |
| evict | 1 | 50 331 648 | 2357.33 | 4.71 % |
| evict | 8 | 50 331 648 | 5741.82 | 11.48 % |
| none | 1 | 0 | 0.15 | 0.00 % |
| none | 8 | 0 | 0.12 | 0.00 % |

`none` at 0.15 µs is the floor — two clock reads around an empty operation. Eviction at 8
threads streams 384 MiB through one memory system per trial, which is why it costs 2.4× what
it does at one thread.

### 7. Test suites and schema

71 functional tests pass in release, debug, asan, tsan and the portable ci preset; all 7
perf-labelled tests pass in release. 20 of these are new.

All three cold modes validate against `schema/benchmark-result.schema.json` and through
`bench validate`. A result claiming `params.cold: "maybe"` is rejected by both. `params` is
deliberately open-ended in the schema, but the keys it does pin down are now also checked by
the engine's own validator — a wrong cold mode is a false claim about methodology, which is
worth catching in the tool that writes the file rather than only in the one that reads it.

### A note on the power state

These runs were taken **plugged in**, with the Windows power plan "Balanced" and the power
mode set to **"Best power efficiency"** — the least favourable of the three Windows power
modes for benchmarking, because it holds clocks down and biases the scheduler toward E-cores.
That was the mode already configured on the machine and it was deliberately left alone, so
the absolute numbers here are a floor rather than a best case.

It shows. The pointer chase's *warm* baseline moved between 3.65 and 12.34 ns/load between
runs, and the cold DRAM latency between 49 and 217 ns. On a hybrid CPU those are the
signatures of the measuring thread landing on a P-core, an E-core or a low-power E-core from
one run to the next, which a power-efficiency bias makes more likely.

Every ratio reported above is measured *within* a single run, where the power state and core
assignment are constant, so the ratios are unaffected by this. The absolute latencies are
not directly comparable to M2.1's and M2.2's, which record "plugged in" but not which power
mode was active.

One thing that did **not** work: pinning the measuring thread to vCPU 0 to stop it migrating.
It made the spread worse (the warm baseline went from 3.65 to 12.34 ns/load in one run of
three, and the control test drifted to 1.30×), because vCPU 0 also carries interrupt and
kernel work, and because — as M2.1 already established — guest-level pinning does not
determine which physical core Hyper-V runs you on. The fix for the spread is repetitions,
not affinity.

## Five interview questions

**1. Why would you flush the cache before a benchmark trial, and where exactly do you put
the flush?**

Because otherwise the trial inherits whatever the previous trial left in cache, so trial 1
measures cold memory and trial 500 measures warm cache and the average is a blend nobody
chose — and it changes if you reorder the trials. Flushing makes every trial start from the
same state. It goes *outside* the timed region, before the synchronisation barrier, because
flushing is expensive: eviction mode costs 5.7 ms here against a 50 ms trial, so including it
would inflate every result by 11 %. It also has to be the *last* thing the thread does before
the barrier — anything touched afterwards can pull the flushed lines back in, and a hardware
prefetcher following that access can drag in neighbouring lines too.

**2. What is the difference between `CLFLUSH` and `CLFLUSHOPT`, and what do you have to add
when you use the latter?**

`CLFLUSHOPT` lets flushes of different cache lines proceed in parallel and out of order,
where `CLFLUSH` is strictly ordered — a large region is far faster. The cost is that when
the instruction retires the line may not be gone yet, so you need an `SFENCE` after the loop
to order it, and in practice an `MFENCE` so nothing afterwards is reordered ahead of the
flush completing. On this machine the flush instructions themselves are unmeasurably cheap
and essentially the entire cost is that fence, because it is waiting for a dirty line to be
written back to DRAM. Flushing is not "an instruction", it is "wait for memory".

**3. Your benchmark has a 512 MiB working set and the CPU has a 24 MiB last-level cache.
Should you flush it before each trial?**

No. It was never cache-resident, so flushing cools nothing that was warm — and it is not
free: about 5.5 ns per dirty 64-byte line, which for 512 MiB is roughly 46 ms per trial. The
important part is what you do instead of flushing. Don't silently skip it and still label the
output "cold", because then every row of the file carries a false claim about methodology.
Record what actually happened — this engine writes `cold: "n/a"` next to
`cold_requested: "clflush"` — so the two facts stay separate and a reader can tell.

**4. How would you test that your cache-flushing code actually works?**

Time something whose speed depends entirely on where the data is. A random cyclic pointer
chase is the standard tool: each load's address is the previous load's result, so the CPU
can neither overlap the loads nor prefetch them, and the nanoseconds per step tell you which
level of memory you are in. Measure warm, flush, measure again: here that is 3.65 ns against
105 ns, a factor of 29. Three things make it a real test rather than a demo. Use Sattolo's
algorithm, not a plain shuffle, or the chase falls into a short sub-cycle and stays in L1.
Include a control with no flushing at all — without it, a chase that is simply slow every
time passes just as well. And take enough repetitions: at 9 repetitions this test's eviction
ratio swung between 2.95× and 23.63× on the same binary and failed its own bar once, which
looks exactly like an intermittent bug and is really just a sample size.

**5. You call `mmap` for a 48 MiB buffer and `madvise(MADV_HUGEPAGE)`. What can you assume
about what you got?**

Nothing — you have to read it back. `mmap` returns a promise, not memory: the pages are
allocated on first write, and each of those first writes is a page fault of a microsecond or
two, so you touch every page before the timed region rather than paying 16,000 faults inside
it. And `madvise` is advice: transparent huge pages may be disabled entirely, or set to
`madvise`-only, or there may be no contiguous memory free. So read `AnonHugePages` back
from `/proc/self/smaps` and record what you actually got. Read it for the specific mapping
rather than the process-wide rollup, because with several threads allocating at once a
rollup difference can credit one thread's huge pages to another.
