# M1.3 — API: ingest and list

*Milestone notes, written for someone learning how a measurement pipeline is put together.
Everything here was run on 2026-09-21 on the same Core Ultra 9 185H laptop under WSL2 as
the engine milestones, with Postgres 16 and Redis 7 from `deploy/docker-compose.yml` and
the API running natively in WSL. Raw logs and the exact commands are in
`docs/results/m1.3/`. Earlier notes: `M1.2.md` … `M4.1.md`.*

## The problem this milestone solves

The engine can produce a run envelope with a thousand trustworthy numbers in it. Until
this milestone, that document's only home was a file. A file is fine for one machine and
one afternoon; it cannot answer "is this machine faster than that one", "has this metric
drifted since last week", or "show me the trial distribution" without someone writing a
one-off script each time.

The API is the part that makes the measurements *queryable* — and the part where a
measurement platform usually starts lying. Three failure modes matter more than
throughput:

1. **Silent schema drift.** The engine adds a field, the API ignores it, and six months of
   rows quietly lack it. Nothing errors. The dashboard shows a gap and no one knows when
   it started.
2. **Duplicate ingest.** A POST times out, the client retries, and the same 1000 trials are
   stored twice. Every mean, every CoV, every count is now wrong in a way that looks
   plausible.
3. **Slow-by-construction ingest.** Row-by-row `INSERT` of 100K measurements takes a minute,
   so ingest gets used less, so fewer runs are recorded.

M1.3 is the smallest thing that addresses all three: one ingest endpoint, one list
endpoint, and the tests that hold them to the schema.

## What was built

1. **`api/` Go module**, `net/http` with Go 1.22 method-pattern routing, `log/slog` JSON
   logs, configuration from the environment ([config.go](../../api/internal/config/config.go)).
2. **Migration `0001_init`** — `machines`, `runs`, `measurements`, plus the composite index
   `(machine_id, metric, workload, thread_count, working_set_bytes)` every read endpoint
   filters on. Applied by a 180-line runner in
   [api/migrations/migrations.go](../../api/migrations/migrations.go) that keeps
   golang-migrate's file convention.
3. **`POST /v1/runs`** — validates, upserts the machine, inserts the run, bulk-loads the
   measurements with `CopyFrom`, all in one transaction. Idempotent on `run_id`.
4. **`GET /v1/measurements`** — the five schema filters plus keyset pagination.
5. **`GET /healthz` / `GET /readyz`** — liveness that never touches Postgres, readiness
   that pings it.
6. **[openapi.yaml](../../api/openapi.yaml)** describing both endpoints; the dashboard's TS
   types are generated from it in M1.5.
7. **20 tests**: handler tests against a fake store, model tests against the schema file,
   and five integration tests against compose Postgres behind `-tags integration`.

## Each decision, and why

### Validation: strict decoding, not the JSON Schema at request time

`schema/benchmark-result.schema.json` is normative. The plan allowed either embedding it
and running a JSON Schema library per request, or strict struct decoding plus explicit
enum checks. This is the second, for a measured reason.

On a 50,000-result envelope (13.6 MB of JSON, which is what a 1000-trial sweep of several
configurations looks like):

| path | time | allocated | allocations |
|---|---:|---:|---:|
| `json.Decoder` with `DisallowUnknownFields` + `RunEnvelope.Validate()` | **98.3 ms** | 91.8 MB | 120,037 |
| `json.Unmarshal` into `any` + `jsonschema.Validate` | **1050.3 ms** | 901.6 MB | 18,150,422 |

That is **10.7× slower and 151× more allocations** for the same verdict
(`docs/results/m1.3/validation_bench.log`). The reason is structural, not a library flaw:
JSON Schema validates a generic tree, so every result object becomes a `map[string]any`
with boxed values, and the `allOf` of twelve `if/then` blocks visits each result twelve
times. Strict decoding fills a struct once.

The second reason is the error message. The schema library reports
`/results/8412/unit: value must be "ops/s"`; the Go validator reports
`results[8412].unit: metric cpu_int_ops is measured in ops/s, got "GB/s"`, and it reports
up to 20 problems in one response instead of stopping at the first.

The cost of this choice is duplication: the enum lists and the metric→unit/workload
pairings now exist in two places. That is what the next section is about.

### The tests that make the duplication safe

Three tests in [internal/model](../../api/internal/model) read the schema file *at test
time* and compare it to the Go code:

- `TestEnumsMatchSchema` — the `workload`, `metric` and `unit` enums must be equal as
  ordered lists.
- `TestMetricPairingsMatchSchema` — reads the twelve `if/then` blocks out of
  `$defs/result_core/allOf` and rebuilds the metric→unit and metric→workload maps from
  them, then compares to `model.UnitOf` and `model.WorkloadOf`. It also asserts the block
  count equals the metric count, so a metric added to the enum without an `if/then` block
  fails here rather than silently accepting any unit.
- `TestGoValidatorAgreesWithJSONSchema` — takes the repository's own valid example and
  applies **fourteen one-field mutations** (a `run_id` that is not a UUID, a timestamp
  without `Z`, a metric with the wrong unit, a `thread_count` of 0, a machine block
  smuggled into a result, an unknown top-level field, …). For each, the compiled JSON
  Schema and the Go path must reach the same verdict.

So the JSON Schema library *is* a dependency — of the test binary, not the request path.
It is the oracle; the fast path is what ships.

### Idempotency lives in the database, not in a memory of recent requests

`POST /v1/runs` is `INSERT INTO runs … ON CONFLICT (id) DO NOTHING`. If no row was
inserted the run is already stored, the transaction ends, and the response is
`{"inserted": 0, "duplicate": true}`.

Choosing 200-with-`inserted: 0` over 409 was deliberate: the engine's `--post` (M1.4)
retries a POST it could not confirm, and a client that retried correctly should not have
to treat success as an error. The `duplicate` flag is there so a caller that *does* care
can see it.

Note what this is not: it is not deduplication of *measurements*. Two different runs of the
same configuration are two different `run_id`s and both belong in the table. The unit of
idempotency is the run, which is exactly the unit the engine emits.

### `CopyFrom`, in batches, inside the transaction

Ingest uses pgx's `CopyFrom` (the Postgres COPY protocol) rather than an `INSERT` loop,
in batches of 10,000 rows. One batch would hold the entire 50K-row slice in the protocol
buffer at once; one row per call is the thing being avoided. The measured ingest rate is
in `M5.1.md` — this milestone only makes the choice.

`CopyFrom` has one property worth stating: it does not fire `ON CONFLICT`. That is fine
here because the conflict is resolved one level up, on `runs.id`, before any measurement
row is written. It would not be fine if measurements had their own uniqueness rule.

### Keyset pagination from the first endpoint

`GET /v1/measurements` pages with `WHERE id > $cursor ORDER BY id LIMIT $n`, never
`OFFSET`. `OFFSET 90000` makes Postgres walk and discard 90,000 rows; the last page of a
100K-row list costs as much as the whole scan. The keyset form is a range scan from an
index position regardless of depth.

`next_cursor` is returned **only when the page came back full**. A short page is the last
page, and handing out a cursor there would invite a client to poll an endpoint that has
nothing more to give.

One detail that matters at the boundary: filters use `*int` / `*int64` pointers, not
values. `working_set_bytes=0` is a real filter — it is what every CPU metric records — and
a zero-valued int would be indistinguishable from "not filtering".

### Why `/healthz` must not touch Postgres

Liveness and readiness answer different questions. Liveness is "should this process be
restarted"; readiness is "should this process receive traffic". If `/healthz` pinged
Postgres, a 30-second database blip would get every API instance killed by the orchestrator
— which is the one thing guaranteed to make the outage longer. A handler test asserts
exactly this: with the store's ping failing, `/readyz` is 503 and `/healthz` is still 200.

## The bug the first real POST found

Every test passed. The example envelope in `schema/examples/run.json` ingested. Then the
first POST of an actual engine run:

```
{"error":{"code":"invalid_json","message":"request body is not a valid run envelope",
          "details":["json: unknown field \"canary_attempts\""]}}
```

The engine's `summary` entries carry the M2.5 run-quality fields — `late_trials`,
`canary_attempts`, `clock_call_ns_start`, `clock_call_ns_end` — which the schema allows and
the Go `Summary` struct did not have. `DisallowUnknownFields` did its job: it refused a
document it did not fully understand, instead of dropping four fields on the floor.

This is the trade-off of strict decoding, and it is the right side of it. The lenient
alternative would have ingested that run happily, and the fields would have been missing
from every row without a single error anywhere. The fix was four struct fields; the
lesson was that **the hand-written example is not a substitute for real output**, so
`TestRealEngineRunDecodesStrictly` now reads the committed engine run in
`docs/results/m1.3/engine_run.json`, decodes it strictly, validates it, and checks the
normative JSON Schema accepts it too.

The second finding was cosmetic but the same shape. pgx renders `timestamptz` into the
API process's local zone, so the first list response carried
`"recorded_at": "2026-09-21T14:21:08.939112-05:00"` — the right instant, in the wrong
convention for a project whose every other timestamp is UTC with a `Z`. Responses now
convert on scan.

## Verification

All of these are in `docs/results/m1.3/`.

```
$ go test ./...                       15 tests, ok
$ go test -tags integration ./...      5 store tests against compose Postgres, ok
$ go vet ./... && gofmt -l .          clean
```

End-to-end, against a real engine run of 10 `cpu_int` trials:

| step | result |
|---|---|
| first `POST /v1/runs` | `{"run_id":"993fe091…","inserted":10,"duplicate":false}` |
| second POST, same run | `{"inserted":0,"duplicate":true}` |
| `select count(*) from measurements` | `10` |
| `machines` | one row: `7fea9eca…`, MatthewLaptop, 11 cores, 24576 KiB L3 |
| `runs.argv` | the exact command line, as `jsonb` |
| `GET /v1/measurements?metric=cpu_int_ops&limit=2` | trials 0 and 1, `4.696e9` and `4.881e9` ops/s, `next_cursor: 12` |
| `GET /v1/measurements?metric=nope` | HTTP 400, `invalid_query` |
| `/healthz`, `/readyz` | 200, `{"postgres":"ok"}` |

The integration tests are worth listing individually, because each one pins a property
rather than a line of code:

- `TestIngestRoundTrip` — a result read back through SQL equals the result that was
  posted, `params` included, and carries the run and machine ids the envelope hoisted.
- `TestIngestIsIdempotentOnRunID` — a second POST adds no rows.
- `TestMachineUpsertKeepsFirstSeen` — `first_seen` is the minimum, `last_seen` the
  maximum, and mutable machine fields (a renamed host) follow the newer run.
- `TestKeysetPaginationCoversEveryRowExactlyOnce` — 250 rows paged 37 at a time land on
  250 distinct ids, each seen once.
- `TestFiltersNarrowAsAdvertised` — seven filter combinations return the counts the
  fixture was built to have.

Each integration test creates its own Postgres schema, migrates it, and drops it
afterwards, so they are order-independent and leave nothing behind.

## What this milestone does not do

- **No streaming decode.** The whole body is decoded into memory. The 50K-result envelope
  above allocates 91.8 MB doing it. That is M5.1.
- **No machines/runs endpoints, no gzip, no request ids, no timeouts.** Also M5.1.
- **No aggregation.** Everything here is raw rows; mean/median/p95/CoV are M5.3.
- **No Redis.** The cache-aside layer is M5.3, and the API must keep working without it.
- **Summaries are accepted but not stored.** The engine computes them; the API will
  recompute them from the measurements in SQL, so storing them would create a second
  source of truth that could disagree with the rows it summarizes.
