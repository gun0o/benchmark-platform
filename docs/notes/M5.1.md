# M5.1 — Ingest and query hardening

*Milestone notes, written for someone learning how an ingest path is made to hold up.
Measured on 2026-09-21 on the Core Ultra 9 185H laptop under WSL2, Postgres 16-alpine in
Docker Desktop (data on a VHDX, as with every disk number in this project), API running
natively in WSL. Raw logs: `docs/results/m5.1/`. Earlier notes: `M1.3.md`, `M1.4.md`.*

## The problem this milestone solves

M1.3's ingest worked on a ten-trial run. Three things about it do not survive contact with
the real thing:

1. **It decodes the whole document before storing any of it.** A 1000-trial sweep is tens
   of megabytes of JSON; the object graph is live in memory for the length of the request,
   once per concurrent ingest.
2. **Its unit of idempotency is the run.** That was fine while one run was one POST. It
   stops being fine the moment a run is too large for one request, because "this run
   already exists" then means "ignore the rest of it".
3. **Nothing is bounded.** No request timeouts, no body limit, no panic recovery, no
   request id to connect a slow response to the query that caused it.

M5.1 fixes those and adds the read endpoints the dashboard needs to name a machine.

## What was built

1. **Streaming ingest** — `model.StreamRunEnvelope` hands each result to a callback as it
   is parsed; `store.IngestStream` fills a 10,000-row batch, sends it with `CopyFrom`, and
   reuses the buffer. Peak retained heap for a 50K envelope: **2.3 MB instead of 11.5 MB**.
2. **Row-level idempotency** — a unique index on
   `(run_id, metric, thread_count, working_set_bytes, trial)` (migration `0002`), so
   chunks of one run append and a repeated chunk inserts nothing.
3. **`bench run --post-chunk` (default 50,000)** — the engine splits a larger run into
   several POSTs sharing its `run_id`.
4. **Four read endpoints** — `GET /v1/machines`, `/v1/machines/{id}`, `/v1/runs`,
   `/v1/runs/{id}`.
5. **Middleware** — `X-Request-ID` in and out, one structured log line per request with its
   duration, panic recovery, gzip, and a 5-second handler deadline that reaches Postgres.
6. **Server and pool limits** — `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`,
   `IdleTimeout`, `MaxHeaderBytes`, and `PG_MAX_CONNS` (default 20).
7. **Postgres tuning in compose** — `shared_buffers=512MB`, `work_mem=32MB`, and
   `synchronous_commit` left **on**, with `deploy/.env.loadtest.example` as the only way to
   turn it off.
8. **Migration `0003`** — the filter index now ends with `id`. Why is below.

## Each decision, and why

### Streaming buys memory, not time

| path (50,000 results, 13.6 MB of JSON) | time | allocated | allocations | retained |
|---|---:|---:|---:|---:|
| whole-document decode + validate (M1.3) | 96.9 ms | 91.8 MB | 120,031 | 11.5 MB |
| streaming decode + validate | 93.5 ms | 19.8 MB | 170,005 | — |
| streaming into 10K batches (what ingest does) | 96.3 ms | 21.1 MB | 170,011 | **2.3 MB** |

Two things in that table are worth reading carefully.

**The time is identical.** `encoding/json` already reads from an `io.Reader` incrementally;
what changes is what the program *keeps*, not how it parses. Anyone expecting streaming to
be faster would have been wrong, and the measurement says so.

**"Allocated" and "retained" are different numbers and the second is the one that matters.**
The whole-document path *allocates* 91.8 MB but *retains* 11.5 MB — most of that 91.8 MB is
garbage from growing one big slice repeatedly. Retained memory is what decides how many
concurrent ingests fit in a container; the streaming path holds one batch, so it is flat in
the envelope's size. `TestRetainedHeap` measures it with `runtime.ReadMemStats` and fails if
the streaming peak is not well under half.

The allocation *count* went up (120K → 170K), because each result is now decoded into its
own value instead of into a slice the decoder grows. That is the trade, and it costs
nothing measurable in time.

### Idempotency had to move from the run to the row

Chunking and M1.3's rule contradict each other: if "run already exists" means "do nothing",
the second chunk of a run is silently dropped. The fix is a unique index on
`(run_id, metric, thread_count, working_set_bytes, trial)` — the tuple that *defines* one
measurement — and `ON CONFLICT DO NOTHING` when inserting.

`COPY` cannot express a conflict rule, so the conflict-aware path copies the batch into a
temp table and moves it across with `INSERT … SELECT … ON CONFLICT DO NOTHING`. That costs
**19,323 rows/s against 26,611** for a plain `CopyFrom` — about 30 % — so it is not used
unconditionally:

- **New run** → plain `CopyFrom`. Nothing in the table can conflict with a run that did not
  exist a moment ago.
- **Existing run** (a later chunk, or a retry) → the temp-table path from the start.
- **A new run whose own envelope repeats a configuration** → the plain copy hits the unique
  index, the batch is rolled back to a `SAVEPOINT`, and it is re-run through the
  conflict-aware path. Without the savepoint, the unique violation would poison the whole
  transaction and lose the run.

`TestSelfDuplicatingEnvelopeIsStoredOnce` exercises exactly that: 22 results of which 2 are
repeats, answered with `results: 22, inserted: 20, skipped: 2`. The response reports
`skipped` rather than hiding it, because a client that posted 22 rows and stored 20 should
be told.

### The ingest-rate target, and where the time actually goes

The target was a 50,000-result envelope in under 2 seconds. Measured:

| | |
|---|---:|
| 17.0 MB envelope, POSTed with `curl` | **2.05 s** |
| 12.0 MB fixture, in-process (no HTTP) | 1.64 s |
| the same 50,000 rows written *inside* Postgres, no client, no JSON, no HTTP | **1.43 s** |

So the target is met in-process and **missed by 0.05 s over HTTP** — and the third line says
why that is not an ingest-path problem. `INSERT … SELECT … FROM generate_series(1,50000)`,
which involves no Go, no network and no decoding at all, takes 1.43 s on this Postgres. The
write rate of this instance is the binding constraint at about 35,000 rows/s.

Two more measurements close off the obvious suspicions:

- **`synchronous_commit=off` changes nothing** (2.08 s, with the API restarted so its pooled
  sessions actually pick the setting up). It is one transaction, so there is one WAL flush
  to save; the cost is elsewhere.
- **`params` jsonb is free**: copying the same rows with `params` set to NULL gives
  26,984 rows/s against 26,611. The jsonb blob is not what is slow.
- **Index maintenance is ~15 %**: dropping the three indexes gives 31,395 rows/s.

The honest summary is that this is a Postgres on a VHDX inside Docker Desktop inside WSL2,
and it writes about 30K rows/s no matter how the rows are handed to it. The number is
recorded as measured rather than tuned until it passes.

What the milestone *does* establish is the pitfall it names: **row-by-row `INSERT` is
4,437 rows/s**, 11.3 s extrapolated to 50,000 rows, against 26,611 for batched `CopyFrom`.
Six times, not the sixty the plan guessed — but the guess and the measurement disagree in
magnitude only because this Postgres is slow at the write itself, which compresses every
ratio above it.

### Batch size 10,000, not 1 and not 50,000

One `CopyFrom` of all 50,000 rows measured 27,435 rows/s against 26,611 for ten batches of
10,000 — a 3 % difference, inside the run-to-run spread. The batching is therefore not
there for speed; it is there so that the Go side never holds more than 10,000 rows, which
is the whole point of streaming. Paying 3 % for a bounded memory profile is an easy trade,
and the measurement is what makes it a trade rather than an assumption.

### The filter index had to end with `id`

`EXPLAIN (ANALYZE, BUFFERS)` on the list query with all five filters showed an **Index Scan
on the primary key**, not on `measurements_filter_idx`. The planner was right: the query is
`WHERE (five columns) ORDER BY id LIMIT 100`, and an index on those five columns cannot
produce `id` order, so using it would mean a sort of everything that matched. Walking the
primary key and filtering was cheaper.

Migration `0003` appends `id` to the index, which lets one index answer the filter, the
keyset cursor and the ordering together. The plan did not change on the data present at the
time — every row in the table then belonged to one machine and one metric, so the primary
key finds 100 matches within 421 rows and the composite index really is more work. That is
the planner behaving correctly on a degenerate table, so **this verify step is completed
against the seeded 100K rows over five machines in M5.2** (`docs/results/m5.2/explain.log`),
where the filters are actually selective.

The same `EXPLAIN` run did settle the pagination question, on today's data:

| | time | buffers |
|---|---:|---:|
| keyset (`id > 40000 … LIMIT 100`) | 0.16 ms | 26 |
| `OFFSET 40000 … LIMIT 100` | **26.98 ms** | **8,388** |

168× slower and 322× the buffers, for the same page, at a depth a dashboard reaches by
scrolling. This is why M1.3 used keyset pagination from the first endpoint.

### Middleware, and one thing deliberately left out of it

The stack is, outermost first: request id → logging → recovery → gzip → handler deadline.

- **Request id** is echoed when the client sends one, minted (8 random bytes, hex) when not,
  and on the response header either way. The log line carries it, so
  `"request_id":"from-the-shell"` in the API's log is the exact `curl` that produced it.
- **Gzip** is applied only when the client asked, and it sets `Vary: Accept-Encoding` so a
  cache cannot serve a compressed body to a client that cannot read it. On a 1000-row
  measurement page: **428,545 → 30,035 bytes, 14.3×**. Measurement rows are extremely
  repetitive JSON; this is the cheapest bandwidth in the project.
- **Recovery** turns a panic into a 500 with a log line, and a test asserts the panic value
  does not reach the client.
- **The 5-second handler deadline does not apply to `POST /v1/runs`.** Five seconds is a
  *query* budget; ingest reads a body that may be 17 MB and writes 50,000 rows, and the
  measurement above says that legitimately takes 2 s and could take more on a slower disk.
  Ingest is bounded by the server's `WriteTimeout` instead. Applying one deadline to both
  would have meant either killing legitimate ingests or giving every read five times the
  budget it needs.

### Postgres tuning is in compose, and durability is not

`shared_buffers=512MB`, `work_mem=32MB`, `effective_cache_size=2GB` are defaults in the
compose file. `synchronous_commit` stays **on**. The load-test profile
(`deploy/.env.loadtest.example`) is the only thing that turns it off, and any k6 number
taken under it says so — which, given the measurement above, is mostly a matter of honesty
rather than performance, since it changed nothing here.

New integration tests: streaming ingest matches the decoded path; chunks append and repeats
are no-ops; a self-duplicating envelope stores once; a rejected document leaves no run and
no rows behind; and the 50K timing test above, which fails if ingest ever crosses 2 s
in-process.

## What this milestone does not do

- **No aggregation and no cache.** `/v1/aggregates`, `/v1/compare`, `/v1/trials` and Redis
  are M5.3.
- **No `/metrics` or `/debug/pprof`.** M5.5.
- **No tuning of the write rate.** The 30K rows/s figure is recorded, its cause is located
  (Postgres on a VHDX), and nothing was changed to flatter it.
