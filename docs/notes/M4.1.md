# M4.1 — Disk I/O with O_DIRECT

*Milestone notes, written for someone learning benchmark methodology. Measured on
2026-09-21 on a Core Ultra 9 185H laptop under WSL2, release build, **plugged in**, Windows
power plan "Balanced", power mode **"Best performance"**, battery 100 % and charging. The
test file is 4 GiB on the ext4 root, which is a VHDX on the Windows host; guest
`MemAvailable` at the time was 13.4 GB. Power state was recorded before and after every
run; the logs are in `docs/results/m4.1/`. Earlier notes: `M1.2.md`, `M2.1.md`, `M2.2.md`,
`M2.3.md`, `M2.4.md`, `M2.5.md`, `M3.1.md`, `M3.2.md`.*

## The problem this milestone solves

A disk benchmark has one failure mode that swallows all the others: **measuring the page
cache instead of the disk**. Read a file twice and the second read is a `memcpy` from RAM,
which on this machine is fifty times faster than the SSD. Every number would be real, and
every number would be about the wrong thing.

The defence is `O_DIRECT`, which tells the kernel to move data between the device and the
caller's buffer with nothing in between. It comes with alignment rules — buffer address,
file offset and transfer length all aligned to the device's block size — and with an
important limit: from inside WSL2 it bypasses the **guest's** page cache, and says nothing
about whether the Windows host is caching the VHDX that backs this filesystem. That limit
is documented and tested up to its boundary, not worked around, because it cannot be
observed from inside the guest.

This milestone is also where the engine finally produces two different kinds of answer from
one trial: `disk_rand_read_iops` (a rate) and `disk_rand_read_p99_us` (a percentile over the
individual reads that rate counted).

## What was built

1. **`disk_seq`** — 1 MiB `O_DIRECT` `pread`/`pwrite`, one contiguous region of the file per
   thread. Writes call `fdatasync` inside the timed region.
2. **`disk_rand`** — 4 KiB `O_DIRECT` reads at uniformly random 4 KiB-aligned offsets, queue
   depth = thread count (one outstanding synchronous I/O per thread). Random writes add
   `O_DSYNC`. Every call is timed into a 1 µs-bucket histogram.
3. **The test file**: `--disk-path` (default `$HOME/.cache/bench/testfile`), created with
   `fallocate` and **filled with random data** through 1 MiB `O_DIRECT` writes plus
   `fdatasync`, reused if it already exists at the right size. `bench disk prep` and
   `bench disk clean` manage it, so a 4 GiB file is never left behind by accident and is
   never inside the repository.
4. **Guards**: `--disk-path` under `/mnt` is refused unless `--i-know-this-is-9p`; the write
   metrics need `--allow-writes`; `--write-budget` (default 1 GiB) stops the run at a trial
   boundary once that many bytes have been written.
5. **`--trial-ms` defaults to 500 for disk**, because a 4 KiB read is ~110 µs and a 50 ms
   trial would hold a few hundred samples — too few for a p99 to mean anything.
6. **17 new tests** (`disk_io_test.cpp`) and 20 new `params` keys. 168/168 pass in release,
   debug, ci, asan and tsan.

## The bug that was worth the whole milestone

`disk_rand_read_p99_us` came out as **exactly 0.00 in every row** of the first run. The IOPS
next to it were fine. Nothing errored, nothing warned, and the zero looked enough like "not
implemented yet" to be easy to wave past.

The histogram lives in the workload, which lives on the worker thread. The worker's loop is:

```
wait at the start barrier → run the trial → arrive at the end barrier → before_trial() → …
```

and the main thread's is:

```
arrive at the end barrier → read every worker's slot, including the histogram → next trial
```

Both threads leave the end barrier at the same instant. The worker's very next act is
`before_trial()`, which **clears the histogram** so the next trial's p99 is over the next
trial's reads. The main thread was still counting those buckets. The worker usually won.

The existing comment in the runner says every write to a worker's slot happens between the
two barriers, so the main thread's reads can never race the next trial. That is true — and
the histogram is not in the slot. It is four megabytes of workload-owned memory that the
slot merely points at, and the invariant did not extend to it.

The fix is two histograms, alternating. `before_trial()` flips to the other buffer and
clears *that* one, which the previous trial's reader finished with two trials ago; the
pointer the worker publishes to its slot is the buffer it just filled. There is a test whose
only job is to fail if someone goes back to one buffer.

Two things about how this was found are worth recording. The first is that the fix had to be
made before TSan would have had anything to say — under ASan and in the debug build the race
resolved the other way and the p99 came out correct, which is the worst possible behaviour
for a bug. The second is below.

## A build that was lying, and a clock that was lying to it

While fixing the above, the release build began segfaulting in `merge_latencies` while the
debug build ran clean. The fault was a dereference of `0x3da174040` — not null, not a heap
address, just wrong.

It was a **stale object file**. `runner.cpp.o` had been compiled against the old header, in
which the histogram was one vector rather than two; the new `latency_histogram()` read a
differently-shaped object through the old layout and handed back a garbage pointer. Ninja
should have rebuilt it and did not.

The reason it did not is the same WSL2 clock instability M3.2 recorded from the other side.
Measured at the time: the guest clock read `12:15:05` while the Windows host read
`12:20:50` — **5 minutes 45 seconds apart** — and six files in the build tree carried
timestamps in the guest's future. Ninja compares timestamps; with the clock sliding back and
forth under it, "newer than" stops being a reliable question, and `cmake` eventually failed
outright with `manifest 'build.ninja' still dirty after 100 tries, perhaps system time is
not set`.

M3.2 saw the same clock from the measurement side: a run whose envelope claimed 5 minutes
47 seconds for 1.7 seconds of work. Same skew, same magnitude, two milestones apart. The
project's rule that *all timing uses `steady_clock` and `started_at`/`finished_at` are
metadata* is what kept every measured number correct through both.

The practical recovery, recorded in case it recurs: pull future-dated files back to now
(`find build -newermt "@$(date +%s)" -exec touch -d "@$(($(date +%s)-5))" {} +`), then
reconfigure. A clean rebuild of all five presets followed.

## Verify 1 — is `O_DIRECT` actually on, and are the transfers the right size?

`docs/results/m4.1/strace.log`, produced by `strace_check.sh`:

```
openat(AT_FDCWD, ".../testfile", O_RDONLY|O_DIRECT)            = 3
openat(AT_FDCWD, ".../testfile", O_WRONLY|O_DSYNC|O_DIRECT)    = 3

disk_seq_read_bw    transfer sizes:   32 x 1048576      (1 MiB)
disk_rand_read_iops transfer sizes:   96 x 4096         (4 KiB)
                    offset mod 4096:  96 x 0            (all aligned)
disk_seq_write_bw   144 x pwrite64 of 1048576, 9 x fdatasync    (144/16 = 9)
```

All four claims hold, including the one that is easy to get wrong by one: the sequential
write path calls `fdatasync` exactly once per 16-block batch, which is what the code says it
does. (The handful of 48-, 68- and 784-byte `pread64`s in the raw trace are the dynamic
loader reading ELF headers, which is why the sizes are counted rather than eyeballed.)

## Verify 2 — the numbers, and a comparison that had to be run twice

PLAN.md asks for agreement with `fio --direct=1 --ioengine=psync` within about 10 %. fio is
not packaged on this machine and there is no root, so it was **built from source**
(fio 3.36; the `psync` engine needs no optional libraries). The build commands are recorded
at the top of `fio_compare.sh`.

### The first comparison, run the obvious way

| measurement | bench | fio | difference |
|---|---:|---:|---:|
| seq read, 1 thread | 2690 MB/s | 2688 MB/s | **+0.1 %** |
| seq read, 4 threads | 6405 MB/s | 5449 MB/s | **+17.5 %** |
| rand read, QD 1 | 9131 IOPS | 8120 IOPS | **+12.5 %** |
| rand read, QD 4 | 32808 IOPS | 29219 IOPS | **+12.3 %** |
| rand read, QD 16 | 89966 IOPS | 83696 IOPS | +7.5 % |
| p99, QD 1 | 274 µs | 285 µs | −3.7 % |
| p99, QD 4 | 234 µs | 276 µs | −15.4 % |
| p99, QD 16 | 300 µs | 305 µs | −1.7 % |

Three of the throughput rows are outside the 10 % band, all in the same direction. The
tempting conclusion is that the engine's loop is leaner than fio's — plausible, and wrong.

### The second comparison, run the way M2.5 taught

M2.5's most transferable finding was that a single A-then-B comparison confounds the knob
with *when it ran*, on a machine that drifts. Storage has a drifting variable of exactly
this kind, and it is the one thing this environment cannot control: the Windows host's cache
over the VHDX. So the comparison was re-run **alternating**, engine then fio, same
parameters, three repetitions:

| measurement | median bench/fio | range over 3 reps |
|---|---:|---|
| seq read, 1 thread | **0.968** | 0.954 – 1.025 |
| seq read, 4 threads | **0.984** | 0.981 – 0.990 |
| rand read, QD 1 | **0.958** | 0.928 – 0.979 |
| rand read, QD 4 | **1.016** | 0.995 – 1.061 |
| rand read, QD 16 | **1.030** | 0.989 – 1.063 |

Every ratio is within **±5 %**, comfortably inside PLAN.md's 10 %. The +12 to +18 % was
drift, not a tool difference. A supporting measurement points the same way: fio's own
`randread` at QD 1 moves between **7763 and 8815 IOPS** depending only on which of four
reasonable parameter choices it is given (`--norandommap`, `--random_generator`, `--thread`)
— a 13 % spread inside the reference tool itself.

**The engine agrees with fio.** The honest way to state the comparison is the alternating
one, and the first table is kept because a reader who runs the obvious experiment will get
the obvious answer and should know why it is wrong.

### The measurements themselves

| metric | 1 thread | 4 threads | 16 threads |
|---|---:|---:|---:|
| `disk_seq_read_bw` | 2690 MB/s | 6405 MB/s | — |
| `disk_seq_write_bw` | 1487 MB/s | 1951 MB/s | — |
| `disk_rand_read_iops` | 9131 | 32808 | 89966 |
| `disk_rand_read_p99_us` | 274 µs | 234 µs | 300 µs |
| `disk_rand_write_iops` | 512 | 554 | 585 |

Three things in that table are worth reading rather than just recording.

**Random reads scale almost linearly and sequential reads do not.** 9131 → 32808 → 89966 is
3.6× then 2.7×, against sequential's 2.4× from 1 to 4 threads. A single synchronous reader
is limited by round-trip latency (9131 IOPS is 110 µs per read, and it does nothing while
waiting), so adding threads adds independent requests the device can overlap. Sequential
reads already keep the device busy, so there is less to recover.

**Random writes do not scale at all**: 512 → 554 → 585 IOPS, +14 % for sixteen times the
threads. That is `O_DSYNC` doing exactly what it is for. Every write must be durable before
it returns, so the cost is a device-level flush, and flushes serialize no matter how many
threads ask for one. The metric is defined as durable 4 KiB writes because that is the
number a database's commit path lives on, and 512 IOPS at QD 1 — about 2 ms per durable
write — is the number. It is 18× slower than a 4 KiB read on the same device.

**The p99 does not rise with queue depth the way the mean does.** 274, 234, 300 µs across
QD 1, 4 and 16, while IOPS went up tenfold. At QD 16 the device is working nearly ten times
harder for a 10 % worse tail. Note also that p99 at QD 1 (274 µs) is nearly **2.5× the mean**
(110 µs), so the tail is far from the average even on an idle device — which is the entire
reason the metric exists alongside IOPS.

## Verify 3 — the cold check

If `O_DIRECT` is doing its job, two things must be true: the first trial of a run is no
slower than the rest (nothing is warming up), and deliberately filling the guest page cache
with the whole file first must not make the next run faster.

Ten trials of 300 ms with **no warmup at all**, then `dd if=testfile of=/dev/null` (which
took the guest's `buff/cache` from 4251 MB to 8347 MB, i.e. the whole 4 GiB file is now
cached), then ten more:

```
cold start : 2126  2235  2552  2453  2422  2425  2332  2254  2285  2465   MB/s
warm cache : 2130  2341  2528  2351  2374  2496  2325  2540  2377  2399   MB/s
```

| | median of ten | trial 0 / rest |
|---|---:|---:|
| cold start | 2377 MB/s | 0.878 |
| guest page cache deliberately filled | 2375 MB/s | 0.896 |

**−0.1 %.** Four gigabytes sitting in the guest's page cache are worth nothing to the next
read, which is what `O_DIRECT` promises and is now measured rather than assumed. And trial 0
is *slower* than the trials after it (0.88×) in both runs — the opposite of a caching
effect, and consistent with M1.2's finding that a first trial pays for frequency ramp and
first-touch.

**What this does not show.** Nothing here rules out the Windows host caching the VHDX. The
guest cannot see the host's cache, cannot drop it, and cannot measure it; `drop_caches`
needs root, which this machine does not have, and would only affect the guest anyway. The
sequential read figure of 2.7 GB/s at one thread and 6.4 GB/s at four is within the range a
PCIe 4 NVMe SSD can do unaided, so it is not *evidence* of host caching either. The honest
label, which PLAN.md chose in advance and this milestone keeps, is **"virtual disk"**: these
are the numbers a program running in this WSL2 guest will see, which is a useful thing to
know and is not the same as the device's numbers.

## Design decisions worth their paragraph

**One `fdatasync` per 16 MiB batch, not per trial.** PLAN.md puts the sync "at trial end
inside the timed region", but the trial loop runs whole batches and a workload cannot see a
trial boundary. Syncing every batch is inside the timed region, is *stricter* than syncing
once per trial, and makes `disk_seq_write_bw` mean "sequential write throughput including
durability" — which is what the figure is usually taken to mean anyway. `strace` confirms
the 16:1 ratio.

**The p99 is nearest-rank, not the `linear` interpolation the rest of the project uses.**
`stats.hpp` pins percentiles to numpy's `linear` method, and trial-level summaries still use
it. Interpolating between two adjacent 1 µs buckets would invent precision the histogram does
not have — the samples were rounded to a microsecond on the way in. Nearest rank reported at
the bucket's upper edge answers "99 % of reads completed within X µs", quantized by at most
1 µs, which is under 0.4 % of a 274 µs p99.

**The file is filled with random data, never left sparse or zeroed.** A sparse file's reads
never reach the device, and thin-provisioned, compressing or deduplicating layers
short-circuit runs of zeros. Either would turn a disk benchmark into a benchmark of the
filesystem's bookkeeping. A test reads the whole file back and asserts zero all-zero 4 KiB
blocks.

**N threads are N sequential streams.** Each thread owns a contiguous, block-aligned region
of the file and wraps inside it. The alternative — N threads interleaving into one stream —
would measure something real but not sequential I/O, and would make the 4-thread number
incomparable with fio's `--offset_increment` behaviour.

**Writes are gated twice.** `--allow-writes` is required at all, and `--write-budget`
(1 GiB by default) stops the run at a trial boundary once that much has been written. The
study raises the budget to 8 GiB explicitly, and the raised value is recorded in the run's
`argv`, so a reader can see that the wear guard was lifted on purpose. Verified working: a
run asking for 20 write trials against a 256 MiB budget stopped after 1 trial and said so.

## Deviations from PLAN.md

- **`--trial-ms` is 500 by default for disk, 50 otherwise**, implemented as a default that
  only applies when the user did not pass the flag. PLAN.md asks for this; it is recorded
  because a silently different default per workload is the kind of thing that surprises
  someone comparing runs.
- **fio was built from source**, since it is not installed and there is no root. Recorded in
  `fio_compare.sh` so the comparison is reproducible.
- **The p99 rides on the IOPS trial.** PLAN.md lists `disk_rand_read_p99_us` as its own
  metric; running it as its own configuration would measure a different second's worth of
  I/O and cost twice the time for a worse answer. The "rider" mechanism built in M3.1 exists
  for exactly this, and `--metric disk_rand_read_p99_us` refuses rather than silently
  running something else.

## What is not established here

- **No CoV claim.** 3–5 trials per configuration, enough for a number, not for a variance.
- **No host-cache determination**, for the reasons above.
- **`disk_rand_write_iops` has no p99**, because CLAUDE.md defines only the read one. The
  histogram is recorded for writes too and is available in `params`.
- **These are virtual-disk numbers** on a laptop whose storage is shared with Windows. A
  background Windows indexing or update pass during a run would show up and is not
  detectable from here; the run log records `uptime` and the power state around every run,
  which is as close as the guest can get.
