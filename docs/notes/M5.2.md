# M5.2 — A synthetic data generator that is not random noise

*Milestone notes, written for someone learning how to build test data worth developing
against. Run on 2026-09-21 against the compose Postgres and the API from M5.1. Raw logs:
`docs/results/m5.2/`. Earlier notes: `M1.3.md`, `M1.4.md`, `M5.1.md`.*

## The problem this milestone solves

The dashboard needs 100,000+ measurements before it exists, and the API needs them before
it can be load-tested. The obvious way to produce them — a loop that inserts random values
— would satisfy the row count and nothing else. Uniform noise has no scaling curve, no
cache steps and no queue saturation, so every chart built on it would be a flat cloud, and
every chart would look "fine" whether or not the query behind it was right.

The rule this project applies to its own measurements — *a number is only worth having if
you can say what it means* — applies to fake numbers too, in the negative: **fake data
must be labelled as fake, and must be shaped like the thing it stands in for**, or it
teaches you nothing and might mislead you.

So the generator is a model. Each value is the expected value of a described physical
behaviour plus per-trial noise, and every synthetic machine says `synthetic-NN` and
`engine_version: "seed"` so it can never be mistaken for something measured.

## What was built

1. **Five machine profiles** — a 64-core EPYC server, a 14-core laptop, a 4-vCPU cloud
   instance, an old 4-core desktop, and a hybrid-core laptop. They differ in cores, cache
   sizes, memory bandwidth, disk class, clock and noise level.
2. **Five value models** — Amdahl-like CPU scaling with an SMT penalty, a blended cache
   hierarchy for bandwidth and latency, write-allocate, a saturating disk queue, and a
   skewed p99.
3. **`cmd/seed`** — `--machines --trials --seed --runs-per-machine --out --post --chunk
   --allow-small`. Prints the exact row count, refuses to exit 0 below 100,000 rows, and
   posts through the real ingest path.
4. **Eleven generator tests** that assert the *shape* of the curves, not just that values
   exist.

The default invocation is 5 machines × 225 configurations × 100 trials = **112,500 rows**.

## Each decision, and why

### The values come from models, and each model is a claim

| metric | model | what it produces |
|---|---|---|
| `cpu_*_ops` | `T(n) = T1·n / (1 + (n−1)s)`, times an SMT penalty | scaling that bends and then flattens; the 4-vCPU instance (`s = 0.09`) reaches 6.2× at 16 threads, the EPYC (`s = 0.004`) 14.9× |
| `mem_*_bw` | per-thread bandwidth from a blended hierarchy, capped by a shared ceiling | the knee: adding threads helps until the level saturates |
| `mem_write_bw` | the same, with a write-allocate factor that fades in as the set leaves L1 | the 3.6× cliff M3.1 measured on the real machine |
| `mem_latency` | blended L1/L2/L3/DRAM, plus a slow climb past the LLC | steps at the cache sizes, and the +20 % drift M3.2 found from 24 MiB to 1 GiB |
| `disk_seq_*_bw` | `ceiling · (0.42 + 0.58·q/(q+2.2))` | one stream is already most of the device; more help a little |
| `disk_rand_*_iops` | `cap · q/(q + halfQD)` | Little's law with a ceiling |
| `disk_rand_read_p99_us` | grows with queue depth, log-normal, plus injected stalls | a tail that behaves like a tail |

The "blended hierarchy" is worth a sentence, because it is where a naive generator gives
itself away. A step function over the cache sizes produces a staircase no measurement ever
looks like: a real sweep starts missing before the working set equals the cache, because
of associativity, other data and the chase's own metadata. The generator blends adjacent
levels with a logistic over `log2(bytes)`, width 0.55, so each transition takes about a
factor of 1.5 in working set to complete — which is roughly what the M3.2 sweep shows
between 48 KiB and 64 KiB.

The models are deliberately tied to the project's *own* measurements: the write-allocate
factor, the post-LLC latency climb and the hybrid machine's poor 16-thread scaling are all
things M3.1, M3.2 and M2.4 found on the real laptop. A synthetic machine that behaves in
ways this project has never observed would be a worse fixture.

### Noise is log-normal, and the p99's is not the same as the others'

Per-trial noise is `base · exp(N(0,σ) − σ²/2)`: log-normal, not Gaussian. A throughput
cannot be negative, and the real distributions in M2.5 are right-skewed — most trials sit
near the mode with a slow tail. The `− σ²/2` term keeps the *mean* at `base` rather than
letting the exponential inflate it.

σ is a property of the machine (1.0 % for the server, 4.0 % for the noisy cloud instance),
scaled per metric: latency ×1.4, `disk_rand_write_iops` ×0.6, `disk_rand_read_p99_us`
×2.2. That mirrors M2.5 and M3.2: the same box is far more repeatable on a throughput
number than on a latency one.

`disk_rand_read_p99_us` also gets an injected stall — 4 % of trials multiplied by 1.6–4.0×
— and this is the one place where the verification does *not* match the model's σ, on
purpose. Measured CoV for that metric is **23–45 %** against the ~2–9 % its σ would
suggest. That is the point of the metric: a p99 exists to catch the stalls a mean hides,
so a p99 whose trial-to-trial variation looked like a throughput's would be a bad fixture
for the dashboard's tail-latency view. The verification states the number and the reason
rather than quietly excluding the metric.

Every other configuration checked matches within the 20 % tolerance the milestone asked
for (`docs/results/m5.2/spot_checks.log`):

| metric @4 threads | synthetic-01 | -02 | -03 | -04 | -05 |
|---|---:|---:|---:|---:|---:|
| profile σ | 1.0 % | 2.5 % | 4.0 % | 1.5 % | 3.5 % |
| `cpu_int_ops` CoV | 1.185 | 2.389 | 3.989 | 1.391 | 3.440 |
| `mem_read_bw` CoV | 1.044 | 2.478 | 3.433 | 1.401 | 3.463 |
| `mem_latency` CoV (σ×1.4) | 1.471 | 3.403 | 5.667 | 2.057 | 5.153 |
| `disk_rand_write_iops` CoV (σ×0.6) | 0.489 | 1.752 | 2.407 | 0.897 | 2.086 |

With n = 100 trials the sampling error of a CoV estimate is around 7 %, which is most of
the spread in that table.

### Determinism is per configuration, not per document

The obvious way to make a generator deterministic is one RNG consumed in document order.
It works, and it is brittle: adding a metric or changing `--trials` reshuffles every value
after the insertion point, so two seeded databases that should differ in one dimension
differ everywhere.

Instead each configuration gets its own generator, seeded from
`(seed, machine index, configuration index)`. `--trials 200` extends each configuration's
sequence rather than replacing it; adding a sixth machine leaves the first five untouched.
Run ids are derived the same way, so re-seeding a database stores the same runs rather
than a second copy of them — which is only useful because M5.1 made ingest idempotent per
row.

One honest caveat: the *timestamps* are relative to the day the generator runs (the
30-day window ends "today"), so two runs on different days produce different documents.
The file-level `cmp` check in `seed.log` is therefore a same-day check; the unit test pins
`Now` explicitly.

### The configuration set, and how it reaches 100,000 rows

225 configurations per machine:

| metrics | thread counts | working sets | configurations |
|---|---|---|---|
| 3 CPU | 1, 2, 4, 8, 16 | n/a (0) | 15 |
| 3 bandwidth | 1, 2, 4, 8, 16 | 32 KiB … 512 MiB (6) | 90 |
| 1 latency | 1, 2, 4, 8, 16 | 4 KiB … 1 GiB (9) | 45 |
| 5 disk | 1, 2, 4, 8, 16 (queue depth) | 1, 2, 4 GiB (3) | 75 |

× 100 trials × 5 machines = 112,500 rows, above the 100,000 floor with room to spare. The
command prints the exact number before generating and exits 1 below the floor unless
`--allow-small`, so "the seeder ran" and "the target is met" cannot be confused.

Thread counts above a machine's logical CPU count are **not** filtered out — 16 threads on
the 4-vCPU instance is a real thing to measure, and the model answers it with the
oversubscription penalty rather than with a missing row. The dashboard needs to be able to
draw that.

### Each machine is swept over six runs, not one

A real machine is not measured all at once, and a `runs` table with one row per machine
would make the run-level endpoints pointless. Each machine's 225 configurations are split
across 6 runs on different days, which is also what spreads the timestamps across the
30-day window: 30 runs, each on its own day.

### The seeder posts through the real API

`--post` sends each envelope to `POST /v1/runs` exactly as the engine does, chunking at
50,000 results. Nothing writes to Postgres behind the API's back, so the seed run is also
a test of ingest: 112,500 rows in **5.08 s end to end**, about 22,100 rows/s through
HTTP + JSON + `CopyFrom`, against the ~30,000 rows/s M5.1 measured for the database alone.

## Verification

```
$ go run ./cmd/seed --post http://localhost:8080
seed: 5 machines x 225 configurations x 100 trials = 112500 measurement rows
seed: generated 112500 rows in 30 runs in 28ms
seed: 112500 rows inserted, 112500 generated, total 5.077s
real 5.15 s

$ psql -c 'select count(*) from measurements'   ->  112510
```

| verify step | result |
|---|---|
| ≥ 100,000 measurements | **112,510** (112,500 synthetic + 10 real) |
| all 12 metrics present | yes, each for all 5 synthetic machines, with the right unit |
| CoV in SQL within 20 % of σ | yes for 20 of the 25 configurations checked; the five exceptions are all `disk_rand_read_p99_us`, whose injected stalls are the point |
| filters return the expected counts | 6 filters over HTTP, all equal to SQL; an integration test asserts the same against `SELECT count(*)` |
| same seed twice | identical files (`cmp`), and a unit test diffs two generations |

The generator's tests check shape rather than values:

- throughput never falls as threads are added, never scales above linear, and its
  per-doubling gain never *improves*;
- the 64-core server scales better at 16 threads than the 14-core laptop;
- latency is monotonic in working set and DRAM is ≥ 20× L1;
- DRAM bandwidth at 16 threads is under 8× its single-thread value (it saturates), and a
  write is slower than a read at a DRAM-sized set;
- random IOPS rise with queue depth with diminishing gains;
- every envelope passes the same `Validate` as engine output, and every machine is
  labelled synthetic.

### The M5.1 verify step that needed this data

M5.1 could not show its list query using the composite index, because every row in the
table then belonged to one machine and one metric. Over the seeded 112,510 rows
(`docs/results/m5.2/explain.log`):

```
Limit (actual time=0.045..0.068 rows=100 loops=1)
  Buffers: shared hit=12
  ->  Index Scan using measurements_filter_idx on measurements
        Index Cond: ((machine_id = '99603cdd…') AND (metric = 'mem_read_bw')
                     AND (workload = 'mem_bw') AND (thread_count = 4)
                     AND (working_set_bytes = 67108864))
Execution Time: 0.096 ms
```

Index Scan on the composite index, 12 buffers, 0.096 ms — and with a keyset cursor the
`id > 40000` predicate joins the same `Index Cond` rather than becoming a filter, which is
exactly why migration `0003` appended `id` to that index.

## What this milestone does not do

- **No aggregation endpoints.** The CoV table above was computed with `stddev_samp` in
  psql by hand; `/v1/aggregates` is M5.3.
- **No dashboard badge yet.** The data is labelled (`synthetic-NN`, `engine_version:
  "seed"`) but nothing consumes the label until M6.
- **`seed.json` is not committed.** 43 MB, and byte-identical on regeneration.
