# M2.1 — Worker pool with synchronized start

*Milestone notes, written for someone learning benchmark methodology. Measured on
2026-09-18 on a Core Ultra 9 185H laptop under WSL2 (22 Hyper-V vCPUs), release build,
plugged in. Raw runs and commands are in `docs/results/m2.1/`. Earlier notes: `M1.2.md`.*

## What was built

Until now every configuration ran on one thread. This milestone makes `--threads N` real:
the runner spawns N workers, starts them at the same instant, times the whole group, and
reports both the aggregate and each thread's own number.

1. **A worker pool per configuration** ([runner.cpp](../../engine/src/runner.cpp)). For
   `thread_count = N`, N `std::jthread`s are spawned. Each one optionally pins itself to a
   CPU, sets up its own workload object (allocating and first-touching its own memory on
   its own thread), signals a `std::latch` that it is ready, and then loops: wait at the
   start barrier, run whole batches until `trial_ms` has elapsed, record what it did, wait
   at the end barrier. Workers do not know how many trials there will be; the main thread
   tells them to stop through the `std::stop_token` at a trial boundary.
2. **Two barriers with completion functions.** The start barrier's completion function
   stamps `t_release`; the end barrier's stamps `t_done`. The main thread is a participant
   in both. **Aggregate throughput for a trial is Σ ops_i ÷ (t_done − t_release)**: all the
   work every worker did, divided by the wall time from the instant the last participant
   arrived at the start barrier to the instant the last worker finished.
3. **A per-worker result slot padded to 128 bytes** (`struct alignas(128) Slot`, with a
   `static_assert(sizeof(Slot) == 128)`). Each worker writes only its own slot, and only
   between the two barriers; the main thread reads them after the end barrier.
4. **Pinning** (`--pin`, `--cpus`). Default CPU order is stride 2 then the odd CPUs
   (0, 2, 4, …, 1, 3, 5, …) so the first N workers avoid hyperthread siblings on the
   common "sibling = cpu + 1" layout. Each worker samples `sched_getcpu()` at the start and
   end of every trial; mismatches are counted in `params.pin_violations`.
5. **Ctrl-C** sets an atomic flag from the signal handler; the main thread notices it at
   the next trial boundary, stops the workers, and the CLI still writes the results
   collected so far.
6. **Diagnostics per trial** in `params`: `start_spread_us` (latest minus earliest worker
   start), `release_to_first_start_us`, `per_thread_ops_per_s`, `per_thread_cpu`,
   `per_thread_start_us`, `pin_violations`, `warmups_run`.

Two things changed from the plan as written, both because of measurements described below:
`std::barrier` was replaced by a purpose-built spin barrier
([sync.hpp](../../engine/include/bench/sync.hpp)), and warmup gained a time floor
(`--warmup-ms`, default 500 ms) on top of the trial count.

## Each correctness decision, and why

### Why the timestamps are taken inside the barrier's completion function

The obvious way to get "when did the trial start" is to have thread 0 read the clock after
the barrier releases. But thread 0 might be descheduled right then and read the clock a
millisecond late, making every other thread look like it started early and the trial
look shorter than it was. A barrier's completion function runs in exactly one thread, the
last one to arrive, at the moment the phase completes. That thread is by definition
running right now. Its clock read is the release instant, independent of how quickly any
waiter resumes. The same logic makes `t_done` exact: the last worker to finish stamps it.

### Why aggregate = Σ ops ÷ (t_done − t_release), not the sum of per-thread rates

Each worker measures its own window and its own ops, so `ops_i / window_i` is that thread's
rate. Summing those rates would be the throughput of a machine where every thread was
running at full speed the whole time. If one thread started 5 ms late, that fiction
overstates what the machine delivered. Dividing total work by the wall time of the whole
group charges late starts and stragglers against the result, which is the honest number.
The per-thread rates are still recorded, and the test `Pool.AggregateIsSumOfThreadsOverWallTime`
checks that aggregate ≤ Σ rates always holds (a thread's window is a subset of the group's).

### Why the slot is 128 bytes and not 64

Each worker writes its slot during the trial. If two workers' slots shared a cache line, each
write would force the line to bounce between cores (false sharing). A cache line is 64 bytes,
but Intel's adjacent-line prefetcher pulls lines in pairs, so 128 bytes is the safe
distance. C++17 gives `std::hardware_destructive_interference_size` for this, but GCC warns
that its value is ABI-fragile, so the constant is written out.

The false-sharing test needed its own lesson. The first version had eight threads doing plain
relaxed stores to packed counters and saw **no** slowdown (0.84×, packed slightly faster).
Plain stores go into the store buffer and the core keeps running; a `load + store` loop is
served by store-to-load forwarding and never needs the cache line either. A locked
read-modify-write (`fetch_add`) must own the line at every iteration, and that showed the
effect at once: **14.4× slower packed than padded**. Real per-thread counters are usually
RMWs, so that is the pattern the test keeps.

### Why `std::barrier` was replaced

`std::barrier::arrive_and_wait` parks waiting threads on a futex. When the last thread
arrives, the kernel wakes the sleepers one at a time, and in a VM a sleeping vCPU may have
been parked by the hypervisor, so waking it means the host scheduler has to run first.
Measured with 8 threads, spread between the earliest and latest worker start, over 100
trials:

| variant | median | max |
|---|---|---|
| no barrier (threads stamp as soon as spawned) | 1220 µs | 3.1 ms |
| `std::barrier`, sleeping waits at both ends | 69 µs | 0.6 ms |
| `std::barrier` at start with spin-then-`wait(token)`, sleep at end | 43–129 µs | 3–11 ms |
| `SpinBarrier` at both ends | **0.10 µs** | 3.0 ms (one trial; see below) |

Three attempts were needed. Sleeping at both ends was the naive version. Spinning at the
start barrier but still calling `std::barrier::wait(token)` afterwards did not help, because
libstdc++'s wait path spins only ~16 iterations, then calls `sched_yield` four times, then
sleeps on the futex; any phase update that lands after those iterations sends the waiter to
sleep. Sleeping at the *end* barrier was equally bad: a worker asleep between trials has a
parked vCPU when the next trial is released. The fix that worked is a barrier whose waiters
never sleep: an arrival counter, a generation counter, and a completion callback run by the
last arriver. Workers spin with `PAUSE`; the main thread, whose wake-up latency affects no
measurement, polls with a 50 µs sleep so it does not burn a core.

Discarding the `std::barrier` token instead of waiting would have left a real race (a fast
worker could arrive for the next phase before the last arriver had stored the new phase), so
a purpose-built barrier was the right call. `std::latch` stayed where it fits: waiting for
every worker to finish setup before the first trial, where nothing is being timed.

### Why warmup has a time floor

Even with spinning barriers, the first trials of every configuration had spreads of 5–15 ms
and the rest were sub-microsecond. The spread time series over 100 trials made it obvious:
bad trials were indices 0–6, then almost nothing. Spawning 8 busy threads changes what the
hypervisor sees, and it takes roughly 250 ms for the vCPUs to settle onto physical cores.
Five 20 ms warmup trials did not cover that window. Warmup now runs until *both* the trial
count and `--warmup-ms` (default 500) are satisfied; the number actually run is recorded in
`params.warmups_run` (16–17 in the runs below). The three timing-tolerance unit tests that
compare runs were made to use the floor too, after they flaked for exactly this reason.

### Why workers loop until told to stop

Because warmup is now time-based, the main thread decides per trial whether it is warmup or
timed, and the workers cannot be given a trial count up front. So workers loop forever and
the main thread ends the loop by calling `request_stop()` on every worker *before* its own
arrival at the start barrier. Every worker checks the token *after* that barrier. The
barrier's happens-before guarantee means they all see the same answer, so nobody is left
waiting at a barrier that will never complete. Ctrl-C uses exactly the same path.

### Why pinning at full subscription is worse

At 22 threads on 22 vCPUs there is also the main thread, polling, plus whatever else the
guest runs. Pinned workers cannot move out of the way; unpinned ones can. The scaling data
shows it directly (below). Pinning is for reducing variance at moderate thread counts, not
for squeezing the last core.

## What the Verify steps showed

### Start synchronization

8 threads, 100 timed trials of 20 ms, default warmup (5 trials and 500 ms):

| | unpinned | pinned |
|---|---|---|
| warmup trials actually run | 16 | 17 |
| median spread | 0.51 µs | 0.33 µs |
| p95 spread | 161 µs | 105 µs |
| max spread | 2.0 ms | 0.77 ms |
| trials over 50 µs | 9 of 100 | 7 of 100 |
| release → first worker start (median) | 0.19 µs | 0.18 µs |

The plan's "< 50 µs" holds for the typical trial and for over 90% of trials. The residue is
scattered through the run (trial indices 12, 14, 24, 45, …), not clustered at the start, and
the late thread is a different one each time. That is the host preempting a vCPU, which the
guest cannot prevent. It is recorded per trial, so later milestones can report it rather
than average over it. The `--no-barrier` number the plan asked for is the "none" row of the
table in the previous section: 1220 µs median.

### False sharing

`tests/false_sharing_test`, 8 threads, 5M `fetch_add` each, best of 3: padded 30.7 ms,
packed 441.6 ms, **14.4×**. The plan expected ≥ 2× and asserts ≥ 1.3×.

### Pinning

`--pin --verbose` with 8 threads: CPU list `0 2 4 6 8 10 12 14`, `pin_failures 0`,
`pin_violations 0` across all trials, and `sched_getcpu()` at the start and end of every
trial equal to the assigned CPU. This proves guest-level pinning only; Hyper-V may still move
the vCPU between physical cores underneath.

### ThreadSanitizer

The `tsan` preset's 41 functional tests, a pinned 8-thread run, and a 22-thread run
interrupted by SIGINT all report no races. TSan found one real bug on the way: the first
version wrote `cpu_start` into the slot *before* the start barrier, while the main thread
could still be reading the previous trial's slots. Moving every slot write inside the
barrier-protected window fixed it.

Reading it: near-linear to 4 threads, then per-thread throughput falls as workers land on
E-core vCPUs and hyperthread siblings, and the total flattens around 33–35 Gops/s at 16
threads. Pinning lowers variance at 1 and 16 threads and is worse at 22 (oversubscribed,
see above). The single-thread number is 4.1 Gops/s, consistent with M1.2's estimate that the
kernel is near the `imul` throughput bound (about 11 cycles per 8-lane iteration at ~5 GHz).
The 10M ops/s target from the plan is exceeded by three orders of magnitude at any thread
count, and the formal check is M2.4's job.

## Five interview questions

**1. Eight threads each run a loop; you time from "spawn the first thread" to "join the
last". What is wrong with that as a throughput measurement?**
Thread creation takes tens to hundreds of microseconds each, so the last thread starts long
after the first, and the measured window includes time when only some threads were working.
Start them together with a barrier and stamp the release instant in the barrier's completion
function, which runs in the last arriver at the moment everyone is ready. Then divide total
work by the time from that instant to the last finish.

**2. Why would you ever write your own barrier when C++20 has `std::barrier`?**
`std::barrier` is correct, but its waiters sleep on a futex. Wake-up is sequential and, in a
VM, may require the hypervisor to un-park a vCPU: measured medians of tens of microseconds
to a millisecond. When the point of the barrier is that every thread starts within
microseconds, waiters must spin instead of sleep. A spinning barrier is 30 lines: an arrival
counter, a generation counter the last arriver bumps, and a callback. Keep the standard
type for cases where wake latency does not matter.

**3. What is false sharing, and why might a demo of it show nothing?**
Two threads writing different variables that happen to share a 64-byte cache line force the
line to bounce between cores; each write waits for ownership. A demo with plain stores can
show nothing because the store buffer absorbs the writes and the core moves on, and a
load-then-store loop is served by store-to-load forwarding. A locked read-modify-write
(`fetch_add`) has to own the line every time, which is why that demo shows a 10–15× penalty.
Pad per-thread data to 128 bytes, not 64, because the adjacent-line prefetcher pairs lines.

**4. Your pinned worker reports it stayed on CPU 6 for the whole trial. Does that mean it
ran on the same physical core?**
Only if you are on bare metal. Under a hypervisor, CPU 6 is a virtual CPU; the host is free
to run it on any physical core and to preempt it. Guest pinning still helps (it stops the
guest scheduler from migrating you and keeps a thread's cache state in one place from the
guest's point of view), but a run's residual multi-millisecond start delays on WSL2 came from
the host, and no guest-side setting removes them.

**5. Threads are stopped by a flag they check "between trials". How do you make sure no
thread is left waiting forever at a barrier?**
Everyone must make the same decision for the same trial. The coordinator sets the stop
request *before* it arrives at the start barrier, and workers check it *after* that barrier
returns. The barrier's completion establishes happens-before from the coordinator's write to
every worker's read, so either all of them break out or none do. Deciding the flag after
arriving, or checking it before the barrier, can split the group and deadlock the rest.
