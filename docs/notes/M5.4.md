# M5.4 — 1000 req/s at p95 ≤ 50 ms, and what the number is worth

*Milestone notes, written for someone learning to read a load test. Measured on
2026-09-21 on the Core Ultra 9 185H laptop (22 vCPUs) under WSL2, plugged in, Windows
power mode "Best performance" — the same machine state as every other number in this
repository. Postgres 16 and Redis 7 in compose with `synchronous_commit=on`; the database
holds the 112,513 rows M5.2 seeded. Raw summaries: `docs/results/m5.4/` and
`docs/results/k6_2026-09-21.json`. Earlier notes: `M5.1.md`, `M5.2.md`, `M5.3.md`.*

## Target #4, and the result

> **API ≥ 1000 req/s, p95 ≤ 50 ms** — k6 `constant-arrival-rate` at 1000 iter/s for 60 s
> against the seeded DB, `http_req_duration p(95) < 50`, error rate < 0.1 %.

| requirement | measured |
|---|---|
| p(95) < 50 ms | **1.17 ms** |
| ≥ 60,000 requests in 60 s | **60,001** |
| `dropped_iterations` = 0 | **0** |
| error rate < 0.1 % | **0.00 %** |

**Met, with a factor of 43 in hand on the latency.** Both halves of the run matrix pass:
(a) API native in WSL with Postgres and Redis in compose, k6 native — p95 1.17 ms; and
(b) API, Postgres, Redis and k6 all on the compose network — p95 1.12 ms.

A target passed by that margin is a weak measurement on its own. Most of this milestone is
therefore about the runs that make the number mean something: what happens with the cache
off, with writes underneath, with a smaller pool, and at rates where something finally
bends.

## What was built

1. **`loadtest/read_heavy.js`** — `constant-arrival-rate`, 1000/s for 60 s, with a 10-second
   warmup scenario in front of it and the thresholds scoped to the measured window.
2. **`loadtest/ingest.js`** — 50 POSTs/s of 100-result envelopes, each with a fresh
   `run_id`.
3. **`loadtest/mixed.js`** — both at once, which is the only profile where the cache is
   being invalidated while it is being read.
4. **`loadtest/lib.js`** — `setup()` fetches the machine inventory from the API and builds
   the combinations the request mix draws from.
5. **`make load` / `load-mixed` / `load-compose`**, and `api/loadtest/summarize.py`, which
   builds the results table out of the committed `--summary-export` files.

## Each decision, and why

### `constant-arrival-rate`, and `dropped_iterations` as the proof

The pitfall the plan names first is using `constant-vus`. With 50 VUs looping, the
*offered* load is a consequence of the response time: if the API slows down, the test
slows down with it, the p95 stays flat, and the throughput number silently becomes
"whatever the server felt like doing". `constant-arrival-rate` holds the arrival rate
fixed and adds VUs to keep it, which is what "1000 requests per second" means.

That makes **`dropped_iterations` the most important counter in the summary**. It is k6
saying "I could not start a request on schedule" — so a run with dropped iterations
measured a *smaller* load than it claims, and its latency numbers describe that smaller
load. It is a threshold (`count==0`) rather than a footnote for that reason.

It earned its place immediately. The first 2000/s run reported 47 dropped iterations, and
the obvious reading — "the API cannot take 2000/s" — was wrong:

| run | p95 | dropped |
|---|---:|---:|
| 2000/s, `preAllocatedVUs: 100` | 1.10 ms | **47** |
| 2000/s, `preAllocatedVUs: 400` | 1.13 ms | **0** |

Identical latency, drops gone. The drops were k6 initializing VUs at the start of the
scenario, not the server. The fix was a load-generator setting; the lesson is that a
number produced by a tool under load is also a measurement of the tool.

### The 10-second warmup, and why the thresholds ignore it

At t=0 Redis is empty, Postgres's buffer cache is cold, and the Go runtime has not grown
its heap. Judging a p95 over that window measures the first ten seconds of a process's
life, which is not what the target is about. The profile runs a `warmup` scenario at a
fifth of the rate for 10 s, then `measured` at the full rate, and every threshold is
scoped to `{scenario:measured}`. The warmup's own latencies are still reported — excluded
from the judgement, not from the record.

The `measured` and `all reqs` columns in the results table exist for the same reason: the
top-line `http_reqs` of 62,003 includes the warmup's 2,002, and the 60,001 that the target
is about is the measured window alone.

### The request mix is built from data that exists

`setup()` calls `GET /v1/machines` and builds the (machine, metric, workload, working set)
combinations from the real inventory, failing loudly if there are fewer than two machines.
A load test that invents ids measures the latency of a 404 — a code path with no database
work in it at all, which would make the result look excellent and mean nothing.

The mix is 60 % aggregates, 20 % compare, 15 % measurements, 5 % trials: aggregate-heavy,
because that is what a dashboard page does.

### The cache's contribution, measured rather than assumed

| | p50 | p95 | cache hit rate |
|---|---:|---:|---:|
| cache on | 0.38 ms | **1.17 ms** | 95.9 % |
| cache off (`REDIS_URL=`) | 0.81 ms | **3.46 ms** | — |

Redis is worth **3× on the p95** at this rate, and the target is met with a factor of 14
in hand *without it*. That is the useful form of the answer: the cache is an optimization
the system does not depend on, which is exactly what M5.3 claimed and this is the
measurement that supports it.

Turning it off required a small change. `REDIS_URL=""` did not disable the cache, because
the config helper treated an empty value as "unset" and fell back to the default. An
explicitly empty variable now means "no cache" (`os.LookupEnv`), which is also the honest
reading: the operator said something, and it was "nothing".

### Writes underneath reads: the mixed profile

The read-only profile measures a cache that is only ever filled. The mixed profile runs
50 ingests/s of 100 rows each *while* the reads happen, and each ingest evicts the cache
for the machine it wrote to (M5.3).

| | p50 | p95 | max | cache hit rate |
|---|---:|---:|---:|---:|
| reads only | 0.38 ms | 1.17 ms | 54 ms | 95.9 % |
| reads + 5,000 rows/s of ingest | 0.43 ms | **2.17 ms** | 161 ms | **80.8 %** |

The hit rate falls from 95.9 % to 80.8 % and the p95 not quite doubles — still 23× inside
the target, with zero errors and zero drops while the table grows by **300,000 rows** in
60 seconds. The `max` of 161 ms is the honest cost: some request waited behind a
`CopyFrom` transaction.

Those 300,000 rows were then deleted (they are tagged `engine_version: "loadtest"`), but
not before one more run against the enlarged 412,513-row table: p95 **1.30 ms**, against
1.17 ms at 112,513 rows. Nearly 4× the data for 11 % more latency — which is what the
composite index from M5.1 is for.

### The pool sweep only matters once the cache is out of the way

The plan asks for `PG_MAX_CONNS` at 10/20/40. Swept at 1000 and 2000 req/s, the three
sizes were indistinguishable — at a 96 % cache hit rate, Postgres sees ~80 queries a
second and the pool is never contended. Sweeping a knob at a load that cannot exercise it
produces three numbers and no information.

Repeated with the cache **off** and the rate at 6000/s, so that every request is a query:

| `PG_MAX_CONNS` | p50 | p95 |
|---:|---:|---:|
| 10 | 3.97 ms | **41.49 ms** |
| 20 | 1.53 ms | 10.49 ms |
| 40 | 1.48 ms | **9.17 ms** |
| 80 | 1.45 ms | 8.34 ms |

Ten connections is **4.5× worse at the p95** and within 20 % of failing the target
outright, with a p50 that is barely affected — the classic signature of queueing, where
the median request finds a free connection and the tail waits for one. Past 40 the returns
are small, and the `max` column in `summary.txt` gets *worse* (190 ms at 40, 347 ms at 80),
which is Postgres doing more context switching for no throughput.

The default of 20 is a reasonable place to be: it is past the cliff, short of the churn,
and this is the measurement that says so rather than the folklore that usually picks it.

### Finding the knee, and finding k6 instead

| rate | achieved | p95 | dropped |
|---:|---:|---:|---:|
| 1000/s | 1000/s | 1.17 ms | 0 |
| 2000/s | 2000/s | 1.13 ms | 0 |
| 3000/s | 3000/s | 1.09 ms | 26 |
| 5000/s | 5000/s | 1.15 ms | 0 |
| 8000/s | ~7900/s | 1.49 ms | 419 |
| 12000/s | ~10,000/s | 2.36 ms | 602–1072 |

There is no latency knee in this range. What appears instead is the load generator giving
up: at 12,000/s the request rate falls short of the target and the drops climb, while the
p95 is still 2.36 ms. The CPU sample says why (`docs/results/m5.4/cpu.log`, 5-second
windows from `/proc`, where 100 % is one of 22 vCPUs):

| | 1000 req/s | 12,000 req/s |
|---|---:|---:|
| k6 | 37 % | **360 %** |
| api | 30 % | 320 % |
| postgres | 8 % | 110 % |
| redis | 4 % | 36 % |

**k6 is the single largest consumer at the high rate.** The load generator, the API, the
database and the cache are all on the same 22 vCPUs, so past ~5000/s the test is measuring
a machine competing with itself. The reported numbers are conservative for that reason,
and the honest statement of the ceiling is "at least 5000 req/s at a p95 of 1.15 ms, on a
laptop that is also generating the load" — not a number for the API in isolation.

This is the same lesson as M4.1's fio comparison in a new place: when the measurement
tool shares the resource under test, the tool is part of the system.

### The two-variant matrix, and why it changed nothing

The plan's variant (b) exists because Docker Desktop publishes container ports through a
proxy, which adds latency between WSL and the compose services. Variant (a) has that proxy
on the API→Postgres and API→Redis hops; variant (b) puts everything on the compose network
so there is none.

(b) was run by building a static `CGO_ENABLED=0` binary, bind-mounting it into an
`alpine` container on `benchmark-platform_default`, and running the official `grafana/k6`
image in the same network. p95 **1.12 ms** against (a)'s 1.17 ms, and a much lower `max`
(21 ms against 54 ms). The proxy is not free, but at these latencies it is inside the
noise of everything else. Both variants pass, so (a) is the headline and (b) confirms it.

That container is a stand-in, not the deployment: the real `api` service and its
Dockerfile belong to M1.6 and M7.1. When those exist this variant becomes
`docker compose up api` plus `make load-compose`, which is why the Makefile target is
written that way already.

### Why `synchronous_commit` stayed on

M5.1 added `deploy/.env.loadtest.example`, which turns it off. It was not used: M5.1 also
measured that turning it off changed a 50,000-row ingest by 0.03 s out of 2.05 s, and the
read-heavy profile does not write at all. Publishing a load-test number taken under
relaxed durability, when durability was not the constraint, would be dressing the result
up. The profile that does write — mixed — also ran with it on.

## Verification

```
$ make load
     ✓ http_req_duration{scenario:measured} p(95)=1.16ms < 50
     ✓ http_req_failed{scenario:measured}   rate=0.00%   < 0.001
     ✓ dropped_iterations                   count=0      == 0
     ✓ checks                               rate=100.00% > 0.999
     60,001 requests in the 60 s measured window
```

All fifteen runs are in `docs/results/m5.4/summary.txt`, generated from the committed
`--summary-export` files by `api/loadtest/summarize.py`, so the table and the runs cannot
disagree.

One verify step could not be completed as written: **the `/metrics` snapshot**. `make load`
is supposed to save it next to the k6 JSON, and there is no `/metrics` endpoint until
M5.5. The target saves the `/readyz` snapshot instead and says so in its own output; the
Prometheus snapshot and the pprof capture arrive with M5.5.

## What this milestone does not do

- **No `/metrics`, no pprof profile.** M5.5, which is also where the plan asks for the
  top-3 hot spots under load.
- **No sustained soak.** The longest run here is 70 seconds. Thermal drift on this laptop
  takes minutes to show (M2.5), so a p95 from a one-minute window is not a claim about an
  hour.
- **No remote client.** Everything is loopback; there is no network between the client and
  the API, and a real deployment would have one.
