# M3.2 — Cache latency: the pointer chase

*Milestone notes, written for someone learning benchmark methodology. Measured on
2026-09-21 on a Core Ultra 9 185H laptop under WSL2, release build, **plugged in**, Windows
power plan "Balanced", power mode **"Best performance"** ("Max Performance Overlay"),
battery 100 % and charging, Docker containers stopped. Power state was recorded before and
after every run; the logs are in `docs/results/m3.2/`. Earlier notes: `M1.2.md`, `M2.1.md`,
`M2.2.md`, `M2.3.md`, `M2.4.md`, `M2.5.md`, `M3.1.md`.*

## The problem this milestone solves

M3.1 measured how many bytes per second the machine can move. This one measures how long
**one** access takes, and the two answers are not two views of the same thing.

A streaming read is the best case the memory system ever sees: the addresses are known in
advance, so the prefetcher fetches ahead, dozens of loads are in flight at once, and the
cost of any single one is hidden behind the others. Real programs chasing a linked list, a
tree or a hash table get none of that. The address of the next access is *in* the data you
just fetched, so nothing can start until the previous load finishes.

The pointer chase measures that second case, and it is the chart that makes a cache
hierarchy visible. On a 256 MiB working set this milestone measures **163 ns per dependent
load**, while M3.1's streaming read over the same 256 MiB moves a 64-byte line every
**2.8 ns** (22.9 GB/s). A factor of **59**, on the same memory, on the same machine.
Neither number is wrong; they answer different questions, which is why both metrics exist.

## What was built

1. **`mem_latency`** — a random cyclic pointer chase over `working_set_bytes`, one pointer
   per 64-byte line, built with Sattolo's algorithm. `value` is nanoseconds per dependent
   load.
2. **`thp_policy()`** — read the kernel's transparent-huge-page policy from
   `/sys/kernel/mm/transparent_hugepage/enabled` and record it in `params`.
3. **A fix to huge-page reporting**: `alloc_buffer` now measures the huge-page grant for
   *every* large buffer, not only the ones that asked for it, because under a THP policy of
   `always` the kernel backs a big mapping with huge pages whether or not it was advised —
   and `params.huge_pages` would have read `false` on a run whose pages were huge.
4. **`params.buffer_huge_page_bytes` / `buffer_huge_pages`** — the *chase buffer's* own
   huge-page grant, reported separately from `params.huge_pages`, which describes the
   cold-prep scratch buffer. For this workload the buffer is the whole measurement.
5. **A correction to how a latency value is formed**, described below.
6. **17 new tests** (`mem_latency_test.cpp`, plus two `perf` ratio tests). 152/152 pass in
   release, debug, ci, asan and tsan.

## Two things that would have silently produced a wrong number

### Sattolo's algorithm, not Fisher–Yates

The chase has to visit **every line of the working set, exactly once per lap**. If it does
not, it spends its time in a subset; that subset fits in a smaller cache than the one being
measured; and the metric reports a number that is wrong by a factor of thirty while looking
entirely reasonable.

Fisher–Yates produces a uniformly random permutation. A uniformly random permutation of *n*
elements decomposes into about **ln(n)** disjoint cycles — measured over 200 seeds at 4096
elements, a mean of **8.8 cycles** against ln(4096) = 8.3 — and a chase started anywhere
falls into one and stays there forever. A "256 KiB working set" whose chase is trapped in a
30 KiB cycle reports L1 latency.

Sattolo's algorithm is Fisher–Yates with one character changed: the random index is drawn
from `[0, i)` rather than `[0, i]`. That one character makes every permutation it produces a
single *n*-cycle, by construction. The test suite asserts it directly (no fixed points,
exactly one cycle, for six sizes × eight seeds) and also measures the contrast: over 200
seeds, **0 of 200** Fisher–Yates shuffles of 4096 elements came out as a single cycle.

The chase is then verified in memory as well as in the permutation: following `next_line`
from line 0 for *n* steps visits *n* distinct lines and closes back on 0.

### A latency is per thread; a rate is per machine

The runner sums work units across threads and divides by wall time. That is right for every
throughput metric and **wrong for a latency**. Eight threads each performing 1000 dependent
loads in 100 µs did 8000 loads and took 100 ns per load *each*. Dividing 100 µs by 8000
gives 12.5 ns — a "latency" that falls as you add threads, which is the opposite of what
loaded latency does.

So `value_from_units` takes the thread count, and the `ns_per_unit` rule divides by the
per-thread count. Nothing else uses it: summing across threads is exactly what a rate
wants. There is a test whose only job is to fail if someone removes the argument.

## The kernel is one instruction

```
40:  sub    $0x1,%rax
44:  mov    (%rcx,%rdx,8),%rdx     <- the operation
48:  jne    40
```

`idx = words[idx]`. x86 addresses as base + index × 8, so the index arithmetic is free, and
the loaded value **is** the next address. There is nothing between two loads for the machine
to overlap them with. No unrolling (pointless — the loop is one dependent load deep), no
vectorization (impossible — the addresses are not known in advance). Full disassembly:
`docs/results/m3.2/disasm_mem_latency.log`.

### A deviation from PLAN.md: 64 Ki loads per batch, not 1 Mi

The trial loop runs whole batches and can only overshoot a trial's time budget, never cut a
batch short. A DRAM-resident load costs ~160 ns here, so PLAN.md's 1 Mi-load batch would
take **160 ms** — more than three times the default 50 ms trial, making every DRAM trial a
single batch of the wrong length.

64 Ki keeps the worst-case batch at ~10 ms (a fifth of a trial), while an L1-resident batch
is still ~65 µs, four thousand times the cost of the one clock read that brackets it.

## Verify 1 — the working-set sweep

Five independent passes, each 10 trials of 30 ms, warm (`--cold none`), 1 thread. Medians
of the five pass medians. Full table with every pass: `docs/results/m3.2/analysis.md`.

| working set | ns/load | pass spread (max/min) | region |
|---|---:|---:|---|
| 4 KiB | 1.02 | 1.0× | L1d |
| 16 KiB | 1.07 | 1.0× | L1d |
| 32 KiB | 1.05 | 1.1× | L1d |
| **48 KiB** | **1.10** | 1.1× | L1d, exactly at capacity |
| **64 KiB** | **3.25** | 1.1× | **L2** — the step |
| 128 KiB | 3.27 | 1.1× | L2 |
| 512 KiB | 3.87 | 1.1× | L2 |
| 1 MiB | 4.36 | 1.1× | L2 |
| **2 MiB** | **6.07** | 1.4× | L2, at capacity |
| 4 MiB | 15.33 | 1.3× | L3 |
| 8 MiB | 46.01 | **3.8×** | L3 — see below |
| 16 MiB | 118.82 | 1.6× | L3 / DRAM |
| 24 MiB | 146.40 | 1.1× | DRAM |
| 32 MiB | 155.21 | 1.0× | DRAM |
| 64 MiB | 157.32 | 1.0× | DRAM |
| 256 MiB | 163.46 | 1.0× | DRAM |
| 1 GiB | 175.78 | 1.0× | DRAM |

**The L1 step lands exactly on the cache size.** 48 KiB reads 1.10 ns; 64 KiB reads
3.25 ns. `bench sysinfo` says L1d is 48 KiB, and the sweep includes 48 KiB precisely so the
boundary can be put between two adjacent points rather than inferred. That is the cleanest
result in the milestone: a 3× step at a size nobody told the benchmark about.

**1.02 ns at 4 KiB is an L1 hit, and the number is checkable.** M2.4 measured this core at
about 4.83 GHz, so 1.02 ns is 4.9 cycles — the textbook L1d load-to-use latency on this
family is 5 cycles. The chase is measuring what it claims to measure.

**The L2 plateau is not flat, and that is real.** 3.25 ns at 64 KiB rising to 6.07 ns at
2 MiB. L2 on this part is 2 MiB, so the far end of the plateau is at capacity and some
accesses already miss. The rise is gradual because a random chase over a working set near
capacity misses a growing fraction of the time, not all at once.

**The L3 "plateau" does not exist.** This is the milestone's most interesting negative
result. Between 4 MiB and 24 MiB — all of it inside a 24 MiB L3 — latency climbs from 15 to
146 ns, a factor of 10, with no flat region anywhere. The chase is not getting a 24 MiB
cache. It is getting a fraction of one, and the fraction shrinks as the working set grows.

Two things explain it, and both are consequences of the environment rather than the method:
L3 is shared with everything else on the package **and, under WSL2, with whatever the
Windows host is doing**; and this is a hybrid part where the path from a core to the ring
L3 is not the same for every core type.

**The 8 MiB point is bimodal, with a 3.8× spread across passes.** Measured over eight
separate single-point runs before the sweep was written:

```
17.0  17.2  18.6  19.3  29.0  35.9  107.5  129.9    ns/load
```

Two clusters, about 18 ns and about 120 ns, with nothing much in between — not a
distribution with a wide tail, but two different machines. The same vCPU id produced both
(vCPU 20 gave 19.3 in one run and 107.5 in another), so it is not the vCPU. It is what
`CLAUDE.md` warns about and M2.1 and M2.3 both measured: **under WSL2, pinning a thread to a
vCPU does not determine which physical core runs it**, and on a 6 P-core + 8 E-core + 2 LP
E-core part the core types do not share a path to the last-level cache. 18 ns is a core
with L3; 120 ns is a core going to memory.

This is why the sweep is run five times in five separate processes rather than once. One
pass reports whichever core it happened to land on. Five report the distribution, and the
`max/min` column above is part of the result rather than an embarrassment hidden by
averaging.

It is also why the `perf` test suite asserts the L1-vs-DRAM ratio (150× measured, 10×
asserted) and deliberately **does not** assert the L2→L3 step. A test that asserted
"8 MiB is faster than DRAM" would fail about a quarter of the time on a correct engine. A
fact that cannot be asserted belongs in the notes, not in a flaky test.

### DRAM is 146–176 ns, not PLAN.md's 90–110

PLAN.md predicted "~90–110 ns on this laptop". Measured: **146 ns at 24 MiB rising to
176 ns at 1 GiB**, with pass-to-pass spread of 1.0× — these are the most repeatable points
in the whole sweep, so the gap is not noise.

Two contributions, both identifiable:

- **The VM.** M2.3 measured cold-DRAM latency for a *flushed 256 KiB* chase at 105 ns
  median, but with a run-to-run range of 49–217 ns. The 90–110 figure came from the good
  end of that range. A steady-state chase over a large working set is a harder case than
  refilling a small flushed one, and the extra is real.
- **The working set itself.** Latency keeps climbing *after* every cache is exhausted:
  146 ns at 24 MiB, 176 ns at 1 GiB, a further **+20 %** over a span where nothing about the
  cache hierarchy changes.

That last one is worth pinning down, because the obvious explanation is wrong. It is not
the TLB: the huge-page grant is measured, and every point from 2 MiB up got **100 % of its
buffer in huge pages** (a 1 GiB chase is 512 huge pages, which the TLB holds). What is left
is DRAM itself — a random access pattern spread over a wider address span hits an open DRAM
row less often and conflicts across banks more. The memory is not slower; the accesses are
worse.

## Verify 2 — `--no-hugepages`, and a prediction that mostly held

Three alternating pairs, so any drift lands on both sides. Medians of the three:

| working set | huge pages | 4 KiB pages | penalty |
|---|---:|---:|---:|
| 8 MiB | 84.1 | 74.0 | −12 % |
| 64 MiB | 157.7 | 169.3 | **+7 %** |
| 256 MiB | 164.6 | 184.3 | **+12 %** |
| 1 GiB | 195.6 | 215.3 | **+10 %** |

PLAN.md predicted "the ≥ 64 MiB points rise noticeably". They rise, by **7–12 %**, in all
three cases and with a consistent sign. The prediction holds in direction, and the size is
smaller than "noticeably" suggests.

Why it is only 10 %: a 1 GiB chase over 4 KiB pages misses the TLB on essentially every
load, but a page walk is four memory accesses that are themselves cached in the paging
structure caches, and it can overlap with the load that triggered it. Against a 195 ns DRAM
access, adding a mostly-cached page walk is a 10 % tax rather than a doubling. The huge-page
path is worth having — and, more to the point, worth *knowing about*, because without
`params.buffer_huge_page_bytes` there would be no way to tell a run where it worked from a
run where it did not.

The 8 MiB row goes the wrong way and means nothing: it is the bimodal point, and both of its
numbers (84.1 and 74.0) are averages over passes that landed on different core types. It is
in the table because deleting an inconvenient row is how tables start lying.

## Verify 3 — CoV at 1 MiB, and a PLAN prediction that did not hold

200 trials of 50 ms at a 1 MiB working set, pinned. **This is not the Target #2
measurement** — that needs ≥ 1000 trials and belongs to M3.3, which is out of scope for this
milestone. It is recorded because M3.2's Verify block asks for it.

| cold mode | median | mean | CoV | MAD/median | min | max | trials > 2× median |
|---|---:|---:|---:|---:|---:|---:|---:|
| `--cold clflush` | 5.04 ns | 5.47 | **33.97 %** | 5.20 % | 4.55 | 19.81 | 4 of 200 |
| `--cold none` | 4.26 ns | 4.39 | **8.59 %** | 2.94 % | 4.07 | 7.02 | 0 of 200 |

**PLAN.md's M3.3 expectation is that cold mode *reduces* CoV for working sets ≤ L3**, on the
grounds that every trial then starts from the same state instead of inheriting the previous
trial's residue. Measured here, at 1 MiB, cold mode makes CoV **four times worse**.

The shape says what happened. MAD/median is 5.2 % against a CoV of 34 %: the bulk of the
distribution is tight and four trials out of 200 are 4× the median. That is a heavy tail,
not a wider spread. The cold path does two things the warm path does not — it issues 16384
`CLFLUSHOPT`s (measured at 36 µs per trial) and it leaves the first lap of the chase to be
served from memory — and both are opportunities for a preemption or an eviction to land
somewhere that costs milliseconds rather than microseconds.

This is a preliminary 200-trial result at one working set, so it is not a refutation of the
M3.3 hypothesis; it is a reason to expect the hypothesis to need qualifying when M3.3 is
run. Recorded rather than smoothed over.

## What cold mode does to a chase, which is not what it does to a bandwidth kernel

| working set | `--cold none` | `--cold clflush` | ratio | `params.cold` |
|---|---:|---:|---:|---|
| 256 KiB | 3.28 | 3.27 | 1.00× | `clflush` |
| 1 MiB | 4.42 | 4.69 | 1.06× | `clflush` |
| **8 MiB** | **17.79** | **117.88** | **6.62×** | `clflush` |
| 64 MiB | 156.42 | 156.29 | 1.00× | `n/a` |

M3.1 found cold mode worth well under a percent for bandwidth: a 50 ms trial makes
thousands of passes and only the first is cold. The same arithmetic explains this table,
and it explains why the answer here is completely different.

What matters is **how many laps a trial completes**. At 256 KiB the chase laps 4096 lines
every 13 µs, so a 30 ms trial does over 2000 laps and the one cold lap is invisible. At
8 MiB the chase has 131072 lines and a *cold* lap costs 131072 × ~120 ns = 16 ms — more than
half the trial. The trial does not get past its first lap, so `--cold clflush` at 8 MiB does
not measure "L3 latency starting cold"; it measures **cold-miss latency**, full stop.

At 64 MiB the working set exceeds L3, `ColdPrep` correctly records `n/a` rather than
flushing 64 MiB to cool nothing (M2.3's rule), and warm and cold agree to 0.1 %.

The general rule, which belongs in `docs/methodology.md` and is now there: **`--cold` on a
latency chase is only interpretable when the trial is long enough to complete many laps.**
Otherwise the cold lap is not a transient, it is the measurement.

## An artifact worth recording: the wall clock went backwards

One run during development reported `started_at` 16:42:24 and `finished_at` 16:48:11 — five
minutes and 47 seconds — for work that the next identical run did in 1.7 seconds. The
following run's timestamps were *earlier* than the "finished" time of the one before.

Nothing was slow. `started_at` and `finished_at` come from `system_clock`, which WSL2
resynchronizes against the Windows host and which can therefore jump forwards or backwards.
Every actual measurement uses `steady_clock` (`duration_ns` per trial, the barrier stamps),
and those were all correct: 30–39 ms per trial, as configured.

This is exactly the failure the project's "timing uses `steady_clock` only" rule exists to
prevent, observed in the wild. The envelope timestamps are metadata for ordering runs, not
measurements, and `duration_ns` is the thing to trust. Worth knowing before someone computes
a throughput from `finished_at − started_at`.

## What is not established here

- **No Target #2 claim.** The 1 MiB CoV above is 200 trials at one configuration. The
  ≥ 1000-trial variance study for the memory metrics is M3.3.
- **The L3 latency of this machine.** The 4–24 MiB region is bimodal and environment-bound;
  what is established is the *distribution*, not a number.
- **Loaded latency.** `--threads N` is implemented and the per-thread arithmetic is correct
  and tested, but no multi-thread sweep was run for this milestone. PLAN.md asks only that
  it be labelled as loaded latency, which it is.
- **These are virtual-machine numbers**, with the hybrid topology hidden from the guest.
