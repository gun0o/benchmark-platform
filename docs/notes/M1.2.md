# M1.2 — Measurement fundamentals (single thread)

*Milestone notes, written for someone learning benchmark methodology. Everything measured
here was measured on 2026-09-18 on a Core Ultra 9 185H laptop under WSL2, release build
(`-O3 -march=native`), plugged in. Raw run files and the exact commands are in
`docs/results/m1.2/`.*

## What was built

Before this milestone the engine could produce a well-formed JSON document, but the number
inside it was not trustworthy: one batch of work, timed once, on a cold core. M1.2 adds the
four things that make a single-threaded throughput number believable.

1. **A sink the optimizer cannot see through** (`DoNotOptimize`, `ClobberMemory` in
   [timing.hpp](../../engine/include/bench/timing.hpp)). The benchmark kernel's result is
   passed through an empty `asm volatile` statement that claims to read and modify it. The
   compiler must therefore compute it, so the loop cannot be deleted.
2. **A clock we trust** (`Timer`, `clock_resolution_ns`, `clock_selftest`). All timing uses
   `std::chrono::steady_clock`. At startup the engine measures how long a `now()` call takes
   and refuses to stay silent if it is slow.
3. **Warmup and a frequency ramp.** Each configuration runs `--warmup` trials (default 5)
   that are executed exactly like real trials but never written out, and the whole run starts
   with a `--spin-ms` busy loop (default 500 ms) so the core has left its idle frequency
   before anything is measured.
4. **Time-boxed trials.** A trial is not "N iterations"; it is "keep running whole batches of
   1 Mi operations until `--trial-ms` (default 50 ms) has elapsed". The reported value is
   `ops_done / elapsed_seconds`, and the clock is read once per batch, never inside the
   kernel loop.

The `cpu_int` kernel itself ([cpu_int.cpp](../../engine/src/workloads/cpu_int.cpp)) is now
final: 8 independent 64-bit lanes, each doing `acc = acc * K + ((acc >> 17) ^ i)` per
operation, with `K` and the starting lane values drawn from a random generator seeded at
runtime.

## Each correctness decision, and why

### Why an empty `asm volatile` instead of printing the result or using `volatile`

An optimizing compiler deletes work whose result is never used. Three common ways to keep
the result "used" all have problems:

- **Print it.** The print itself costs microseconds and does I/O, which pollutes the timing.
- **Store to a `volatile` variable.** Forces a memory store every time, and `volatile` semantics
  are broader than needed; it also does not stop the compiler hoisting the *inputs* out of
  the loop.
- **`asm volatile("" : "+m,r"(v) : : "memory")`.** Zero instructions are emitted. The
  constraint tells the compiler "this statement reads `v` and may write it, and may touch any
  memory". The compiler must materialize `v` before it and cannot assume anything about it
  after. This is what Google Benchmark does.

A detail that cost real time: the constraint order matters with GCC. `"+r,m"` (register first)
fails with "impossible constraint in asm" when the value is a compile-time constant such as
`int i = 1`, while `"+m,r"` works. Values larger than a pointer (a 64-byte struct, say) cannot
be in a register at all, so `DoNotOptimize` uses `if constexpr` to pick `"+m"` only for those.

The sink alone is not enough. If the kernel's inputs were literals, the compiler could
precompute the whole loop at build time and hand the sink a constant. That is why `K` and the
lane seeds come from `std::mt19937_64` seeded from the `--seed` flag at runtime.

### Why `steady_clock` and not `high_resolution_clock`

On libstdc++, `high_resolution_clock` is just an alias for `system_clock`, which is wall-clock
time. NTP adjustments, a user changing the clock, or WSL2 resyncing with Windows after sleep
can make it jump forwards or backwards. `steady_clock` is `CLOCK_MONOTONIC`: it only moves
forward and at a constant rate. A test in [timing_test.cpp](../../engine/tests/timing_test.cpp)
checks that `steady_clock::now()` and `clock_gettime(CLOCK_MONOTONIC)` agree.

### Why a clock self-test

A `steady_clock::now()` call is normally ~30 ns on Linux because the kernel exposes the TSC
through the vDSO and no system call happens. If the clocksource is something slow (a VM
without a stable TSC, for example), every `now()` becomes a real syscall costing hundreds of
nanoseconds, and worse, it serializes the CPU pipeline. The self-test calls `now()` 100,000
times back to back, checks it never went backwards, and requires the mean gap to be at most
100 ns. On this machine the resolution is 1 ns and the mean call is 33 ns.

The self-test found a second use during verification, described below.

### Why warmup trials and a spin

A core sitting idle runs at a low frequency and takes milliseconds to tens of milliseconds
to reach turbo. Caches, branch predictors and the TLB are also cold. Anything measured in
that window is lower than the steady state. Warmup trials are the simplest fix: run the exact
same trial a few times and throw the numbers away. The 500 ms spin covers the first
configuration's ramp before even the warmup trials begin.

### Why time-boxed trials with batches

Two alternatives were rejected:

- **Fixed iteration count.** A count that takes 50 ms on this laptop takes 10 ms on a desktop
  and 500 ms on a slow ARM board. Trial duration matters for variance (M2.5), so it should be
  the thing that is held constant.
- **Read the clock every iteration.** A clock read costs ~30 ns and acts as a pipeline
  barrier. With a 0.5 ns operation, that would make the benchmark measure the clock.

So a trial runs whole batches (131,072 iterations × 8 lanes = 1,048,576 ops) and reads the
clock between batches. The trial overshoots `trial_ms` by at most one batch, about 0.5 ms
here. `ops_done` is always a whole number of batches, which the runner test asserts.

### Why 8 lanes

A 64-bit `imul` has a latency of 3 cycles but a throughput of 1 per cycle. A single
accumulator would wait for each multiply before starting the next, measuring latency. Eight
independent accumulators let the out-of-order core overlap them, measuring throughput, which
is what "operations per second" is supposed to mean.

## What the Verify steps showed

### 1. The loop is really there (`objdump`)

The hot loop of `CpuIntWorkload::run_batch` in the release binary contains exactly the source
operations, repeated for 8 lanes, plus the counter (the `cmp $0x20000` is 131,072, the batch
iteration count):

```
bdc2b:  imul   %rdx,%rsi      ; acc * K
bdc2f:  shr    $0x11,%r12     ; acc >> 17
bdc33:  xor    %rax,%r12      ; ^ i
bdc36:  add    %r12,%rsi      ; +
        ... (same four instructions for the other 7 lanes) ...
bdcb0:  add    $0x1,%rax
bdcb4:  cmp    $0x20000,%rax
bdcba:  jne    bdc28
```

Two things worth noticing. There is no vector code in the loop: AVX2 has no 64-bit
multiply, so GCC kept it scalar. And each lane lives in its own register (`rsi`, `rbx`,
`r11`, `r10`, `rcx`, `r9`, `r8`, `rdi`), which is what makes the 8-lane overlap possible.

### 2. Doubling the trial length doubles the work at the same rate

| `--trial-ms` | mean ops per trial | mean ops/s | mean duration | batches |
|---|---|---|---|---|
| 50 | 9.70 × 10⁷ | 1.930 × 10⁹ | 50.25 ms | 92.5 |
| 100 | 1.909 × 10⁸ | 1.898 × 10⁹ | 100.61 ms | 182.1 |

Ratio of ops: **1.969** (target 2.00 ± 5%). Ratio of ops/s: **0.983** (target 1.00 ± 5%).
Both pass. If the compiler had been skipping work, ops/s would not stay constant as the
trial got longer.

### 3. Debug is slower by a plausible amount

| build | ops/s | ns per op |
|---|---|---|
| release (`-O3 -march=native`) | 1.836 × 10⁹ | 0.545 |
| debug (`-O0`) | 2.444 × 10⁸ | 4.09 |

Release is **7.5×** faster. That is the expected range for a loop over a `std::array` at
`-O0` (every element access goes through memory). A ratio near 1000× would have meant the
release build was not doing the work at all.

### 4. Warmup matters, and something else matters more

The plan said: with `--warmup 0 --spin-ms 0`, trial 0 should be visibly below trials 5+.
First attempt, unpinned, 12 trials of 50 ms, values in Gops/s:

```
0.83  1.83  1.99  2.07  1.87  1.92  1.82  1.80  1.61  1.69  1.89  2.14
```

Trial 0 is **55% below** the mean of trials 5+. With 5 ms trials the gap was 22%, because a
shorter trial 0 spends a larger fraction of its time in the ramp. So the effect is real and
warmup is justified.

The control run *with* warmup was supposed to be flat, but it came out bimodal, alternating
between ~2.1 and ~1.0 Gops/s. Repeating the A/B three times gave:

| run | warmup | trial 0 vs steady state | CoV over 12 trials | mean `now()` cost |
|---|---|---|---|---|
| 1 | none | −7.1% | 7.5% | 32 ns |
| 2 | none | −34.6% | 53.3% | **151 ns** |
| 3 | none | −2.3% | 7.3% | 39 ns |
| 1 | 5 + 500 ms spin | −22.2% | 9.0% | **116 ns** |
| 2 | 5 + 500 ms spin | −0.2% | 3.0% | 42 ns |
| 3 | 5 + 500 ms spin | +0.7% | 17.9% | 39 ns |

Median across runs: trial 0 sits **−7.1%** below steady state without warmup and **−0.2%**
with it. That is the verify result. But look at the last column: every bad run is a run
where the clock self-test tripped. The guest was 99% idle the whole time (`top` and
`docker stats` confirmed it), so the slowdown came from outside the VM. WSL2 vCPUs are
scheduled by Hyper-V onto whichever physical core Windows chooses, and when Windows has
other work, a vCPU can be time-sliced or landed on an E-core. When that happens, *every*
instruction gets slower, including the vDSO clock read, which is why the self-test sees it.

Two consequences:

- Pinning inside the guest (tried with `taskset`) does not help, because it pins to a vCPU,
  not to a physical core. A sweep of all 22 vCPUs gave medians between 1.60 and 2.12 Gops/s
  with no clean P-core/E-core split, which is what you expect if the mapping floats.
- The clock self-test doubles as a **host-contention canary**. M2.5 (the 1000-trial variance
  study) will re-run any configuration whose self-test failed rather than average
  contaminated trials in. That has been added to the plan.

The 3–18% CoV seen here over 12 trials is nowhere near the 3% target. That is not a failure
of this milestone: the target belongs to M2.5, which adds pinning, many more trials, and a
quiet-host protocol. What M1.2 established is that the number is *honest*: the work is real,
the clock is sound, and the warm-vs-cold difference is understood and removed.

## Five interview questions

**1. Your benchmark loop reports 50 billion ops/s on a 5 GHz core. What happened, and how
do you prove it?**
The compiler removed the loop: 10 ops per cycle is impossible for a 4-instruction op. Prove
it with `objdump` (the multiply is missing or the loop has no backward branch) and with the
scaling check: doubling the trial length should double the work at a constant rate, and an
optimized-away loop reports the same "work" regardless. Fix it with a `DoNotOptimize` sink on
the output and runtime-derived inputs so nothing can be constant-folded.

**2. Why is `std::chrono::high_resolution_clock` the wrong clock for a benchmark?**
Its name promises precision, not monotonicity. On libstdc++ it is an alias of `system_clock`,
which can jump when NTP corrects the time or a VM resyncs with its host. A negative or wildly
large elapsed time is then possible. `steady_clock` maps to `CLOCK_MONOTONIC` and only moves
forward at a fixed rate, which is what an interval measurement needs.

**3. Why measure "operations until 50 ms elapse" instead of "time for 100 million operations"?**
Holding the duration constant makes trials comparable across machines of very different
speed, and duration is what governs the trade-off between noise averaging and total run
time. It also lets the clock be read once per batch instead of once per iteration, which
matters because a clock read is roughly 60 operations' worth of time and serializes the
pipeline.

**4. Your first trial is consistently 30% slower than the rest. Should you drop it?**
Yes, but by design, not after the fact. The cause is the idle-to-turbo frequency ramp plus
cold caches and predictors. Run a fixed number of warmup trials that are identical to real
trials and never recorded, and busy-spin before the first one so the core is already at
speed. Dropping "outliers" after seeing the data is a different thing and is not allowed,
because it lets you pick the answer you wanted.

**5. Why eight accumulators instead of one, and what would you see if you used one?**
A 64-bit multiply has a 3-cycle latency but can issue every cycle. With one accumulator
each multiply waits for the previous one, so you measure latency: about 1 op per 3 to 4
cycles. With eight independent accumulators the out-of-order engine overlaps them and you
measure throughput. The symptom of getting it wrong is ops/s close to `clock_GHz / 4`.
