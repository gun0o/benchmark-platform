# M1.4 — The engine posts to the API

*Milestone notes, written for someone learning how the pieces of this project connect.
Run on 2026-09-21 on the Core Ultra 9 185H laptop under WSL2, release engine, with the
API running natively and Postgres in compose. Raw logs: `docs/results/m1.4/`. Earlier
notes: `M1.2.md`, `M1.3.md`, `M2.1.md` … `M4.1.md`.*

## The problem this milestone solves

M1.3 gave the measurements a database. Getting them there still meant a file and a
`curl` command typed by a person — which is fine until the person is running a sweep at
11 p.m. and forgets one of the four steps, and a week later nobody can say whether the
missing run was never made or never uploaded.

`--post` closes that: one flag, and the run that was just measured is in the database
before the process exits.

The constraint that shapes everything below is that **this is a benchmark binary**. It
runs on the machine under test, which may be a stripped-down box that someone is about to
measure. Two consequences: no runtime dependency worth avoiding, and nothing that can
block forever.

## What was built

1. **[`bench::post_json`](../../engine/src/http.cpp)** — a blocking HTTP/1.1 client over
   POSIX sockets. ~260 lines: `getaddrinfo`, a non-blocking `connect` with `poll`,
   `send`/`recv` loops with a deadline on every wait, a status-line and header parser, and
   a chunked-transfer decoder.
2. **`bench run --post URL`** — serializes the envelope, POSTs it, prints the API's reply
   on stdout and a one-line summary on stderr.
3. **`--post-timeout-ms`** (default 10,000) — the deadline for *each* of connect, send and
   receive.
4. **Ten tests** ([http_test.cpp](../../engine/tests/http_test.cpp)) including four
   round-trip tests against a one-shot loopback server started inside the test process.

## Each decision, and why

### Sockets, not libcurl

The plan allowed either a socket client or shelling out to `curl`. Both were rejected in
favour of the socket client for the same reason: **a dependency that exists only on the
machine that happens to be developing the engine is a dependency that fails on the machine
being measured.** Shelling out to `curl` also means quoting a 13 MB JSON body through a
shell or a temporary file, and losing the exit-code distinction between "curl is missing"
and "the API said 400".

What that costs: no TLS. `https://` is refused by name rather than silently downgraded —
a benchmark that quietly posts measurements in clear text because the client did not
understand the scheme is worse than one that stops and says so. When the API is deployed
behind TLS (M7.3), this client will post through a local proxy or the engine will grow a
real HTTP library; that is a decision to make with the deployment, not before it.

### Every wait has a deadline

The milestone's stated pitfall is "time-out the socket; a hung API must not hang the
benchmark". Three separate waits can hang, and each is bounded:

- **connect.** A plain blocking `connect()` to a host that drops SYNs takes the kernel's
  retry budget — roughly 2 minutes on Linux, regardless of what the caller wanted. The
  client sets `SOCK_NONBLOCK`, calls `connect`, expects `EINPROGRESS`, and `poll`s for
  `POLLOUT` with the timeout; then reads `SO_ERROR` to find out whether the connection
  actually succeeded, because `poll` reporting writability does not mean it did.
- **send.** A peer that stops reading fills the socket buffer and `send` blocks. Polled
  for `POLLOUT` with the same deadline.
- **receive.** A peer that accepts the request and never answers. Polled for `POLLIN`.

`PostJson.TimesOutOnASilentServer` starts a server that accepts, reads the whole request,
then sleeps 3 seconds without replying. With a 300 ms timeout the client must return an
error in well under 2 seconds; it does, and the error string says `timed out`.

The other socket-level detail worth naming is `MSG_NOSIGNAL` on `send`. Without it, a
peer that closed the connection early gets the writer a **`SIGPIPE`, which by default
kills the process** — so restarting the API mid-post would terminate a benchmark run that
had already collected its data. With it, the same situation is an `EPIPE` return value.

### Read until close, and undo chunking anyway

The request sends `Connection: close`, so the response ends at EOF and the client does not
have to parse `Content-Length` to know when to stop. That removes a whole class of
"response was truncated because the parser trusted a header" bugs, at the cost of one TCP
connection per POST — irrelevant for a handful of posts per run.

Chunked decoding is still implemented, because "the server happens to use
`Content-Length` today" is not a property the client should depend on: Go's `net/http`
picks chunked whenever the handler writes more than its buffer before flushing, which a
large error envelope could do. `DecodeChunked.RebuildsTheBody` pins it, and
`PostJson.UndoesChunkedTransferEncoding` runs it through a real socket.

### The URL is allowed to be short

`--post http://localhost:8080` appends `/v1/runs`; `--post http://host/v1/runs` is taken
literally. Typing the endpoint path on every invocation is noise, and a `--post` pointed
at a path that does not exist is not a silent failure — the 404 is printed with its body
and the exit code is 1 (`docs/results/m1.4/post.log`).

Parsing is done by hand because the shape is small and the failure cases should be
explicit: `rfind(':')` for the port, then a check that the colon is not inside an IPv6
literal (`http://[::1]:8080` parses to host `::1`, port 8080), a `from_chars` port that
must consume the whole string and land in 1–65535, and `https://` rejected with its own
message. Six negative cases are tested.

### What happens to the measurements when the POST fails

Nothing. The envelope is written to `--out` **before** the POST is attempted, and
`post_envelope` returns a status code that only affects the process's exit code. A run
posted to a dead port prints `connect: Connection refused`, exits 1, and leaves a complete
file behind that can be posted later by hand — verified in the log.

The one behavioural wrinkle: with `--post` and **no** `--out`, the envelope is not also
dumped to stdout. Posting *is* the output in that case, and printing 1000 trials of JSON
would bury the API's reply in them. `--post` with `--out` does both.

### Idempotency is the reason this is safe to retry

The client has no retry loop, deliberately — but it does not need one to be safe. Because
M1.3 made ingest idempotent on `run_id`, a user who re-posts a saved envelope gets
`{"inserted": 0, "duplicate": true}` rather than a second copy of the run. That is the
property that makes "write the file first, post second, post again by hand if it failed" a
workflow rather than a hazard.

```
$ psql -tAc 'select count(*) from measurements'      10
$ bench run --workload cpu_int --threads 1 --trials 10 --post http://localhost:8080
bench: POST http://localhost:8080/v1/runs -> 200 (10 results, 9576 bytes)
{"run_id":"31085d5d-955b-4810-8b59-4c9e3a4b1455","inserted":10,"duplicate":false,
 "machine_id":"7fea9ecafd05d7a64f0fcd74cf35f695"}
$ psql -tAc 'select count(*) from measurements'      20
```

and the API's own log line for that request:

```
{"level":"INFO","msg":"ingested run","run_id":"31085d5d-…","inserted":10,"duplicate":false}
```

Failure modes, all from `docs/results/m1.4/post.log`:

| situation | engine output | exit | `--out` |
|---|---|---|---|
| dead port | `--post http://localhost:9/v1/runs: connect: Connection refused` | 1 | written, complete |
| `https://` | `https is not supported by the engine's HTTP client` | 1 | written |
| wrong path | `-> 404` plus the server's body | 1 | written |
| silent server (test) | `read: timed out after 300 ms` in < 2 s | — | — |

`ctest --preset release`: **178/178 pass** (168 before this milestone, 10 new).

## What this milestone does not do

- **No chunking of large runs.** A run with more than 50,000 results is refused by the API
  with a 413 that says to chunk it; the engine does not yet split. That needs the API to
  accept several POSTs that belong to one `run_id` without the second being treated as a
  duplicate, which is an ingest change, so it lands with M5.1.
- **No retries and no queue.** A failed POST leaves a file and an exit code.
- **No TLS, no auth.** Both belong with the deployment milestone.
