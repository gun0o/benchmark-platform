# M2.5 — Variance: how repeatable is a measurement?

*Milestone notes, written for someone learning benchmark methodology. Measured on
2026-09-21 on a Core Ultra 9 185H laptop under WSL2, release build, **plugged in**, Windows
power plan "Balanced", power mode **"Best performance"** ("Max Performance Overlay"),
battery 85%→99% and charging, Docker containers stopped. Power state was recorded before
and after every single run; the logs are in `docs/results/m2.5/`. The headline artifact is
`docs/results/variance_2026-09-21.md`. Earlier notes: `M1.2.md`, `M2.1.md`, `M2.2.md`,
`M2.3.md`, `M2.4.md`.*

## The problem this milestone solves

Every milestone so far has produced numbers. This one asks whether those numbers mean
anything — specifically, if you measure the same thing a thousand times, how much do the
answers differ?

That question has a name: the **coefficient of variation**, standard deviation divided by
the mean. It is dimensionless, so 3% means the same thing for a CPU throughput in billions
of ops per second and a memory latency in nanoseconds. The project's Target #2 is CoV ≤ 3%
over at least 1000 trials.

Why it matters: if your benchmark's CoV is 5% and you use it to evaluate a code change
that made things 3% faster, you cannot see the change. The measurement noise is larger
than the effect. A benchmark's variance sets the smallest improvement it is capable of
detecting, and a benchmark that does not report its variance is asking to be believed
about differences it cannot actually resolve.

**The target was not met.** Best over 1000 trials: 3.47%. This note is mostly about how
that was established, what the noise turned out to be, and why the honest response is to
report it rather than to make it go away.

## What was built

1. **`--interleave`** — rotate through configurations trial-by-trial instead of running
   each to completion. Every configuration's worker pool stays alive; idle ones park on a
   futex rather than spinning.
2. **`bench report run.json`** — prints the per-configuration summary table (CoV, MAD,
   late-trial fraction, canary readings) straight out of the run file.
3. **The clock canary as a re-run rule** — if `steady_clock::now()` looks contended at
   either end of a configuration, throw the whole configuration away and run it again.
4. **Late-trial counting** — how many trials had a worker arrive late off the start
   barrier, reported next to the CoV and never used to drop anything.
5. **Four new summary fields** (`late_trials`, `canary_attempts`, `clock_call_ns_start`,
   `clock_call_ns_end`) through the schema, the engine writer and `bench validate`.
6. **21 new tests**, bringing the suite to 117 — green in release, debug, ci, asan and tsan.

## Each correctness decision, and why

### Interleaving: why idle workers must sleep, when M2.1 proved they must not

M2.1 established that workers must **spin** between trials, never sleep. Waking a parked
thread inside a VM took 85 µs to 10 ms, which wrecked the synchronised start that a
multi-threaded trial depends on. That finding is why the engine has a hand-written
`SpinBarrier` instead of `std::barrier`.

Interleaving appears to contradict it. Six configurations alive at once, five of them
waiting while the sixth runs a 50 ms trial — if all of them spin, the five idle ones steal
CPU from the one being measured, and the measurement is ruined.

Both are right, because they are about different moments:

- **Between a trial's start barrier and its end**, a worker must never sleep. This is
  inside the measurement.
- **Between one configuration's turn and its next**, a worker must never spin. This is
  outside the measurement entirely.

So an interleaved worker parks on a futex (`std::atomic::wait`) until its configuration's
turn, then does its cold-cache preparation, then arrives at the same tight `SpinBarrier`
as always. The slow, uneven futex wake-up happens *before* the barrier, so the barrier
still releases every worker at a single instant and the start spread is unaffected. The
wake-up cost lands in the gap between trials, where nothing is being timed.

The ordering has one hard requirement: the coordinator must open the gate *before* it
arrives at the start barrier. Arriving first would mean waiting at the barrier for workers
that are still asleep and have not been told to wake — a deadlock.

### The warmup floor had to change meaning

Warmup is "at least 20 trials **and** at least 500 ms". The time floor exists because on a
VM the first quarter-second of a configuration shows multi-millisecond start spreads while
the hypervisor settles the newly busy vCPUs onto physical cores.

Under interleaving, wall-clock time is the wrong clock to measure that against. While
`cpu_int`@1 waits its turn, five other configurations are running trials and the wall
clock advances — so a wall-clock floor would be satisfied without `cpu_int`@1 having
warmed up at all.

The floor now counts **time this configuration has spent in its own trials**. In a
sequential run that is the same quantity minus a few microseconds of per-trial overhead,
so nothing measurable changed there; under interleaving it is the only version that means
anything. There is a test that runs two interleaved configurations with an 80 ms floor and
checks each of them separately got its own warmup.

### Late trials are counted and kept

A trial is timed from the barrier release to the last worker's finish. If one worker
arrives at the barrier late — because the host descheduled its vCPU — the whole trial's
measured window stretches, and the reported throughput drops.

That is host preemption, not the workload, and the temptation is to discard those trials.
The engine counts them instead (`late_trials`, threshold 1 ms of start spread) and reports
the fraction next to the CoV. A test asserts `n` always equals the number of timed trials
that ran, so a late trial can never quietly vanish.

The reason this matters is visible in the results: `cpu_fp` at 22 threads had a late worker
in **91.8% of its trials**. Dropping them would leave 82 trials out of 1000 and a CoV
computed over the 8% of the time the machine happened to be unoccupied — a number about a
machine that does not exist. The 9.36% CoV *is* the answer to "what is it like to run 22
threads on this laptop".

### The clock canary, which took four attempts to get right

M1.2 found that `steady_clock::now()` costing more than ~100 ns is a reliable sign the host
is fighting you for the machine: every run where it happened also showed 2–3× lower
throughput. `PLAN.md` turns that into a pre-declared rule — check the clock at the start of
a configuration, and if it looks contended, re-run the configuration rather than averaging
contaminated trials.

The rule is pre-declared and looks only at the clock, never at a trial value, and it keeps
or discards a whole configuration. That is what separates it from outlier trimming, and
the distinction is the entire point: "discard data that looks bad" is how benchmarks lie,
while "discard data collected while a smoke alarm was going off" is how they stay honest.
The difference is whether the discard criterion can see the result.

Implementing it honestly took four tries, and the failures are more instructive than the
final version.

**Attempt 1 — a fixed sample count.** 100,000 samples, as the existing self-test used.
Under 66 spinners on 22 vCPUs, the rule did not fire. The canary can only see contention
that happens *while it is sampling*, so its sample count is really a detection window —
and 100,000 samples is 1.4 ms on a quiet host, short enough to fit between preemptions.

**Attempt 2 — more samples.** 500,000, an 8 ms window, measured to catch the load
reliably. It also broke a pre-existing test: under AddressSanitizer, 500,000 instrumented
`now()` calls consumed an entire `--max-seconds 0.4` budget before a single trial ran. A
sample count is not a window, because the same count takes 8 ms in one build and most of a
second in another.

**Attempt 3 — a time window.** Sample until 8 ms of wall time has passed, whichever comes
first. This fixed the budget problem and exposed the real one: under ASan a now() call
costs ~144 ns on a completely idle machine, so an absolute 100 ns threshold declares the
host contended before anything has happened. Making the threshold relative to a startup
reading did not work either — that reading is taken on the same possibly-busy host, and at
220 spinners it came out at 8 µs and blinded the canary exactly when the host was worst.

**Attempt 4 — measure the shape, not the scale.** Between preemptions, a `now()` call
costs whatever this build's calls cost. So the *cheapest* delta in the window is the
build's own overhead, measured on the spot; contention shows up as a handful of calls that
took thousands of times longer, which moves the mean and not the minimum. The rule is
therefore `mean / min > 3`, and it needs no constant calibrated per build:

| | quiet release | quiet ASan | release under 66 spinners |
|---|---:|---:|---:|
| mean now() | 14.4 ns | ~144 ns | 86.8 ns |
| min now() | 13 ns | ~140 ns | 15 ns |
| **mean/min** | **1.11** | **~1.03** | **5.79** |

Note the third column against the first: the absolute 100 ns rule would have called that
contended host *clean*, because 86.8 < 100. The ratio catches it. A rule expressed as a
ratio survives a change of units; a rule expressed as a constant has to be re-derived
every time the units move, and nobody remembers to.

The canary sweep across load levels (`m2.5/canary_demo.log`) now reads: idle → kept;
1×, 3×, 10× oversubscribed → re-run.

One limitation is documented rather than fixed: the failure is one-sided. A contended host
can still read clean if the contention misses the 8 ms window, but a quiet host never
reads dirty. So the rule can keep bad data; it can never discard good data. For a rule
whose job is to avoid silently averaging in garbage, that is the right direction to fail
in.

### The diagnostics had to be calibrated before they could be read

When a CoV misses its target, the useful question is *what kind* of noise it is. Three
shapes matter, and they have different causes:

- **Bimodality** — trials clustering in two groups. On a hybrid CPU that means some trials
  ran on a P-core and some on an E-core.
- **Slow drift** — a steady decline. That is thermal.
- **Spikes** — a few trials far below the rest. That is something stealing time.

The bimodality detector is 1-D 2-means. Applied to the first result it reported "29% of
trials in a slow cluster, 8.2% below the fast one", which looks like a smoking gun.

It is not, because **2-means splits any sample in two, including a sample with only one
mode.** Before trusting it, it was run against pure Gaussian noise with no second mode at
all: the answer came back "50% of trials, centres 1.5σ apart", at every CoV tested. So one
mode looks like 50% at 1.5σ, and the observed 29% at 1.65σ is barely distinguishable from
noise. The metric now reports the gap in units of σ, with the Gaussian null result printed
next to it, because the raw percentage is uninterpretable on its own.

This is the same discipline as the frequency probe in M2.4 — a measurement you have not
calibrated against a known-null case is not yet evidence.

## What the Verify steps showed

### Verify 1 — Target #2: missed, on every configuration

`--trials 1000 --trial-ms 50 --warmup 20 --pin --cold clflush`, raw CoV, nothing trimmed:

| config | n | CoV | late trials | drift |
|---|---:|---:|---:|---:|
| `cpu_fp_ops`@1 | 1000 | **3.47%** | 0.0% | −0.7% |
| `cpu_hash_ops`@1 | 1000 | 4.02% | 0.0% | +0.6% |
| `cpu_int_ops`@1 | 1000 | 4.96% | 0.0% | +3.1% |
| `cpu_int_ops`@16 | 1000 | 6.03% | 0.7% | −7.6% |
| `cpu_hash_ops`@16 | 1000 | 7.36% | 1.3% | −9.7% |
| `cpu_fp_ops`@22 | 1000 | 9.36% | **91.8%** | −10.6% |

The clock canary read 13.6–15.7 ns at both ends of every configuration, so no
configuration was re-run and the host was quiet throughout. The rule was armed and simply
had nothing to catch — which is worth recording, because "the safeguard never fired" and
"there was no safeguard" produce identical-looking data.

### Verify 2 — the dominant noise source, which differs by thread count

**At high thread counts**: thermal drift of 7.6–10.6% across a 50-second configuration,
plus host preemption. With 22 workers on 22 vCPUs there is no spare capacity, so anything
else that wants the CPU delays a worker, and one late worker stretches the whole trial.

**At 1 thread**: none of the usual suspects. Zero late trials, negligible drift,
`stddev/(1.4826×MAD)` between 0.95 and 1.36 (≈1 means Gaussian), and the 2-means split
sitting on the unimodal null. It is not core migration, not spikes, not drift. The machine
simply does not repeat a 50 ms measurement to better than ~3.5%. On a Hyper-V vCPU whose
physical core the guest cannot see or choose, that is the expected answer, and it is a
more useful result than a number that happened to come out under 3%.

### Verify 3 — the knobs, and why the first pass was thrown away

The first pass ran each knob setting once, one after another. That is worthless on a
machine that drifts 10% across a minute of load: the knob is confounded with when the run
happened. Every knob was re-measured with the settings **alternated and repeated 3 times**,
the same design as M2.4's hash-fold study.

It changed two conclusions. The single pass showed unpinned beating pinned on all three
workloads; with repetition the ranges overlap and the sign is not even consistent. Same
for warmup. Both knobs are washes for CoV at 1 thread.

| knob | verdict |
|---|---|
| `--pin` on/off | no effect (ranges overlap, sign inconsistent) |
| warmup on/off | no clear effect on CoV |
| `--trial-ms` 10 → 50 → 200 | **the only knob that works**: 5.41% → 3.90% → 2.83% (`cpu_int`) |

Warmup being a wash is not evidence that warmup is pointless. M1.2 measured trial 0 coming
in 7–55% below steady state without it. Warmup fixes the *bias* of the first few trials;
CoV only sees the *spread* of all of them, and over 100 trials a few cold ones are diluted.
Two different problems, and the right measurement for one is silent about the other.

### Verify 4 — the trial-length result that does not survive contact with the target

`--trial-ms 200` reaches 2.83% at 100 trials. Target #2 requires 1000, so it was re-tested
there (612 seconds of wall clock):

| config | n | CoV | detrended | drift |
|---|---:|---:|---:|---:|
| `cpu_hash_ops`@1 | 1000 | 3.74% | 3.31% | −6.0% |
| `cpu_int_ops`@1 | 1000 | 3.88% | 3.74% | −3.6% |
| `cpu_fp_ops`@1 | 1000 | 3.94% | 3.76% | +4.0% |

The gain is gone. 1000 trials of 200 ms take 200 seconds per configuration, and the
package heats over 200 seconds: `cpu_int`'s per-100-trial medians run +7% high early and
decline to baseline by the end.

**This is the milestone's real finding.** The two halves of Target #2 fight each other on
a laptop. Longer trials buy steadiness within a trial; the requirement for 1000 of them
spends it on drift between trials. Even removing the drift arithmetically leaves 3.31% —
still short. The target is not missed by a little bad luck; it is unreachable on this
hardware, and now there is a measurement that says why.

### Verify 5 — interleaving does what it was built for

Same configurations, 300 trials, sequential vs interleaved:

| config | drift sequential | drift interleaved |
|---|---:|---:|
| `cpu_int_ops`@1 | +5.3% | **−0.2%** |
| `cpu_fp_ops`@1 | −3.6% | **−0.3%** |
| `cpu_hash_ops`@1 | +0.1% | +1.5% |

Per-configuration drift collapses, because each configuration now samples the whole
thermal history of the run instead of one slice of it. CoV is unchanged — interleaving was
never meant to reduce it. It makes configurations *comparable to each other*, so a drift
penalises all of them equally instead of whichever ran last. That is a fairness property,
not a precision one, and conflating the two would be a good way to believe a comparison
that is not there.

### Verify 6 — the suite

117/117 in release, debug, ci, asan and tsan. 11/11 of the `perf` subset, 106/106 with
`-LE perf`. All 38 run files written by this milestone pass `bench validate` and
`check-jsonschema` against the schema, including the four new summary fields.

## Five interview questions

**1. Your benchmark has a CoV of 5% and your target is 3%. What do you do?**
First, find out what kind of 5% it is, because the fixes are different. I look at three
shapes: two clusters of trials means something is switching between them — on a hybrid CPU,
probably P-cores versus E-cores; a steady decline means thermal; a few trials far below the
rest means something intermittently stealing time. In my case the answer at one thread was
"none of those" — no late trials, no drift, and a distribution whose standard deviation was
within a few per cent of 1.48 × its median absolute deviation, which is what clean Gaussian
noise gives. That told me there was no single culprit to remove, and that the honest
report was 3.47% with the cause named, not a smaller number obtained by other means. What I
did not do is trim outliers. Dropping the slowest 10% would have reported ~3.1% and hit the
target, and it would have been a number I chose rather than measured.

**2. What is the difference between discarding trials because the host was busy and
discarding trials because they look slow?**
Whether the discard criterion can see the result. I have a rule that throws away a whole
configuration when `steady_clock::now()` looks contended — that criterion reads only the
clock, is declared before any data is collected, and discards everything or nothing, so it
cannot select for a particular answer. Trimming outliers reads the values themselves and
keeps the ones it likes, which biases the result by construction and always in the
flattering direction. The practical test I'd apply: could this rule have been written down
before the run, and could it ever make the number worse? If the answer to either is no, it
is not a filter, it is a thumb on the scale. I also record when the safeguard fired —
`canary_attempts` is in every summary — because "the rule never triggered" and "there was
no rule" look identical in the data otherwise.

**3. You add a flag that lets idle benchmark threads sleep between trials. Earlier you
proved benchmark threads must never sleep. Which is it?**
Both, because they are different moments. Inside a trial — between the start barrier
releasing the workers and the last one finishing — a worker must never sleep, because
waking a parked thread in a VM took me 85 µs to 10 ms and that lands directly in the
measured window; that is why the engine has a hand-written spin barrier instead of
`std::barrier`. Between one configuration's turn and its next, under interleaving, a worker
must never *spin*, because five idle configurations spinning would steal the CPU from the
one actually being measured. So an idle worker parks on a futex, wakes, does its cache
preparation, and only then joins the same tight spin barrier as always. The slow wake-up
happens entirely outside the timed region. The general rule is that "never sleep" was never
about threads, it was about the measured window.

**4. You compare two settings by running A then B, and B comes out 8% better. What is
wrong with that?**
The setting is confounded with when the run happened. My machine loses about 10% of its
throughput across a minute of sustained load as the package heats, so an A-then-B
comparison can manufacture an 8% difference out of nothing but ordering — and would have
reported the reverse if I had run B first. The fix is to alternate and repeat: run
A,B,A,B,A,B and compare medians, so the drift lands on both arms equally. When I did that,
two effects I had already half-believed — that unpinned beat pinned, and that warmup
reduced variance — both evaporated into overlapping ranges with inconsistent signs. The
related trap is reporting a single CoV as if it were exact; a CoV estimated from n trials
has a standard error around CoV/√(2n), so my 100-trial estimates were worth about ±0.25
percentage points and I showed the min–max across repetitions rather than a bare number.

**5. You detect bimodality with 2-means clustering and it reports two clusters. Are the
data bimodal?**
You cannot tell yet, because 2-means returns two clusters for any input, including data
with exactly one mode. Before believing it I ran the same algorithm on pure Gaussian noise
with no second mode, and it confidently reported 50% of points in a "slow cluster" with the
centres 1.5 standard deviations apart, at every spread I tried. That is the null result, so
my real data's "29% of trials, 1.65σ apart" was barely distinguishable from a single mode,
and reporting it as bimodality would have sent me hunting for a core-migration problem that
was not there. So I changed the metric to report the gap in units of sigma with the
Gaussian baseline alongside it. The general principle is that a detector you have not run
against a known-negative case is not evidence yet — it is a number that will agree with
whatever you already suspect.
