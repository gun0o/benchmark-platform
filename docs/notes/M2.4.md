# M2.4 — CPU workloads and the 10M ops/s target

*Milestone notes, written for someone learning benchmark methodology. Measured on
2026-09-20 on a Core Ultra 9 185H laptop under WSL2, release build, **plugged in**, Windows
power plan "Balanced". Raw runs and commands are in `docs/results/m2.4/`. Earlier notes:
`M1.2.md`, `M2.1.md`, `M2.2.md`, `M2.3.md`.*

> **The measurements here were taken twice.** The first pass ran with the Windows power
> mode on **"Best power efficiency"** (battery low and charging, 24 %); the headline
> numbers were then re-taken with it on **"Best performance"** ("Max Performance Overlay",
> battery 67 % and charging). The tables in the body of this note are from the second pass.
> The first pass is kept in `docs/results/m2.4/*_powersave.json`, because the difference
> between the two is one of the more useful results in the milestone — see
> **"What the power mode was worth"** at the end, which also corrects a claim the first
> version of this note made about thread pinning.*

## The problem this milestone solves

Up to now the engine had one real workload, `cpu_int`, and everything else was
scaffolding: a thread pool (M2.1), statistics (M2.2), cold-cache control (M2.3). This
milestone adds the other two CPU kernels and then asks the question the whole engine
exists to answer — *how fast is this machine?* — in a way that survives being asked
"how do you know?".

That second part is most of the work. "10 million operations per second" means nothing
until you say what an operation is. If one tool calls a 20-instruction hash one op and
another calls a single add one op, the tool reporting the smaller number may be measuring
twenty times more work. So the unit is defined first, in `CLAUDE.md`, and then the job is
to prove the code performs exactly that unit, exactly as many times as it claims.

## What was built

1. **`cpu_fp`** (`cpu_fp.hpp` / `.cpp`) — eight independent chains of
   `a = std::fma(a, b, c)` on doubles. One op is one fused multiply-add on one lane.
2. **`cpu_hash`** (`cpu_hash.hpp` / `.cpp`) — an xxHash64-style mixer over 64-byte blocks
   read from a 4 KiB L1-resident buffer. One op is one block hashed.
3. **`kBatchOps` on the `Workload` concept.** Previously the runner computed a batch's op
   count as `kItersPerBatch × kLanes`. That works when a lane *is* an op, which is true for
   `cpu_int` and `cpu_fp` and false for `cpu_hash`, whose four mixing lanes cooperate on
   one block. Each workload now declares its batch size directly and the concept requires
   it to be a positive compile-time constant.
4. **16 new tests** — 12 functional (`tests/cpu_workloads_test.cpp`) and 4 timing-ratio
   ones (`tests/cpu_scaling_test.cpp`, labelled `perf`).
5. **A frequency probe** (`docs/results/m2.4/freq_probe.cpp`) — not part of the engine, a
   one-off measurement needed to turn ops/s into ops/cycle.

## Each correctness decision, and why

### The op count is a constant, not a measurement

A benchmark's reported rate is `ops ÷ seconds`. Everyone worries about the denominator
(clocks, timing overhead, what to include). Almost nobody checks the numerator, and the
numerator is where the silent factor-of-eight errors live.

So `run_batch()` always performs exactly `kBatchOps` operations and returns that constant.
Nothing counts, estimates, or samples. The runner reports it as `params.batch_ops`, and a
test asserts that what the function returns equals what the constant says. If those ever
drift apart, every ops/s number in the project is wrong by a fixed factor and no other test
would notice, because everything else — the summaries, the scaling curves, the JSON — would
stay perfectly self-consistent around the wrong value.

This is also why `kBatchOps` became an explicit constant instead of `iters × lanes`.
`cpu_hash`'s mixer uses four accumulator lanes to process *one* block, so `iters × lanes`
would have reported four times too many operations. The old formula was not wrong for the
workloads that existed; it was a coincidence about them, and coincidences do not survive
new cases.

### `cpu_fp`: the lane count is the design, not a tuning knob

An FMA on this core has a latency of about 4 cycles — from issuing the instruction to
having its result available. But the core has two FMA units, so it can *start* two per
cycle. Those two facts fight each other whenever the next operation needs the previous
one's answer.

Run one chain of dependent FMAs and you get one result every 4 cycles: 0.25 ops/cycle,
and you have measured latency. Run eight independent chains and while chain 1 waits its
4 cycles, chains 2–8 keep the units busy: 8 ÷ 4 = 2 ops/cycle, and you have measured
throughput. The gap between those two answers is a factor of eight, and both are honest
numbers about the same machine — they are just answers to different questions.

`cpu_fp_ops` is defined as a throughput metric, so it needs enough lanes to hide the
latency, and eight is exactly that number. M1.2 wrote down the symptom to watch for: if
`ops/s ≈ core_GHz / 4`, the lane count is too low and the benchmark has quietly become a
latency test.

### `cpu_fp`: the arithmetic has to stay boring

`a = a*b + c` repeated 131,072 times per batch is a recurrence, and recurrences go
somewhere. Where they go matters for the measurement:

- If `|b| > 1`, the lanes grow without bound and reach infinity within a few thousand
  iterations. After that every FMA is `inf * b + c = inf`. The instruction still issues,
  so the benchmark still reports a number, but "a double-precision FMA" now means
  arithmetic on infinities.
- If the lanes decayed towards zero they would pass through the **subnormal** range — the
  very small values where the exponent has bottomed out. Subnormal operands cost tens of
  extra cycles on most x86 parts. Throughput would collapse partway through a trial, so
  the reported rate would depend on how long the trial ran. A rate that depends on trial
  length is not a rate.

The fix is to pick `b ∈ [0.5, 0.75)` and `c ∈ [0.25, 0.5)` at runtime. That makes the map
a contraction towards the fixed point `c / (1 − b)`, which lands in `[0.5, 2)`. Every
operand is a normal double for the whole run, so every FMA costs the same at trial 1 and
trial 1000.

The lanes converge to that fixed point within about 50 iterations and then stop changing.
That is fine — FMA timing on normal doubles does not depend on the operand values — and it
buys a strong test: the test asserts each lane lands on `c / (1 − b)` to within 1e-12
relative. A kernel that did a multiply but not the add, or an add but not the multiply,
converges somewhere else or not at all. So a pure arithmetic identity, checkable in
microseconds, proves the kernel evaluates the expression the metric names.

### `cpu_hash`: the buffer is small on purpose

The mixer reads its input from a buffer, and the buffer's size decides what is being
measured. Too small (say, one block) and the "load" is really a register that never
changes, so the memory system is not exercised at all and the compiler may hoist it. Too
big and the loads start missing L1, then L2, and `cpu_hash_ops` silently turns into a
memory-latency benchmark wearing a hash's name.

4 KiB sits far inside this part's 48 KiB L1d, and is 64 times larger than the mixer's own
state. So the loads are real loads that always hit L1, and the metric measures the mixer.
`--working-set` can override it, which is how the L1-residency claim gets tested rather
than asserted.

### `cpu_hash`: the accumulator fold, which was wrong the first time

Each block's hash has to end up somewhere the compiler cannot discard, or `-O3` is entitled
to delete the entire loop. The first version folded with XOR: `acc ^= hash_block(...)`.

The test caught it. The batch is 64 Ki ops over 64 blocks, so **every block is hashed
exactly 1024 times**, and XOR-ing any value an even number of times gives zero. The digest
at the end of every batch was identically 0.

That is worth being precise about, because there are two different problems and only one of
them is urgent:

- **Was the loop being optimized away?** No. The compiler does not know the buffer's
  contents (runtime random) or its length (a runtime member), so it could not have proved
  the cancellation. The measurement was real.
- **Could it be checked?** No — and that is the actual defect. A sink whose value is
  always zero is a sink that cannot demonstrate it received anything. There was no way to
  tell "the loop hashed all 64 blocks" from "the loop did nothing" by looking at the
  output, and one future change — making the block count a compile-time constant, say —
  would turn a latent property into an exploitable one.

The replacement is `acc = acc * P1 + h`: order-dependent and unable to cancel, so the
digest is a genuine checksum over every block the batch touched. That is now a test.

It is **not free**, and the write-up says so. Three folds were built as three binaries and
run alternately, nine repetitions each (`docs/results/m2.4/hash_fold.log`):

| fold | ops/s | vs XOR |
|---|---:|---:|
| `acc ^= h` | 1.360e8 | baseline |
| `acc += h` | 1.312e8 | −3.6 % |
| `acc = acc * P1 + h` | 1.289e8 | −5.2 % |

So 3–5 % of `cpu_hash_ops` is the accumulator rather than the mixer, and the metric is
honestly "hash a block and accumulate it". That is the price of a sink whose value can be
checked, and it is a price worth paying — but it has to be *stated*, not absorbed. (The
run-to-run spread is ±6 %, wider than the gaps, so the ordering is consistent across both
studies while the exact percentages are not precise.)

### `cpu_hash`: independent blocks, not a chain

Every block is hashed with the same seed, so blocks do not depend on each other. The
alternative — feeding each block's hash in as the next block's seed — would turn the batch
into one long dependency chain and each op would cost the mixer's *latency* instead of its
throughput.

This is the same latency-versus-throughput choice as `cpu_fp`'s lane count, and it is
settled the same way: `ops/s` claims to say how many blocks the core can retire per second,
so the blocks must be allowed to overlap. It also matches what real hashing does — hashing
many separate keys, not one long chain.

### `std::bit_cast` for reading the block

The buffer holds bytes; the mixer wants eight `uint64_t`. Pointer-casting bytes to
`uint64_t*` and dereferencing is the obvious way and is undefined behaviour (strict
aliasing), and also assumes alignment the buffer does not promise. So the 64 bytes are
`memcpy`'d into a local array and `std::bit_cast` reinterprets it, which is well-defined
regardless of alignment.

The usual objection is that this must be slower. It is not: the disassembly shows the hot
loop loading the eight words straight out of the buffer with plain 64-bit `mov`s, with no
staging array at all. The copy exists only in the source, as a way of saying something
legal.

### The 10M target is not asserted in a test that runs under sanitizers

There is a test asserting each kernel clears 10M ops/s on one thread, as a smoke test. It
failed under AddressSanitizer — `cpu_hash` runs at 8.0e6 ops/s there against 1.19e8 in
release, a 15× slowdown, because each of the eight loads per block goes through a
shadow-memory check.

That failure was the test's fault, not the kernel's. ASan was working correctly; the
assertion was making a claim about hardware in a build where the number describes the
instrumentation. The test now skips itself under ASan and TSan and says why. The real
Target #1 check lives in `docs/results/`, where it belongs: a green test suite should not
depend on the host being fast.

## What the Verify steps showed

### Verify 1 — the disassembly check, done by exact count

`PLAN.md` asks for a presence check ("FMA: `vfmadd` present; hash: `imul` + `rol`"). Exact
counts are a much stronger check, because presence survives a compiler hoisting seven of
eight lanes out of the loop and counting does not. Every count was predicted from the
source first, then checked (`docs/results/m2.4/disasm_kernels.log`):

| kernel | predicted | found |
|---|---|---|
| `cpu_int` | 8 `imul`, 8 `shr`, 8 `xor` per iteration (8 lanes, unrolled) | 8, 8, 8 ✓ |
| `cpu_fp` | 8 lane-FMAs per iteration, fused, never split into mul+add | 1 `vfmadd132pd` (4 lanes) + 4 `vfmadd132sd`, 0 `vmul*` ✓ |
| `cpu_hash` | 31 `imul` = 16 rounds + 12 merges + 2 avalanche + 1 fold; 16 rotates = 12 round + 4 lane | 31 `imul`, 16 `rorx` ✓ |

Two things worth noticing.

**GCC partly vectorized `cpu_fp`.** It packed lanes 0–3 into a single 256-bit
`vfmadd132pd` and left lanes 4–7 scalar. That is still 8 lane-FMAs per iteration, so the
op count is right, and it happens not to change the rate either: 8 lanes divided by a
4-cycle latency gives 2 lane-ops/cycle whether the lanes are packed, scalar, or mixed. It
is a good illustration of why the op is defined in terms of *lanes* and not instructions —
the instruction count changed and the metric did not.

**`std::rotl` compiles to `rorx`, not `rol`.** `rotl(x, 31)` is `ror` by 33, and GCC picks
the BMI2 form. Checking for `rol` would have reported a failure on correct code.

### Verify 2 — trial-length scaling, all three kernels

Double the trial length; the work must double and the rate must not move
(`trial_length_scaling.log`):

| workload | ops ratio (want ≈ 2) | rate ratio (want ≈ 1) |
|---|---:|---:|
| `cpu_int` | 2.117 | 1.059 |
| `cpu_fp` | 2.008 | 1.006 |
| `cpu_hash` | 2.021 | 1.010 |

Both halves matter. If a kernel were partly optimized away the rate would jump; if ops
were estimated from the clock rather than counted, the ops ratio would track the rate
ratio instead of the time ratio.

### Verify 3 — measuring the clock, because nothing reports it

`ops/cycle` is the number that tells you whether a result is plausible, and it needs a
frequency. WSL2 does not have one to give: `/proc/cpuinfo` reports the same synthetic
`3071.998 MHz` on all 22 vCPUs (impossible on a hybrid part under turbo),
`/sys/.../cpufreq` does not exist, and Windows reports the 2.3 GHz nominal.

So it was measured: time a chain of instructions that must run one after another, with a
known per-instruction latency. The first attempt used `add $1, %rax` — latency 1 cycle,
obviously — and reported **25 GHz**.

The chain was not a chain. Recent Intel cores collapse runs of add-with-immediate to the
same register in the renamer, so the "dependency" was optimized out. The probe had
measured that optimization and called it a clock.

The fix is to never trust one chain. Using two instructions of *different* known latencies
turns the probe into a self-check, because their rates must differ by exactly the latency
ratio:

```
dependent add reg,reg   4.363 G/s  => 4.363 GHz  (latency 1)
dependent imul reg,reg  1.400 G/s  => 4.200 GHz  (latency 3)   ratio 2.99, want 3.00
dependent add $1,reg   25.577 G/s  => not a clock
```

Two independent chains agreeing to 3.9 % is evidence; one chain agreeing with itself is
not. **~4.28 GHz.**

### Verify 4 — Target #1, and three predictions that held

Target #1 is aggregate `cpu_*_ops` ≥ 1e7 at the best thread count. All three pass by two
to three orders of magnitude, which was expected and is not the interesting part:

| metric | best threads | aggregate ops/s | ops/s at 1 thread | ops/cycle at 1 thread |
|---|---:|---:|---:|---:|
| `cpu_int_ops` | 16 | 4.011e+10 | 4.647e+09 | 0.96 |
| `cpu_fp_ops` | 22 | 1.000e+11 | 9.070e+09 | 1.88 |
| `cpu_hash_ops` | 16 | 1.244e+09 | 1.536e+08 | 0.032 |

The interesting part is that each `ops/cycle` value was predicted from the disassembly
before being measured:

| kernel | reasoning | predicted | measured |
|---|---|---:|---:|
| `cpu_int` | 8 `imul` per iteration ÷ one integer-multiply port = 8 cycles per 8 ops | 1.00 | 0.96 |
| `cpu_fp` | 8 lanes ÷ 4-cycle FMA latency | 2.00 | 1.88 |
| `cpu_hash` | 31 `imul` per block on one multiply port → ≥ 31 cycles/block | ≤ 0.032 | 0.032 |

Three independent predictions, three hits. In the first pass, under Best power efficiency,
all three landed 7–10 % low *in the same direction* — which was itself informative, because
a consistent bias is not three separate errors but one. The candidate named at the time was
that the sustained clock during a 50 ms trial sits below the peak the probe catches. The
re-run at a higher power mode tested that and the gap closed to 4–6 %, with `cpu_hash`
landing exactly on its port limit. A prediction that survives an independent change to the
machine is worth considerably more than one that merely fits the data it came from.

This is what makes a benchmark trustworthy. Any program can print a large number. A
benchmark you can predict from first principles, to within a few per cent, is one where
you know what is being measured.

### Verify 5 — scaling, and the hybrid core finding

Aggregate throughput does not scale linearly, and stops improving well before 22 threads:

| threads | `cpu_int` efficiency | `cpu_fp` | `cpu_hash` |
|---:|---:|---:|---:|
| 4 | 89 % | 93 % | 84 % |
| 8 | 77 % | 84 % | 74 % |
| 11 | 63 % | 76 % | 61 % |
| 16 | 54 % | 68 % | 51 % |
| 22 | 39 % | 50 % | 37 % |

In the first pass these read 104–109 % at 2–4 threads, which is impossible — you cannot get
more than N times one thread's work out of N threads. That was not free performance, it was
a bad denominator: the 1-thread baseline had been measured at a fluctuating clock, and its
CoV was 8–15 %. Under Best performance the baseline is stable and every efficiency is
≤ 100 %, which is the shape the arithmetic demands. An impossible number in a table is
always worth chasing; this one was pointing straight at the power mode.

The fall-off is the real finding: 22 "CPUs" are 6 P-cores + 8 E-cores + 2 LP E-cores plus
SMT, presented to the guest as 11 identical cores × 2 threads. Threads landing on E-cores
do meaningfully less work, and hyperthread siblings share one core's execution units, so
the last threads added contribute a fraction of a core each. `PLAN.md` predicted flattening
after ~6 threads; measured, it is closer to 11, and the peak is at 16.

**Pinning: see the correction at the end of this note.** The first pass found pinning
6–9 % slower and this note generalised that. The re-run does not support the
generalisation.

### Verify 6 — the test suite

97/97 pass in all five presets: release, debug, ci (portable `-march=x86-64-v3`), asan and
tsan. 11/11 of the `perf` subset, 86/86 with `-LE perf`.

Three timing-sensitive tests failed once each during an earlier back-to-back run of the
whole matrix, two of which predate M2.4. All three then passed 5/5 in isolation on the same
binaries, and the full matrix passed cleanly on re-run. They are host noise and are
recorded as such in `docs/results/m2.4/README.md` rather than quietly re-run until green.
M1.2's finding applies — the clock self-test is a host-contention canary — and M2.5 is
where that gets turned into a rule.

## What the power mode was worth

The whole milestone was measured once, then measured again with one thing changed: the
Windows power mode moved from "Best power efficiency" to "Best performance". Same binary,
same commands, ten minutes apart, machine otherwise idle and plugged in both times.

| | throughput at best thread count |
|---|---:|
| `cpu_int_ops` | +8.1 % |
| `cpu_fp_ops` | +16.5 % |
| `cpu_hash_ops` | +14.9 % |
| measured 1-thread clock | 4.28 → 4.83 GHz (+13 %) |

`PLAN.md` warned that the wrong power plan "can swing 20 %", and that turns out to be the
right order of magnitude. But throughput was the smaller half of the story.

| 1-thread CoV | Best power efficiency | Best performance |
|---|---:|---:|
| `cpu_int_ops` | 15.0 % | **3.2 %** |
| `cpu_fp_ops` | 8.6 % | **3.9 %** |
| `cpu_hash_ops` | 12.3 % | **2.1 %** |

Roughly four fifths of the single-thread variance was the power mode. That is the lesson
worth carrying: a power-managed laptop does not simply run slower by some constant, it runs
*unevenly*, because the governor keeps re-deciding what clock to grant while the benchmark
is running. A benchmark cannot average that away — it is not noise around a true value, it
is the machine being a different machine from moment to moment.

Two things in the first pass were visibly wrong and both pointed here.

**Scaling efficiency above 100 %.** The first pass reported 104–109 % efficiency at 2–4
threads, which is arithmetically impossible: N threads cannot do more than N times what one
thread does. It was not the numerator, it was the denominator — the 1-thread baseline had
been measured at a wandering clock. Under Best performance every efficiency is ≤ 100 %. An
impossible number in a table is always worth chasing.

**The ops/cycle shortfall.** All three kernels came in 7–10 % below their predicted
ops/cycle, consistently in the same direction. The explanation offered was that the
sustained clock during a 50 ms trial sits below the peak the frequency probe catches.
Raising the power mode closed the gap to 4–6 %, with `cpu_hash` landing exactly on its
port limit. That is the hypothesis surviving an independent change rather than being
fitted to the data that produced it.

### Correction: pinning

The first version of this note said "pinning did not help — at the best thread count the
unpinned run was 9 % faster for `cpu_int` and 6 % faster for `cpu_fp`", and presented that
as the third milestone in a row confirming a general rule. The re-run does not support the
general rule. Difference, pinned minus unpinned, at the best thread count, in standard
errors of the median (30 trials each):

| metric | Best power efficiency | Best performance |
|---|---|---|
| `cpu_int_ops` | −9.3 % (5.4 SE) | +0.4 % (0.3 SE) |
| `cpu_fp_ops` | −5.7 % (2.6 SE) | +4.4 % (1.6 SE) |
| `cpu_hash_ops` | +1.7 % (0.9 SE) | +0.5 % (0.4 SE) |

Under Best power efficiency, pinning really did hurt `cpu_int` — 5.4 standard errors is not
noise. Under Best performance nothing reaches 2 SE in either direction, so neither "pinning
helps" nor "pinning hurts" is supported. The reading that fits both passes: when the package
is power-limited, letting Linux move a thread off a vCPU the host has throttled is worth
something; with power headroom there is nothing to move away from.

What survives unchanged is the underlying reason from `CLAUDE.md` — pinning a thread to a
Hyper-V vCPU does not decide which *physical* core runs it — so pinning here buys much less
than it would on bare metal. The error in the first version was not the measurement; it was
stating a conditional result as an unconditional rule, on one power mode's worth of data.

## Five interview questions

**1. Your CPU benchmark reports 3.9 billion "operations per second". What is an operation,
and why should I believe the number?**
An operation here is one update of one 64-bit lane: `acc = (acc * K) + ((acc >> 17) ^ i)` —
a multiply, a shift, a xor and an add. That definition is written down before any number
is, because without it the figure is uncomparable: a tool that counts a twenty-instruction
hash as one op will report a number twenty times smaller for strictly more work. As for
believing it, three things back it. The op count is a compile-time constant that the kernel
returns and a test checks, so the numerator cannot drift. The disassembly shows exactly
eight `imul`, eight `shr` and eight `xor` in the loop that actually repeats — not "some
multiplies are present", the exact count the op definition implies. And dividing by the
measured clock gives 0.90 ops per cycle against a predicted 1.00, the prediction being that
the core has one integer-multiply port and the loop needs eight multiplies per eight ops.
A number you can derive from the machine's microarchitecture is a different kind of claim
from a number that merely appeared.

**2. You benchmark a floating-point kernel and get about 0.25 operations per cycle on a
core with two FMA units. What went wrong?**
Nothing went wrong with the machine — you measured latency instead of throughput. An FMA
takes about 4 cycles to produce a result, and if each operation feeds the next there is
only ever one in flight, so you get one result per 4 cycles: 0.25 per cycle. The two FMA
units are idle almost all the time because there is no independent work to give them. The
fix is independent chains: with eight lanes, seven others make progress while one waits,
and you get 8 ÷ 4 = 2 ops/cycle, which is the throughput number. Both figures are true
statements about the same CPU; they answer "how long does one FMA take" and "how many FMAs
can it retire per second", and a benchmark has to say which one it is reporting. The
diagnostic to memorize is that if your ops/s comes out near `frequency ÷ latency`, you are
measuring a dependency chain.

**3. You need the core's clock speed and the OS won't tell you. How do you measure it, and
how do you know your measurement is right?**
Time a chain of dependent instructions with a known latency: N instructions that must each
wait for the previous one take N × latency cycles no matter how wide or clever the core is,
so wall time gives you the frequency. The catch is that you have to be sure your chain is
really a chain. I wrote one using `add $1, %rax`, which is latency 1 by any reference, and
got 25 GHz — because recent Intel cores collapse runs of add-with-immediate to the same
register in the renamer, so there was no dependency left to time. The general fix is to
never trust a single chain: use two instructions with *different* known latencies, here
`add reg,reg` at 1 cycle and `imul` at 3, and require their rates to differ by exactly the
latency ratio. Mine came out at 2.99 against an expected 3.00, and the two implied
frequencies agreed within 4 %. One chain can only agree with itself; two chains of
different latencies can catch the CPU cheating.

**4. A colleague's hash benchmark XORs every block's hash into an accumulator so the
compiler can't remove the loop. What would you check?**
Whether the accumulator can cancel. I hit exactly this: the batch was 65,536 blocks over a
64-block buffer, so each block was hashed exactly 1024 times, and XOR-ing anything an even
number of times gives zero. The digest was identically zero at the end of every batch.
I'd separate two questions there. Was the loop actually optimized away? No — the compiler
could not see the buffer's contents or its length, so it could not prove the cancellation,
and the timings were real. But could the sink *demonstrate* the work happened? Also no, and
that is the defect worth fixing: there was no way to distinguish "hashed all 64 blocks"
from "did nothing" by inspecting the output, and one refactor away it stops being merely
untestable and becomes exploitable. I switched to `acc = acc * PRIME + h`, which is
order-dependent and cannot cancel, so the digest is a real checksum and a test can assert
it changes when any input does. That cost a measured 5 % of throughput, which I reported
rather than absorbed — the metric is now honestly "hash and accumulate".

**5. Your benchmark suite has a test asserting the machine does at least 10M ops/s, and it
fails under AddressSanitizer. Do you lower the threshold?**
No — the threshold is fine and the test is in the wrong place. Under ASan my hash kernel
ran at 8.0e6 ops/s against 1.19e8 in release, a 15× slowdown, because every load goes
through a shadow-memory check. ASan was doing its job; the assertion was making a claim
about hardware in a build whose timings describe the instrumentation. Lowering the
threshold to something ASan passes would make the test meaningless in release too, which is
the one build where it matters. So the test skips under ASan and TSan with an explicit
reason, and the actual performance target lives in a committed results file with the
machine state recorded next to it. The general rule is that a test suite should assert
things that are true of correct code, and "the host is fast" is not one of them — a green
suite must not depend on who is running it.
