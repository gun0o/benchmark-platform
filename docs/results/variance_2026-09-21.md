## The dominant noise source, per configuration class

The diagnostics separate cleanly into two regimes.

### Many threads: host preemption and thermal drift

At 16 and 22 threads the run loses 7.6–10.6% of its throughput from start to finish — a
steady decline, which is thermal. On top of that, `cpu_fp`@22 had a worker arrive more
than 1 ms late off the start barrier in **91.8% of trials**. With 22 workers on 22 vCPUs
there is no spare capacity, so any guest or host activity delays somebody, and the trial
is timed from the barrier release to the last worker's finish — one late worker lengthens
the measured window for everyone.

These trials are counted, reported and kept. Dropping them would remove precisely the
trials that describe what running 22 threads on this machine is actually like.

### One thread: broad jitter, and nothing else

At 1 thread there are **no** late trials (0.0%), no meaningful drift at 50 ms, and no
canary trips. The distribution is almost exactly Gaussian — `stddev / (1.4826 × MAD)` is
0.95–1.36, and the 2-means split lands at the 1.5σ gap that pure unimodal noise produces
(calibrated in `m2.5/analyze.py`). So:

- **not bimodality.** No minority cluster of slow trials, so this is not core migration
  between P-cores and E-cores.
- **not spikes.** 3–55 trials in 1000 sit more than 3 robust sigmas low; removing all of
  them would not close a 0.5-percentage-point gap.
- **not drift** at 50 ms — detrending changes 4.96% to 4.88%.

What is left is that this machine simply does not repeat a 50 ms measurement to better
than ~3.5%, trial to trial, with no single identifiable event to blame. On a Hyper-V vCPU
whose physical core the guest cannot see or choose, that is the expected answer.

## The effect of each knob

Every setting was run **3 times, alternating with the others**, because a single A-then-B
comparison on a machine that drifts ~10% per minute confounds the knob with when the run
happened. Cell = median CoV across repetitions (min–max). 1 thread, 100 trials per rep.

### `--pin` on vs off

| setting | `cpu_int_ops` | `cpu_fp_ops` | `cpu_hash_ops` |
|---|---:|---:|---:|
| pinned | 5.05% (3.6–5.5) | 3.83% (2.9–3.9) | 3.66% (3.6–4.4) |
| unpinned | 4.88% (3.7–5.3) | 3.27% (2.9–4.1) | 4.80% (3.5–5.3) |

**No effect.** The ranges overlap almost completely and the sign is not even consistent
across the three workloads. A single-pass comparison earlier in this study appeared to
show unpinned winning on all three; that did not survive repetition, which is the reason
for repeating.

### Warmup on vs off

| setting | `cpu_int_ops` | `cpu_fp_ops` | `cpu_hash_ops` |
|---|---:|---:|---:|
| `--warmup 20 --warmup-ms 500` | 3.90% (3.7–4.6) | 3.59% (3.2–5.0) | 4.43% (4.1–4.7) |
| `--warmup 0 --warmup-ms 0 --spin-ms 0` | 4.85% (4.1–5.4) | 3.90% (3.8–4.1) | 3.54% (3.3–3.8) |

**No clear effect on CoV**, and again not consistent in sign. This is not evidence that
warmup is pointless — M1.2 measured trial 0 landing 7–55% below steady state without it.
It says that over 100 trials the cost of a handful of cold ones is diluted. Warmup fixes
the *bias* of the first trials, not the *spread* of all of them, and CoV only sees the
spread.

### Trial length

| setting | `cpu_int_ops` | `cpu_fp_ops` | `cpu_hash_ops` |
|---|---:|---:|---:|
| `--trial-ms 10` | 5.41% (5.3–6.4) | 3.69% (3.3–4.4) | 6.16% (5.0–6.2) |
| `--trial-ms 50` | 3.90% (3.8–5.3) | 3.80% (3.0–4.0) | 3.96% (3.4–4.7) |
| `--trial-ms 200` | **2.83%** (2.6–3.4) | **3.01%** (2.2–3.1) | 3.23% (2.9–3.8) |

**The only knob that works.** A longer trial averages more jitter inside each measurement,
so the measurement is steadier. At 100 trials, 200 ms reaches the 3% target.

### …but not over 1000 trials

Target #2 requires ≥ 1000 trials, so the 200 ms setting was re-tested at that length
(`m2.5/target2_trialms200.json`, 612 s of wall time):

| config | n | CoV | CoV detrended | drift over run |
|---|---:|---:|---:|---:|
| `cpu_hash_ops`@1 | 1000 | 3.74% | 3.31% | −6.0% |
| `cpu_int_ops`@1 | 1000 | 3.88% | 3.74% | −3.6% |
| `cpu_fp_ops`@1 | 1000 | 3.94% | 3.76% | +4.0% |

The gain evaporates. 1000 trials of 200 ms take 200 seconds per configuration, and over
200 seconds the package heats: `cpu_int`'s per-100-trial medians run +7% high early and
decline to baseline by the end. Longer trials buy steadiness within a trial and spend it
on drift between trials.

**That is the real finding of this milestone.** On a laptop, the two halves of the target
fight each other: "≥ 1000 trials" and "CoV ≤ 3%" cannot both be satisfied, because the
trial count sets a floor on how long the machine must hold still. Even with the drift
removed arithmetically, the best detrended figure is 3.31% — still short.

### Interleaving

`--interleave` rotates through configurations trial-by-trial. Same three configurations,
300 trials, sequential vs interleaved:

| config | drift, sequential | drift, interleaved | CoV, sequential | CoV, interleaved |
|---|---:|---:|---:|---:|
| `cpu_int_ops`@1 | +5.3% | **−0.2%** | 5.79% | 5.17% |
| `cpu_fp_ops`@1 | −3.6% | **−0.3%** | 3.09% | 4.05% |
| `cpu_hash_ops`@1 | +0.1% | **+1.5%** | 4.15% | 5.04% |

It does what it was built to do: drift per configuration collapses from ±5% to well under
1%, because each configuration now samples the whole thermal history of the run instead of
one slice of it. It does not reduce CoV — it was never meant to. It makes configurations
*comparable to each other*, by ensuring a drift hits all of them equally rather than
penalising whichever ran last.

## On not hitting the target

The honest summary is that this machine does not meet Target #2 and no knob available
makes it. Three things were deliberately *not* done:

1. **No outlier trimming.** Every CoV here is over the raw timed trials. Dropping the
   slowest 10% of `cpu_int`@1 would report ~3.1%; that number would be chosen, not
   measured.
2. **No re-running until a number came out well.** Each headline figure is from the
   configuration `PLAN.md` specifies, run once. Repeating a 1000-trial run and publishing
   whichever attempt dipped below 3% is selection bias wearing a lab coat.
3. **No quiet redefinition.** The detrended column is labelled a diagnostic everywhere it
   appears and is never quoted as the CoV, because a machine that drifted was genuinely
   not running at one speed.

What would meet the target is bare-metal Linux with a fixed frequency governor, no
hypervisor between the benchmark and the core, and a thermal envelope that does not
decline over three minutes. None of that is available here. The engine's job was to
measure honestly and say what the noise was; it does, and it names it.
